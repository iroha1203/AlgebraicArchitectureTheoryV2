# PR Review

PR の内容をレビューする。目的は承認することではなく、PR の主張を落とす事実を探すことである。
主張を落とそうとしても落とせなかったときだけ、Mergeable を出す。

作業規律は、PR が触る領域の guideline([Tool guideline](../../../docs/tool/guideline.md) など)と
[Workflow guideline](../../../docs/workflow/guideline.md) にある。レビューはそれに照らして行う。

## 決まり

- **ファイルを編集しない。** 直すのは実装の側である。
- **実装者の申告を証拠にしない。** PR 本文の説明、チェック済みの項目、tracking Issue の記載は、確かめる対象であって証拠ではない。コード、テスト、実行結果を自分で確かめる。
- **観点ごとに新しいサブエージェントを立ち上げる。** 実装した側の会話、期待する判定、他の観点の結果は渡さない。
- **指摘は、Issue の受け入れ要件のどれかを破るものに限る。** 各指摘に、破る受け入れ要件と、どう破るかを書く。どの受け入れ要件にも対応しない気づきは、指摘ではなく参考として返し、判定に使わない。ただし観点2は guideline の責務範囲を破るものを、観点4は受け入れ要件が求めていない追加そのものを指摘する。
- **判定は二つ。** Mergeable か Needs changes。「条件付きで可」は出さない。レビューを実行できなかったときだけ Blocked とする。

## 手順

1. **PR を読む。**
   - `gh pr view <PR> --json number,title,headRefOid,body,files,closingIssuesReferences,url`
   - `gh pr diff <PR>`
   - 紐づく Issue の受け入れ要件を読む。紐づく Issue がなければ、Needs changes の理由にする。
   - 触る領域の guideline と、振る舞いを決める仕様の文書(ツールならマニュアル)を特定する。
   - PR のブランチを確かめるときは、一時的な worktree を使う。

2. **4観点をサブエージェントで並行して実行する。** 各サブエージェントには、PR 番号、head のコミット、Issue の受け入れ要件、読むべき guideline と仕様の文書、観点の名前と目的だけを渡す。

   1. **受け入れ要件と仕様**
      - Issue の受け入れ要件の一つ一つが、差分の実体で満たされているか。
      - 実装の振る舞いが、仕様の文書と食い違っていないか。
      - 仕様の文書が決めていない振る舞いを、実装だけで決めていないか。決めたなら、同じ PR で仕様の文書に書かれているか。
   2. **責務範囲**
      - 領域の guideline の責務範囲を守っているか。ツールなら、入力が ArchMap と Law の二つだけか、ArchMap に判定を書かせていないか、計算の中核が言語の知識を持っていないか、入力から決まらないことを沈黙として返しているか。
   3. **正しさとテスト**
      - 計算や処理が正しいか。受け入れ要件の使い方で、誤った結果や落ちる入力を探す。
      - テストが、コマンドを実際に実行して、仕様の例の結果を確かめているか。テストを実行して通るか。
   4. **贅肉**
      - 受け入れ要件が求めていないものが入っていないか。先回りの運用の作り込み、守りの規則、使われない機能、仕様の文書にない一般化。

   各サブエージェントへの依頼文:

   ```text
   この PR を、割り当てた観点から敵対的にレビューしてください。目的は承認ではなく、
   PR の主張を落とす事実を探すことです。PR 本文などの実装者の説明を証拠にせず、
   コードと実行結果を自分で確かめてください。ファイルは編集しないでください。

   日本語で次を返してください。
   1. 指摘: Issue の受け入れ要件のどれかを破るものだけを、重大な順に。各指摘に、
      中心か非中心か、ファイルと行、破る受け入れ要件とどう破るか、根拠を書く。
      中心とは、受け入れ要件の実体か責務範囲を破るものをいう。
   2. 参考: どの受け入れ要件にも対応しない気づき。
   3. 反証の試み: 何を落とそうとし、どの証拠で成功または失敗したか。
   4. 確かめたもの: 読んだコードと文書、実行したコマンドと結果。
   5. 確かめていない範囲。

   指摘がないときは、どんな反証を試みて、なぜ失敗したかを書いてください。
   ```

3. **本体で確かめる(観点と並行してよい)。**
   - PR 前の共通確認(`git diff --check`、hidden / bidirectional Unicode scan)を差分に対して実行する。
   - 領域のテストを実行する。

4. **判定する。**
   - **Needs changes**: 中心の指摘が一つでもある。受け入れ要件の未達、テストの失敗も含む。
   - **非中心の指摘だけのとき**: 本体が、非中心の指摘の一つ一つを「直す」か「見送る」に振り分け、理由を書く。
     観点どうしで食い違う指摘は、受け入れ要件と guideline に照らして本体が決め、理由を書く。
     直すものがあれば、実装の側が直し、「修正後の確認」へ進む。すべて見送るなら Mergeable とする。
   - **Mergeable**: 4観点すべてに中心の指摘がなく、どの観点も反証の試みを示している。受け入れ要件を満たし、テストが通る。非中心の指摘は、すべて直したか、理由を書いて見送った。
   - **Blocked**: PR を取得できない、サブエージェントを立ち上げられない、テストを実行できない。本体が観点を肩代わりして Mergeable を作らない。
   - 観点の結果に、根拠のない指摘や、反証の試みのない「指摘なし」があれば、その観点をやり直す。

5. **監査コメントを投稿する。** マージの前提になる。`gh pr comment <PR> --body-file <ファイル>` で、次を投稿する。
   - 判定と、レビューした head のコミット
   - 観点ごとの指摘、参考、反証の試み
   - 非中心の指摘ごとの振り分け(直す / 見送る)と理由
   - 受け入れ要件ごとの照合結果
   - 実行した確認とテストの結果、確かめていない範囲

   投稿に失敗したら、判定は Blocked とする。

## 修正後の確認

実装の側が指摘をまとめて直したら、直した指摘の種類で確認の仕方を決める。

- **中心の指摘を直したとき**: 直した後の head で、手順1から全体をやり直す。
- **非中心の指摘だけを直したとき**: 新しいサブエージェントを一つ立ち上げ、「直す」に振り分けた指摘と修正の差分だけを渡して、次を確かめさせる。
  1. 各指摘が実体で直っている(記述の付け替えで消していない)。
  2. 差分に、指摘の外の変更がない。
  3. 差分が、受け入れ要件と責務範囲を変えない。仕様の文書への変更は、直した振る舞いの書き戻しに限る。

  三つとも満たせば、結果を監査コメントに追記し、Mergeable とする。一つでも満たさなければ、全体をやり直す。

## 報告

判定、指摘、実行した確認、監査コメントの URL を、日本語で報告する。
