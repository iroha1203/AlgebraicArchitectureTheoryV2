# PRD Loop

PRD を完了まで実装する。1周は、ギャップ分析 → Issue → 実装と PR → `pr-review` → マージ。
受け入れ要件がすべて満たされたように見えたら、独立した完了レビューで閉じる。

作業規律は、触る領域の guideline([Tool guideline](../../../docs/tool/guideline.md) など)と
[Workflow guideline](../../../docs/workflow/guideline.md) を読んで従う。

## 入力

- PRD のパス(必須)。
- 任意: `max-iterations <N>`(この実行で回す周回の上限)、対象にする受け入れ要件の絞り込み。

## 決まり

- **PRD はループの間変えない。** 矛盾や実装できない要求が見つかったら、直さずに止まって報告する。PRD を変えるのは人である。
- **1周 = 1 Issue = 1 PR。** 小さく切る。同時に二つの PR を開かない。
- **状態は GitHub に置く。** tracking Issue に進み具合を残し、セッションの記憶に頼らない。中断しても、同じ PRD で起動すれば同じ所から再開できる。
- **完了への近道をしない。** 受け入れ要件を読み替えたり弱めたりしない。実装を求める要件を docs の変更だけで満たしたことにしない。進まない要件は、止まって報告する。
- **PRD が求めていないものを足さない。** ギャップ分析は PRD の受け入れ要件の文言に限る。
- **実装とレビューを同じ文脈で行わない。** レビューは `pr-review` が立ち上げる独立したサブエージェントが行う。

## tracking Issue

- タイトル `PRD Loop: <PRD のファイル名>` の open Issue を探し、なければ作る。
- 本文には、PRD のパスとコミット、受け入れ要件の checklist(PRD の文言を1項目1行で写す)だけを置く。
- 各周の終わりに、コメントを1件足す: `iteration N: <受け入れ要件> → Issue #X → PR #Y → merged | needs-changes | stalled | blocked`
- checklist の check は、「過去の周がそう主張した」ことしか意味しない。完了の証拠には使わない。

## 手順

0. **前提を確かめる。**
   - 作業ツリーに未コミットの変更があれば、始めずに報告する。
   - main を最新にする。
   - PRD の「## 問い」と受け入れ要件を読む。tracking Issue を確かめるか作る。

1. **ギャップ分析。**
   - 次に扱う受け入れ要件を一つ選び、その要件と直接の依存だけを、今のコード・テスト・docs と突き合わせる。全要件の事前監査はしない。
   - 満たしているかは実体で確かめる。要件が求めるテストが実在し、通るか(必要ならテストを実行する)。
   - 選ぶ順は、他の要件の前提になるもの、依存が少ないもの。
   - 人の判断や外部の入力が要るものは `blocked` として tracking Issue に理由を書き、飛ばす。
   - 未着手の要件も、未達・blocked・stalled もなければ、手順5へ進む。

2. **Issue を作る。**
   - 受け入れ要件には、対応する PRD の受け入れ要件を文言のまま引用する。
   - 同じギャップを扱う open Issue があれば、それを使う。
   - tracking Issue の sub-issue にする。

3. **実装して PR を出す。**
   - 専用のブランチで実装する。
   - 実装中に、マニュアルや仕様が決めていない振る舞いを決めたら、同じ PR で仕様の文書に書く。
   - 領域の guideline の検証を実行する(ツールなら `cargo test`)。PR 前の共通確認を実行する。
   - PR を出す前に、自分の差分を Issue の受け入れ要件と突き合わせる。PR 本文に、差分にない主張を書かない。
   - PR は `.github/pull_request_template.md` に沿って日本語で書く。受け入れ要件をすべて満たしたときだけ `Closes #N` を書く。

4. **レビューしてマージする。**
   - `/pr-review <PR>` を実行する。CI の完走は待たない。
   - **Mergeable**: 次の三つがそろったら、`gh pr merge <PR> --merge --delete-branch` でマージする。
     1. `pr-review` の判定が Mergeable
     2. CI が green(マージ直前に `gh pr checks <PR>` で確かめる。失敗なら Needs changes として手順3へ戻る)
     3. `pr-review` の監査コメントが PR に投稿されている
   - **Needs changes**: finding をまとめて直し、`pr-review` の「修正後の確認」で判定し直す。同じ Issue で Needs changes が2回続いたら、その要件を `stalled` とし、PR を開いたまま停止の判定へ進む。
   - **Blocked**: 理由を tracking Issue に書き、停止の判定へ進む。
   - マージしたら main を最新にし、tracking Issue に iteration コメントを足して checklist を更新する。手順1へ戻る。

5. **完了レビュー。**
   - 新しいサブエージェントを一つ立ち上げ、PRD のパス、tracking Issue の番号、main の最新コミットだけを渡す。ループを回した側の「満たしたはず」は渡さない。
   - 依頼する内容:
     - PRD から受け入れ要件を1項目1行で取り出し、各項目をコード、テスト、実行結果の一次証拠で判定する(満たした / 未達 / 未確認)。tracking Issue、PR 本文、checklist は証拠にしない。
     - PRD の「## 問い」に、今の状態が答えているかを、受け入れ要件とは別に判定する。
     - ファイルは編集しない。
   - すべて満たし、問いにも答えていれば、結果を tracking Issue にコメントして close し、終了する。
   - 未達・未確認があれば、それをギャップとして手順2へ戻る。問いに答えていないときは、人の判断事項として止まる。

## 停止

次のどれかで止まって報告する。止まることは失敗ではない。

- 完了: 完了レビューが、すべての要件を満たし、問いにも答えていると判定した。
- 全 blocked: 残りの要件がすべて blocked か stalled。
- stall: 同じ要件が2周続けてマージに至らない。
- PRD の欠陥: PRD の矛盾や実装できない要求が見つかった。
- budget: `max-iterations` に達した(指定したときだけ)。

## 報告

終了したら、次の順で日本語で報告する。

1. 終了の理由
2. 受け入れ要件ごとの状態(満たした / 未達 / blocked / stalled)
3. 完了レビューの結果(実行した場合)
4. 周ごとの Issue、PR、結果と、main の最新コミット
5. 人の判断が要る点と、次に再開するとき最初に扱う要件
