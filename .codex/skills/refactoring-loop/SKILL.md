# Refactoring Loop

点検 → 短い計画の固定と人間確認 → 改善・検証 → 条件の達成確認 → PR のマージと記録同期を行う。
一回の起動は、確認済みの改善対象だけを扱う。起動頻度や自動スケジュールは人間が別途決める。
所定の条件を満たし、人間の判断待ちがない場合は、Codex の判断でマージまで進める。
個別にローカルのみ・マージしない等の指定があれば、その納品状態まで進める。

## 入力と参照

- 対象パスまたは改善課題、関連 Issue、既存の確認済み計画を受け取る。
  対象を特定できなければ点検範囲を人間に確認する。
- [AGENTS.md](../../../AGENTS.md)、[Workflow guideline](../../../docs/workflow/guideline.md)、
  触る領域の guideline を読む。Tooling では[Tool guideline](../../../docs/tool/guideline.md)を読む。
- ArchSig の期待動作は[マニュアル](../../../docs/tool/archsig_manual/README.md)と対象章から読む。
  このループでは既存マニュアルを参照し、そこに定められた振る舞いを保存する。
  マニュアルの執筆・改訂はループに含めない。コードや既存テストは現状の証拠として使い、
  期待動作を実装の現状に合わせて変更しない。マニュアルの曖昧さ・矛盾は人間へ戻す。
- PRD が関係する場合は[PRD guideline](../../../docs/prd/guideline.md)を読む。
  PRD は対象範囲・受入条件を定め、期待動作にはマニュアルを参照する。
  機能の追加・仕様の変更は、この改善計画へ混ぜず既存[prd-loop](../prd-loop/SKILL.md)側の仕事として提案する。

## 1. 点検して計画を固定する

1. 作業ツリー、base commit、対象コード・テスト、既存 Issue / PR を確認する。
   他担当の進行中の変更と重ならない worktree を使う。対象が競合する場合は調整を求める。
2. 対象と直接依存を読み、改善が必要な箇所を、具体的なコードと影響で示す。
   重複、責務の混在、読みにくい制御、検証しにくい構造などから今回扱うものを選ぶ。
   改善が不要なら、点検範囲と見送り理由を報告して正常終了する。
3. 次の情報を一つの短い計画に置く。
   - 対象と改善理由、base commit、期待動作を読むマニュアルの章・節。
   - 改善条件: 何が変われば今回の改善を達成したと判定できるか。
   - 保存する振る舞いと、その回帰検証の方法・比較対象。
   - 非対象、依存する問題、必要な人間判断。
   - 今回の納品状態(既定はマージと記録同期まで)と、個別に指定された操作の制限。
4. 同じ課題の既存 Issue を優先し、計画と確認記録の置き場を一つ決める。
   Issue 本文に既にある情報は参照し、不足分だけ本文またはコメントで補う。
   別の tracking Issue、PRD、計画ファイルを機械的に増やさない。
   新規 Issue が必要なら[issue-creater](../issue-creater/SKILL.md)で重複確認と起票を行う。
   GitHub への書込みが許可されていない場合は、レビュー可能なローカル計画を示し、
   保存場所を報告する。後で移す際も、参照先を一つにそろえる。
5. 計画を人間に示し、確認を得てから実装へ進む。既存の確認済み計画が今回の対象・base に
   適用できれば、その確認記録を使う。人間の返答待ちを実装許可と解釈しない。
   再開時は計画と確認記録を読み、base や依存の変化が条件に影響するなら再確認する。

## 2. 改善と検証を回す

- 固定した計画の未達条件を一つ選び、レビュー可能な単位で改善する。
  単一 Issue の実装手順は[issue-to-pr](../issue-to-pr/SKILL.md)を使い、PR 作成後は次のレビューとマージへ進む。
  個別にローカルのみ等の指定がある場合は、その制限を呼出先にも渡して指定の納品状態で止める。
  計画の対象・改善条件・保存する振る舞いを変える必要が出たら、先に人間へ戻す。
- 変更前の検証結果を記録し、変更後に同じ保存条件を検証する。
  既存テストの成否だけでなく、その assertion が保存条件を確かめているかを見る。
  検証方法・実行経路は領域の guideline と計画を参照し、失敗・未実行・未確認を区別する。
- ループ中のバグは次の基準で扱う。行数だけで分類しない。

  | 判断 | 処置 |
  | --- | --- |
  | 期待動作がマニュアル等から明確、修正が局所的、回帰テストで検証可能 | 軽微なバグとしてその場で直す。再現、期待動作の根拠、変更箇所、回帰テストを記録する。 |
  | 仕様判断が必要、広範な変更、重大な影響、または分類不明 | 既存 Issue を確認し、なければ起票して人間に報告する。修正に進まず判断を求める。 |

  リファクタリングの振る舞い保存と、既存バグの意図した挙動修正は差分・記録・検証で区別する。
  軽微なバグ修正では、対象の期待動作への修正を追加記録し、それ以外の保存条件を維持する。
  仕様や対象の拡大が必要なら軽微扱いにしない。Issue の取得・起票ができなければ、
  起票済みとせず、再現情報と未起票の理由をローカルに残して報告する。
- 重大問題が今回の安全な実装・検証を妨げるなら、依存する作業を止めて報告する。
  独立した作業を続ける場合も、影響の切り分けを記録し、止めた条件を完了扱いにしない。

## 3. レビューを分類し、改善条件の達成を判定する

- ローカル納品では自己点検と必要な独立確認を行う。
  PR を扱う場合の正式レビューは[review-pr](../review-pr/SKILL.md)、
  修正後確認は[共有review protocol](../_shared/review-protocol.md)に従う。
  新たな発見と、今回の必須作業への追加を分け、指摘ごとに次を判定する。

  | 指摘と今回の条件の関係 | 処置 |
  | --- | --- |
  | 改善条件、保存条件、軽微バグの期待動作、必要な検証を破る | 今回の必須修正として直し、該当条件を再検証する。 |
  | 今回の条件を破らない独立した追加改善 | 既存 Issue に関連付けるか別 Issue へ送り、今回の条件に追加しない。 |
  | 仕様・対象の変更が必要、または依存する重大問題で検証不能 | 該当作業を停止し、人間へ判断を戻す。 |

  正式レビューのゲートが未合格・実行不能なら、その状態を維持する。
  範囲外の提案として処理しても既存ゲートを迂回しない。既存規約との衝突で合格できなければ、
  条件を勝手に拡大せず、衝突内容を人間に報告する。
- 固定した改善条件と保存条件、追加した軽微バグの回帰検証が満たされ、納品状態に必要な確認が
  終われば改善条件の達成とし、手順4へ進む。レビュー指摘ゼロや追加改善の全消化を完了条件にしない。
- 同じ未達条件への対応を2回続けても、条件を満たす実体や検証の進展がなければ `stall` として止める。
  適用する既存 SKILL の停止規約、明示された予算・周回上限にも従う。
  進捗の無い同じ検証・レビューを繰り返したり、停止回避のために条件を弱めたりしない。

## 4. 完了条件を確認し、PRをマージする

1. 個別の納品指定を確認する。ローカルのみ・PR まで・マージしない等の指定があれば、
   その状態と必要な確認を満たした時点で結果を記録して終了する。
2. PR をマージする場合は、直前に最新 head を取得し、次を確認する。
   - 固定した計画の改善条件・保存条件と、追加した軽微バグの回帰検証が満たされている。
   - [review-pr](../review-pr/SKILL.md)による規定の独立レビューが内容合格であり、
     必要な修正後確認を含む監査記録が PR に投稿され、確認対象が現在の head に対応している。
   - `gh pr checks <PR>` 等で、現在の head の必須 CI がすべて成功している。
     必須 check の欠落・未確認・実行待ちは成功として扱わない。
   - [Workflow guideline](../../../docs/workflow/guideline.md)の保護対象と、リポジトリの
     マージ要件を満たし、人間によるマージが必要な対象や未解決の人間判断事項がない。
3. すべて満たしたら、都度の人間確認を求めず、Codex の判断で
   `gh pr merge <PR> --merge --match-head-commit <確認済みhead>` を実行する。
   head が変われば、その head の検証と規定のレビュー・修正後確認へ戻る。
   CI 待ちはマージを保留し、CI 失敗は該当条件の修正・検証へ戻る。
   必須ゲートが通らない、保護ルール上の人間マージが必要、判断待ちの問題がある場合は、
   理由を報告して該当作業を止める。マージ要件を緩和・迂回しない。
4. マージ成功を確認し、merge commit と検証・レビュー結果を計画の置き場に記録する。
   関連 Issue の条件別状態と完了記録を同期し、受入条件をすべて満たした Issue だけを閉じる。
   別の未達条件が残る Issue は開いたままにする。同期できなければ、マージ済みと同期未完了を
   区別して報告し、同じ PR のマージを繰り返さず記録同期から再開する。
5. 指定の納品状態と記録同期が完了したら終了する。次の改善対象を自動で選んで周回を増やさない。

## 終了時の記録

計画の置き場に結果への参照を残し、次を報告する。再開時はその記録から未達条件を選ぶ。

1. 終了理由: 完了 / 見送り / 人間判断待ち / blocked / stall / 指定上限。
2. 改善前後の構造、base と結果の commit、PR / merge commit、条件ごとの達成・未達・未確認。
3. 保存した振る舞い、バグとして変えた挙動、それぞれの検証と結果。
4. 未解決問題と Issue、未起票・未確認の理由、止めた作業と停止理由。
5. 人間の判断事項と、再開に必要な入力。

この SKILL に従うリファクタリングの実行依頼では、確認済み計画の実装・push・PR 作成・
手順4の条件を満たした PR のマージ・Issue と完了記録の同期までを、ユーザー指定の運用方針として進める。
個別の操作制限を優先し、公開や対象外の操作、実行環境の許可拡大へ承認を広げない。
SKILL の作成・修正・読取レビューだけの依頼では、実際のリファクタリングループを起動しない。
