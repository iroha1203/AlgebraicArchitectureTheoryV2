# ArchSig QA Loop

マニュアルを読む → 項目を設計・記録する → 実際の配布物とCLIを検証する → findingを報告する
→ 修正候補を再検証する。QAは修正を実装側へ戻し、リリース可否の判断材料を人に渡す。
自動スケジュールやリリース公開はこのループに含めない。

## 入力と許可範囲

- リリース候補commit / version、合意したリリース範囲、配布予定の形、対象binary、
  既存tracking Issue、今回の操作制限を受け取る。足りない情報は未確定と記録し、
  依存する項目を保留して必要な入力を人に求める。候補や配布形態を推測で作らない。
- [AGENTS.md](../../../AGENTS.md)、[Workflow guideline](../../../docs/workflow/guideline.md)、
  [Tool guideline](../../../docs/tool/guideline.md)を読み、作業ツリーと他担当の進行中の作業を確認する。
  独立worktreeと隔離fixture / 一時領域で進める。実データや本番への副作用を勝手に起こさない。
- SKILLの作成・修正・読取評価だけの依頼は、実QA、Issue起票・コメント、push / PR / mergeの
  許可を含まない。QA実行依頼でも個別の操作制限を優先する。
  GitHub書込みが未許可なら、項目と証拠をローカルにまとめ、保存先と未同期の理由を報告する。
  必要な外部書込みを具体化してから許可を求め、許可待ちを実行許可と解釈しない。
- 実装側への引渡しはfindingと関連Issue / PRへの参照で行う。
  [prd-loop](../prd-loop/SKILL.md)、[refactoring-loop](../refactoring-loop/SKILL.md)、
  [review-pr](../review-pr/SKILL.md)は責務の参照先であり、このQAから自動起動しない。
  QA内で製品コード、同梱SKILL、マニュアルを修正しない。

## 1. 候補と期待動作を固定する

1. [ArchSigマニュアル](../../../docs/tool/archsig_manual/README.md)の全章を読み、
   今回のリリース範囲に必要な章節を選ぶ。マニュアルの参照commitを記録する。
   実装や既存テストは現状・fixtureの参考とし、期待結果はマニュアルから導く。
   マニュアルを執筆・改訂したり、期待結果を実装に合わせて書き換えたりしない。
   曖昧さや矛盾で期待結果が決まらない項目は、人間判断待ちとして該当節と問いを報告する。
2. 環境を記録する: macOS版とbuild、CPUアーキテクチャ、必要なruntime / 解析器の版、
   実行日時、実行ディレクトリ。Rosetta等を使う場合はホストCPUと実行方式も区別する。
   当面はMacのみを対象とし、Linux / Windowsは今回の完了条件に入れない。
3. 候補commit / versionと実際に使うbinaryの対応を記録する。
   binaryの絶対パス、SHA-256、入手元、配布物の名前・digestと出所、またはbuild手順と
   source commit / 作業ツリー状態を残す。version表示が取得できる場合は実測値も残す。
   version文字列だけでcommitとの対応が確定したとは扱わない。
   対応未確認ならその理由を記録し、候補のQA合格を宣言しない。
4. 配布予定の形からの入手・展開・インストールと、そこからCLIを呼べることを項目にする。
   開発用buildだけの検証を配布物のインストール検証に代用しない。
   配布形態が未定なら、インストール項目は `未実施`、配布情報は `未確定 / 未検証` と記録する。

## 2. マニュアルから項目を設計し、記録する

項目・finding・測定記録を作るときは[記録テンプレート](references/qa-records.md)を読む。

- マニュアルの章節と項目IDを対応づけ、入力、前提、実行コマンド、期待結果とその根拠、
  観測方法、対象外を実行前に明示する。主要操作、異常入力、コマンド組合せを含め、
  実装の単体テストをなぞるだけの設計にしない。章節に対して項目がない場合も理由を残す。
- 第2章の一周と第8章のCLIを起点に、第3〜5章の入力・問い、第6章の出力と検算へ対応づける。
  `record → status → check → show / verify`、候補検査・分割・組立て・比較・diffなど、
  前の生成物を次へ渡す操作を、今回の範囲に応じて設計する。
  第7章の同梱SKILLは、CLIの確定的な判定と分けて測定する。
  第1・9章の説明や扱わない範囲も読み、主張の範囲を確認する。
- 第6・8章の期待結果に従い、Law違反や沈黙の結果と、結果を作れない入力エラーを区別する。
  `outcome: fails / silent`や終了コード0だけをQA合否と同一視しない。
  期待した沈黙が正しく返ればそのCLI項目は合格になり得る。
- 対象version / リリース範囲の既存tracking Issueを優先し、open / closedと関連Issueを
  読み取って重複を避ける。候補更新は同じ記録に履歴を追加する。
  新規起票が必要で許可もある場合だけ[issue-creater](../issue-creater/SKILL.md)の手順を使う。
  tracking Issueに項目一覧と証拠の参照を集約し、会話の記憶だけに依存しない。
  生ログは再読可能な保存先に置き、Issueから参照する。巨大なログを本文へ複製しない。
- 単体テストがpassでもQA項目を省略しない。単体結果は参考情報として記録する。

## 3. 実測し、findingを報告する

1. 隔離fixtureの入力内容・digestと前提を固定し、記録したbinaryを実際に実行する。
   正確なコマンド、cwd、必要な環境設定、stdout / stderr、終了コード、生成物と変化を
   取得し、項目ID・候補commit・binary digestに結びつける。
   終了コードをパイプや後続コマンドで失わない。期待した観測を取れなければ合格にしない。
2. 期待結果と実測を照合し、項目を次の状態で記録する。

   | 状態 | 判定 |
   | --- | --- |
   | 未実施 | まだ実測していない。理由と再開条件を残す。 |
   | 合格 | 確定した期待結果を満たす実CLIの証拠があり、候補との対応も確認できる。 |
   | 不合格 | 確定した期待結果との差を観測した。findingへ結びつける。 |
   | 中断 | 一部を測定して途中で止まった。測定済み範囲と残り、理由、再開条件を残す。 |
   | 実施不能 | 環境・前提・依存問題等により実測を完遂できない。理由、途中の証拠、再開条件を残す。 |
   | 人間判断待ち | 期待結果の曖昧さ等で合否基準が未確定。測定済みかどうかも記す。 |
   | 実測完了・人間判定待ち | 同梱SKILL等の測定を完遂し、全試行を報告した。合否は人に渡す。 |
   | 実測完了・人間判定済み | 人の回答を別欄へ記録した。観測結果と、人が判断した合否・条件を区別して保持する。 |

   中断した項目は途中の実測を残し、未測定部分を合格にしない。再開可能なら `中断`、
   前提が満たせず再開できなければ `実施不能` とし、中断履歴も保持する。
   再開時はtracking Issueの最後の記録と候補 / binary / fixtureを照合し、未完了部分から進める。
   継続は同じ試行IDへ追記し、最初からやり直す場合は理由と新計画・別試行IDを残す。
   期待結果の曖昧さに人の回答を得た場合は基準と回答を記録し、未測定なら `未実施`、
   測定済みなら既存証拠を確定基準で照合する。同梱SKILLの人間判定は上表の専用状態を使う。
3. 同梱SKILL等、結果が揺れる項目では、モデル / 版、設定、入力、試行数、観測方法を
   実行前に定める。各試行をIDで記録し、失敗・中断を含む全試行と未実施の予定試行を残す。
   成功まで回す、都合のよい試行だけを採る、未測定の成功率を作ることを禁止する。
   再試行・条件変更が必要なら理由と新しい測定計画を残し、旧試行を保持する。
   試行の終了状況（完遂 / 中断 / 不能 / 未実施）と観測結果（成功 / 失敗等）を別軸で数える。
   失敗という結果を得た完遂試行も測定完遂に含め、測定自体の失敗は中断 / 不能として理由を残す。
   中断・不能を成功率の分母から黙って除外せず、実測の件数と分母を明示する。
   測定結果だけで自動passにせず、`実測完了・人間判定待ち`として人へ渡す。
4. findingには再現条件・コマンド・入力、期待と実際の差、影響、マニュアル節、
   候補commit / binary、証拠を含める。既知制限、既知問題、新問題、仕様の曖昧さを区別し、
   既存Issueがあれば関連付ける。既知という理由で観測した不一致を合格へ変えない。
   合意した範囲外の改善提案を勝手に今回の必須項目へ追加しない。
5. 重大問題が依存する検証を不可能にしたら該当項目を止める。独立な項目は、
   影響を切り分けて継続できる。修正は実装側へ戻し、修正候補が来るまで同じ失敗を回し続けない。

## 4. 修正候補を再検証する

- 修正候補のcommit / version、binaryと配布物、マニュアル参照を更新し、旧結果を履歴に残す。
  最新候補の項目別状態を分け、旧候補の合格を無条件に引き継がない。
- 該当findingと影響範囲、前後の生成物を使う操作、配布物変更時のインストールを検討し、
  再試験する項目と範囲・理由を記録して実測する。再試験しない項目も、変更との関係と
  旧証拠を利用できる理由を示す。影響が分からなければ未確認として再試験対象に残す。
- マニュアルやリリース範囲の変更は人の判断を受けた入力として記録する。
  再設計した項目と理由、過去の期待・実測を残し、過去の不合格を消さない。

## 終了と引渡し

今回の許可範囲で実行可能な予定項目は継続する。単に未実施理由を書くことを早期終了の根拠にしない。
実行可能な項目の測定・証拠・finding報告が揃い、残項目がすべて人間判断・修正候補・前提の待ちなら、
未実施 / 不能 / 中断の理由と再開条件を残してQA作業を一区切りにする。
ユーザー指定の範囲・上限や中断に達した場合も、その停止理由と残項目を報告する。
QA実施の完了と、リリース承認・公開を分ける。人間判定待ちや未解決findingを残して
リリース可とは宣言しない。人が既知リスクを受け入れた場合も、その判断・対象候補・条件を
観測結果と別に記録し、不合格 / 不能 / 未実施をpassへ書き換えない。
リスクを受け入れたfindingは `未解決` のまま受入判断を別欄に置き、実測で解消を確認した状態と区別する。
QA作業を一区切りにしただけで未解決項目を閉じない。

終了時はtracking Issueまたはローカル記録への参照を添え、次を報告する。

1. 終了理由、候補commit / versionとbinaryの対応、Mac環境、配布物のインストール実測状況。
2. 項目別状態と件数、章節の対応、実行したコマンドと証拠への参照、未実施・不能・中断の理由。
3. finding、既知制限と新問題、修正側へ渡す再現情報、再検証結果と範囲の理由。
4. 全試行の測定結果と人間判断事項、未解決リスク、再開入力、Issue未同期・未起票の理由。
5. QA作業の終了状態と、別に残るリリース可否の判断・公開の状態。
