# n1018: ArchSig実践検証の振り返りと共通構造の強み

[Issue #6156][parent]と関連Issueに記録された、2026年11月6日までの実在OSSでの検証を
振り返り、ArchSigの位置づけ、強み、反省点、次に行うことを整理する。
実施結果は参照先の記録に基づき、その結果から製品設計について読み取ることを考察として述べる。
実行単位の証拠、作業状況、受け入れ判定は各Issueに置く。

中心に置く考察は、**代数幾何由来の共通構造によって、必要情報の選択、変更範囲の検討、
局所案の統合、後続変更をつなげられることが、ArchSigの強みである**というものだ。
今回の検証では、その接続を使った設計と実装の事例が生まれ、観測・実装への接続・利用手順の
具体的な改善点も得られた。

## 1. ArchSigをどう位置づけるか

ArchSigは、Atom定義・Law・ArchMapから対象、操作、対応を構成し、選択した要求に対する
診断、変更候補、局所からの統合、比較を計算する。入力の役割は
[Tooling guideline](../tool/guideline.md#責務範囲入力トライアドの正本)、
製品の方向は[製品コンセプト](../tool/archsig_v0_6_0_concept.md)にある。

検証を踏まえた位置づけを、次の5点にまとめる。

1. **問いに応じて使う道具である。** ソース読解、解析、設計検討、試験の中で、
   候補間の関係や複数条件の整合を計算する仕事を担う。
2. **Law定義と観測には手間がかかる。** 要求の整理、原始事実の読取り、入力作成、訂正、
   実装後の再観測を利用費用に含める。作った構造を後続の判断へ引き継ぐことも評価する。
3. **TLA+、各種解析ツール、テスト手法と使い分ける。** それぞれが調べる問いと証拠を対応させ、
   同じ開発の中で組み合わせる。
4. **強みは、代数幾何由来の共通構造にある。** 同じ対象・操作・対応を使って、理解、診断、
   変更候補の検討、分担と統合、後続変更を接続する。
5. **複数の仕様・要件が相互に関わる開発を得意領域とする。** 一部の変更が別の要求へ影響する仕事、
   複数担当の局所案を全体として成立させる仕事が、今回の成果から見える適用先である。

複雑さの中身は、要求の数に加えて、要求・操作・担当範囲の相互作用にある。
「何を保ったまま、どこを変えられるか」を繰り返し問う開発に、ArchSigの計算を置く。

## 2. 検証で何が起きたか

### 2.1 横断調査から、同じ仕事の継続開発へ

初期の横断調査は、ソース観測等を行った39作業・30題材として集計された。
その内訳は分析CLIを含む19作業、含まない20作業である。
この初期集計と、以下で扱う後続の実装・比較の成果を分けて読む。
同じ題材の継続や再計算は、初回観測と区別する。
[初期集計][breadth]

初期T1の監査では、ソースから読んだ分岐、出口、条件をCLIで再検査する利用が多かった。
その成果は、条件の明示化と再現可能な確認にあった。一方、通常の読解や試験で判断が進む題材では、
担当がArchSigの分析計算を選ばない例も残った。[T1監査][t1-audit]

後続の検証では、同じ仕事の候補設計、分担実装、統合、再観測、次の変更までを進めた。
そこで、計算結果と開発判断の対応が具体的になった。

| 題材 | 実施結果 | 開発への接続 |
| --- | --- | --- |
| Requests | CookiePolicy、要求cookieの非永続化、応答APIの保存を扱う候補を実装。通常テスト14件成功。再観測後の7 Law・42回答を独立再計算した。 | policyだけを保つ案とAPIも保つ案の違いを明示し、複数の保存条件を実装後に確認した。[記録][requests] |
| SQLAlchemy | 同期・非同期入口を分担実装して統合。通常テストは同期187件成功・12件skip、非同期5件成功。有限診断と最終ソース再観測を行った。 | 同じ操作と条件を、対象の分類、依存の見直し、入口別実装、統合後の確認へ引き継いだ。[記録][sqlalchemy] |
| Saleor | 候補域での共有情報、変更範囲、局所案と全体案の対応を計算。ArchSig・通常・TLA+の3群が、実装・移行・後続変更・最終補修まで独立受入に到達したと記録された。 | 候補の比較から変更する範囲を決め、実装と後続変更へ進んだ。受入検査で追加の欠陥を発見し補修した。[記録][saleor] |
| Blinker | 優先順位の追加、表現変更、once追加の3段階で継続利用。弱参照cleanupの誤観測が段階2へ持ち越され、独立監査で訂正された。 | 構造と根拠を引き継ぐ利用を経験し、変更時に再確認する観測の選び方が課題として具体化した。[記録][sqlalchemy] |

### 2.2 計算が設計判断へ接続した箇所

Saleorの標準app向けの検討では、storageだけの公開情報から、clock、coordination、recovery等を
含む共有情報へ進んだ。続く変更範囲の比較では、宣言・列挙した972候補について、taskのみの変更、
paymentまでの変更では解がなく、注文等との共有部分を含めると8解が得られた。
この結果を使って変更範囲を広げた。[Saleor再評価][saleor]

局所からの構成では、重なりで一致する局所案の組が8組あり、それぞれに全体案が1つ対応した。
組立て後に局所へ戻した結果も一致した。ここで得られたのは、8つの代替案と、各局所案の組から
全体案への対応である。これにより、採用する設計を選ぶ段階まで候補を保持できた。

SQLAlchemyでは、Coarse v2で返されたordinary objectに対する有限診断は、
整合する局所案が1組、大域解とその前像が0だった。この版のbuildは非有限List型に対して
未決を返している。実装再観測版v3ではbuild・localize・diagnoseが成立し、局所案1組、
大域解1、前像1となった。局所の整合と、許された全体案としての実現可能性を別々に調べた結果である。
[SQLAlchemyの後期計算][sqlalchemy]

これらは、計算によって初めて不具合を発見する使い方に加え、候補を絞る、変更範囲を決める、
代替案を保持する、局所案と全体案の対応を確認する使い方に価値があることを示す事例である。

### 2.3 実案件が製品の改善を促した

初期Saleorの固定入力は302対象・2052 Atom・10問だった。初期測定では60秒で中断され、
全問がcancelledとなった。その後の実装改善を経て、全10問が自然終了するようになった。
[初期測定][perf-start]、[全問の完了記録][perf-completion]

性能改善PR #6185の固定旧新1組では、同じ入力について次の結果が得られた。

| 測定値 | 修正前 | 修正後 |
| --- | ---: | ---: |
| 実時間 | 46.64秒 | 33.95秒 |
| CLI CPU時間 | 46.32秒 | 33.90秒 |
| 最大RSS | 3.56GB | 0.586GB |

この比較では出力JSONと終了状態が一致し、保存済み16実行の再計算でも一致した。
実案件で生じた複製・保持の費用を調べ、結果を保ちながら削減した改善である。
[測定と検証][perf-fact]

また、Saleorの実装継続では、同一root型のfield更新を含むObjectAlgebra Mapが内部エラーになる
不具合が見つかり、[Issue #6256][map-bug]と[PR #6257][map-fix]で修理された。
設計上の対応を実際に使う工程が、製品の計算経路を検証する機会にもなった。

### 2.4 費用として何を測ったか

Saleorの後続変更Cと補修について記録された、AI担当の累積稼働時間は次のとおりである。

| 群 | Cとその補修 | 最終品質補修 | 記録小計 |
| --- | ---: | ---: | ---: |
| ArchSig | 26.66分 | 17.32分 | 44.0分 |
| 通常 | 13.93分 | 14.34分 | 28.3分 |
| TLA+ | 25.94分 | 12.41分 | 38.3分 |

この区間では通常群の小計が最も小さく、ArchSig群が最も大きかった。
区間値には読解、設計、観測・モデル作成、試験、CLI待ち、失敗修正、記録・引継ぎを含み、
独立受入待ちの非稼働時間を除く。[時間定義と訂正][saleor]

比較した作業の出発点にも差があった。通常群ではCの依頼本体をBで実装済みだった。
最終補修はArchSig群が新担当、通常・TLA+群がC担当の継続だった。
前段A/BはArchSig群だけAstraで、C・補修の指定はSolだった。
持ち越した欠陥も異なるため、この小計は前段成果と担当配置を含む今回の作業系列の費用として読む。

再理解・再観測だけの時間と、人間の作業時間は分離計測されていない。
取得小計と、初期読解・共通準備・統括作業・製品修理等を含む全工程費用を区別する。
後続変更の完成と構造の再利用は実施結果として残し、負担の変化は次の計測で直接調べる。

## 3. 強みは、共通構造が複数の問いをつなぐこと

### 3.1 対象・操作・対応を共通に持つ

ArchSigが共通に扱うものは、Atom定義による語彙、観測した事実から構成する対象、
Law、許された操作、対象間の対応と保存条件である。
それらを用いて、次の問いを接続する。

| 開発上の問い | 共通構造に対する計算 |
| --- | --- |
| 必要な情報は何か | 公開情報への射影が、選択したLawの判断を保つかを調べる。 |
| 各担当はどんな案を作れるか | 許可変更から候補を作り、局所で読める条件を満たす案を求める。 |
| 各案を全体へ統合できるか | 重なりでの一致と、対応する大域候補の前像を求める。 |
| どこまで変更すればよいか | 固定部分と変更を許す範囲を定め、要求を満たす候補を求める。 |
| 次の変更で何が保たれるか | 対象間の対応、操作、Lawの保存を確認し、合成した対応を比較する。 |

各構成の具体的な意味は[核の標準構成と計算範囲](../tool/archsig_v0_6_0_io/computations.md)にある。
前の計算で得た対象や対応が、次の問いで使われる。その関係を保持することで、
要求から設計、実装後の確認までの判断を追える。

SQLAlchemyでは、定義やLawを保持しながら変更箇所を再観測し、最終的に21問の成立を確認した。
一方、CLIの`--reuse`は入力identityの不一致で旧候補を拒否し、通常評価へ進んだ。
この事例の再利用成果は、定義・Law・対応を開発で引き継いだことであり、導出cacheの再利用とは
別の工程として記録されている。[再観測と再利用][sqlalchemy]

### 3.2 代数幾何を採用した意味

代数幾何的な設計は、条件が定める対象を写像で比較し、局所で調べ、重なりを照合し、
全体へ組み立てるという構成を与える。AATは、圏論・層理論にまたがるこの数学を、
Atomから構成するアーキテクチャの共通構造として採用している。
[AAT数学本文](../aat/algebraic_geometric_theory/README.md)、
[Architecture Geometry・Site・Sheaf](../aat/algebraic_geometric_theory/part_2_architecture_geometry_sites_sheaves.md)

今回直接使われた計算には、公開情報への射影、有限候補の局所化、整合する局所案の列挙、
大域候補への前像、操作や対応の保存がある。
SaleorとSQLAlchemyでは、それらを同じ開発の設計と実装へ接続した。
この成果を、**代数幾何的な共通構造が、異なる開発上の問いをつないだ成果**と評価する。

統一する中身が重要である。あるLawの判定に十分な情報、ある操作の保存、
ある局所案を実現する全体案は、それぞれの対応と条件を持つ。
この対応を保つことによって、一つの問題で得た構造が、次の問題を考えるための構造になる。

### 3.3 Rising Seaとn1016から得る設計上の示唆

Rising Seaは、共通の対象の上で、貼り合わせ、診断、輸送、変更の分類、再構成を接続する。
ArchSig本体を伸ばす際には、その接続を計算の設計へ具体化する。
以下は、論文の結果と[n1016の研究構想][rs-v2]から読み取る製品設計上の考察である。

| 参照点 | 数学で扱う構造 | 本体の改善へ取り込む考え方 |
| --- | --- | --- |
| [第7章§§7.3・7.6][rs-comparison] | 観測に現れない変更と、比較を保つ変更を対応させる。生成比較の適合する持ち上げ全体を、核の作用によるtorsorとして記述する。 | 判定に必要な区別と、適合する候補の自由度を同じ対応から読む。各候補、候補間の関係、元の操作への復元を保持する。 |
| [第8章§§8.3–8.7][rs-reconstruction] | 必要な原始データと整合条件から、対象と構造保存射を組み立てる。lensの基準fiberやプロトコルの生成表から、操作の法則によって射を延長する。 | 担当別の記述から全体モデルを作り、担当別の新旧対応から全体の変更を作る。生成元で調べた保存条件を、合成された変更へ引き継ぐ。 |
| [第4章][rs-transport]・[第5章][rs-base-change] | 輸送の合成と、範囲の選択・基底変換を含む経路の間に、条件を伴う比較写像を構成する。 | 直接の移行と段階的な移行、全体を変更してから局所化する手順と局所案から変更する手順を、実際の写像で比較する。 |
| [n1016 §2.7][rs-v2] | 有限体上の線形な適用族で、局所方程式から共有部分の許容関係と内部の復元情報を生成し、変更範囲ごとの修復を構成する構想。 | 一度作った部品表現から、変更範囲を変えたときの可否、全候補、必要な範囲の拡張を求め、選んだ案を内部の具体的な変更へ戻す。 |
| [n1016 §§5.1・5.4][rs-v2] | 既知情報と変更範囲を固定し、存在判定、具体的な補正の出力、変更そのものの識別に必要な読取りを分ける構想。 | 利用者が求める答えに応じて追加観測を選ぶ。受け取った値を同じ修復問題へ戻し、候補の構成と次の判断に使う。 |

特に第8章の再構成は、必要なデータと保存条件から**モデルと変更の両方を作る**。
第2章の、固定した幾何の上で局所状態を貼り合わせる問題と区別して、製品の操作へ対応させる。
状態の統合、モデルの組立て、変更の組立てで、入力と返す型をそれぞれ定める。

n1016が具体化する方向は、**何を保ったまま、どこを変えれば修復でき、そのために何を読むかを、
一つの構造から求めること**である。今回のSaleorで行った変更範囲の比較、8つの代替案の保持、
共有情報の追加が、この製品設計を考える実例になる。
伸ばす対象を、選択肢全体、その間の対応、局所からの構成と復元まで含む計算に置く。

開発では、まず「なぜ局所の整合が全体へ延びないのか」「どの操作が変更の自由度を制約するのか」を問う。
その理由を共通構造の性質として捉え、そこから必要な入力、判定、候補の構成を定める。
Whyを追うことを、Howである計算方法と利用手順を設計する出発点に置く。

### 3.4 他の手法と、どこで組み合わせるか

| 手法 | この検証から考える使い所 |
| --- | --- |
| ArchSig | 複数要求の下での候補比較、必要情報の共有、変更範囲の選択、局所案の統合、変更間の対応を扱う。 |
| TLA+ | Saleorで扱った送信権、応答喪失、回復、注文処理の前後関係などを状態遷移として検査する。 |
| 言語・フレームワークに即した解析 | 型、参照、呼出し、データフロー等を調べ、ソース観測と実装判断を支える。 |
| 単体・統合・回帰テスト、実行時の計測 | 実装した処理の動作、DBや外部サービスとの接続、例外処理、競合、性能を確かめる。 |

各手法が扱う問いには重なりがあり、同じ開発の異なる工程で組み合わせられる。
SaleorのTLA+側でも、状態遷移の検査結果が一括claimや取消範囲の設計へ反映された。
3群とも独立受入から補修へ進んでおり、設計を調べる計算と、実装を確かめる検査が働いた。
[比較実験の再評価][saleor]

## 4. 反省点と、そこから得た改善方針

### 4.1 計算を、判断する時点へ置く

TypeScriptの初期例では、増分再検査と診断cache更新という元の問いが、読解済みの5分岐と作用値の
検査へ縮小した。元の判断、作った入力、返された結果の対応を追う必要があった。
[判断への接続の監査][decision-audit]

一方、Rollupでは担当へ渡した指示が「使うならSKILLを読む」となり、SKILL未読のまま
不使用を判断した。追読で製品が扱える構造についての理解を訂正し、新しい担当でも再確認した。
[指示不足の記録][rollup-setup]、[理解の訂正][rollup]、[新担当による再確認][rollup-rerun]

改善方針は、同梱SKILLを入口とし、計算の前に「いま選ぶ候補・保つ条件・必要な情報」を短く残すことだ。
計算後には、採用、棄却、変更範囲、分担、追加確認のどれへ結果を使ったかを対応づける。
通常読解や試験で問いが閉じた場合も、その判断と成果を記録する。

### 4.2 業務上の要求と、特定の実装方式を分ける

PostgreSQLの振り返りでは、ArchSig側のemptyGuardと通常側のtruncate案の差が、
要求を特定の実装方式へ狭める問題として記録された。[既存成果の振り返り][refocus]
Lawには、利用者が求める結果と保存条件を置く。候補の採否を決める際は、別の方式でも同じ要求を
満たす案を比較対象に含める。複数の解は、その後の実装・運用上の判断に使う選択肢として保持する。

### 4.3 観測の意味と、変更後の使用箇所を確認する

OpenFGAでは、検査をdelete後へ移したという観測と、検査位置を維持して拒否条件から対象を除外した
実装が食い違っていた。独立確認で発見し、検査位置、削除対象の追跡、拒否からの除外を別の事実として
記述し直した。訂正後の入力とLawで10判定を再現した。[観測訂正][openfga]

Blinkerでは誤観測が次段へ引き継がれ、Saleorでは通貨やpendingの意味、writer、pluginの接続に
訂正や補修が必要となった。これらから、再利用の単位を「前回の入力」に加えて
「その入力を支えるソースと使用文脈」として扱う。
変更された操作と呼出し元・後続処理を確認し、保持、追加、置換、撤回した観測を明示する。

### 4.4 計算結果を、実装の受入までつなぐ

Saleorでは、初回受入後にも活動時刻、subscription失敗によるバッチ停止、plugin配送、
例外後の二重作用、不正応答による状態・参照の破壊が見つかった。
独立受入が実際の欠陥を検出し、各群が必要な補修を行った。[品質補修の記録][saleor]

改善方針は、モデルで区別した状態・操作を、実装の入口、更新箇所、外部作用、失敗経路へ対応づけることだ。
通常テストと独立確認でこの対応を調べ、反例から観測、Law、候補、実装のどこを直すかを決める。
単回送信、不明結果の保持、回復権限、競合管理など、要求に必要な構造を保持しながら補修する。

### 4.5 主案件へ戻り、手順と実装を簡潔にする

初期の運用では、新しい題材、性能修正、教材の追加が進む間に、主案件の出口や復帰先が保留になった。
性能改善や製品修理の成果は、止まっていた入力と判断へ戻して使う。
一つの仕事を設計・実装・再観測まで通すことを、次の割当の基準にする。[運用の振り返り][refocus]

Saleorの追加監査では、各群に次の重複が見つかった。

| 群 | ソース上で確認された重複 |
| --- | --- |
| ArchSig | decoratorと呼出し元での応答処理の再実行、配送先ごとの不変な配送設定集合の再作成。 |
| 通常 | 取引別taskから、同じcheckout全体の取引を再読込・lockする処理。 |
| TLA+ | 同様の全取引再読込に加え、取得済みrosterの再取得、履歴参照のN+1 query。 |

同じ金額foldの連続実行は、3群とも原版から引き継いでいた。
また、入力・CLI引数・試験設定の訂正や、モデルの判定条件を直して探索し直す手戻りも記録された。
独立受入で欠陥を検出する工程と、実装・入力・試験設定の誤りによる手戻りを分けて扱う。
重複の削減は、同じ外部挙動と安全性を保つ修正を実装・検査した後に、その費用を測る。

## 5. 次に行うこと：共通構造を活用するArchSig本体の強化

今回の結果を受けて、次段の主対象をArchSig本体の改善に置く。
必要情報、変更範囲、局所案と全体案、後続変更を同じ構造で扱う方向に、製品として伸ばす価値が見えた。
この強みを中心に、核による構成と復元、候補全体の表現、型付き結果の受渡しを一体として強化する。

目標は、**一度構成した対象・操作・対応を、候補の比較と選択、局所からの統合、移行、
実装後の再観測まで使い続けられる製品へ育てること**である。
既存のSaleor・SQLAlchemy等の成果は、必要な計算とその接続を具体化し、改善を確認する題材として使う。

### 5.1 既存の共通構造を、開発で使い続けられる形へ伸ばす

現行の[実行仕様](../tool/archsig_v0_6_0_io/execution.md)には、同じrun内の型付き結果参照、
候補域と解集合、局所系、写像と合成がある。
[計算仕様§§4–6](../tool/archsig_v0_6_0_io/computations.md)には、全解の有限表示、
許された変更からの局所状態、局所変更の持ち上げ、係数の構成もある。
これらを起点に、候補の選択、部品ごとの構成と復元、新旧の対応づけを、
問いをまたいで使える製品の操作へつなぐ。
以下は、そのための改善方向である。

| 強化する箇所 | 実験から得た理由 | 本体で実現したい使い方 |
| --- | --- | --- |
| 複数解の比較・選択と後続計算 | Saleorでは8つの代替案が残った。設計判断には各案の違いと、その後の実装への接続が必要だった。 | 解集合、候補間の対応、候補の由来を保持し、選択した割当てから候補対象を構成する。その対象を元のLawへ再代入し、局所化、操作の比較、次の変更へ渡す。 |
| 局所案と局所的な変更からの構成 | SQLAlchemyとSaleorで、局所案、重なり、大域候補の前像を使った。実際の分担では担当別の記述を全体へ組み立てる工程も必要だった。 | 局所状態の統合に加え、担当別の型・操作・Lawの記述から全体モデルを、担当別の新旧対応から全体の写像を構成する。組立てと再制限、操作・Lawの保存を核が検査する。 |
| 変更範囲と修復候補の接続 | Saleorでは変更を許す範囲を広げることで解が得られた。 | 同じ部品表現と固定条件から複数の変更範囲を比較し、全解、解を妨げる条件、包含極小の修復可能範囲を求める。選んだ共有値から内部の変更を復元する。 |
| 判断・構成に必要な情報の導出 | Saleorではstorageに加えてclock、coordination、recovery等を共有した。観測訂正は後続の判断にも影響した。 | 既知情報と求める出力を固定し、修復可否の判定、具体的な修復の構成それぞれに必要な読取りを原始位置へ結ぶ。同じ観測で判定が異なる候補対を、追加観測の理由に使う。 |
| 変更・移行・再観測の対応 | SQLAlchemyでは定義・Lawを継承し、Saleorでは新旧のMapを実装継続で使った。 | 設計候補と再観測した対象、旧版と新版の対応を保持し、操作とLawの保存を調べる。直接の変更と段階的な変更を合成・比較し、後続変更へ渡す。 |

複数解から人が選んだ候補の構成と、全解中の一意性に基づく自動修復は、別の操作として扱う。
前者は選択した割当てとその条件を、後者は一意性の判定を保持する。
選択後も、元の解集合と他の候補へ戻れる対応を残す。
候補の同効果関係や同型を扱う場合も、元の割当てと、その関係を与える写像を保持する。
局所案を同一視する際は、重なりでの再同定と、変更禁止箇所を保つ条件も統合へ引き継ぐ。

局所からの構成は、既存rootを局所化する現行の入口に、担当別の記述から全体を構成する入口を加える方向で
設計する。原始事実はArchMap、条件と許す操作はLawに置き、共有部分の対応を宣言する。
核がそこから対象・写像・保存条件を構成し、各担当の案と全体案の関係を計算する。

必要情報の導出では、Law評価、操作保存、局所案の統合など、何の判断を保つかを選び、
可否の判定から具体的な候補の構成へ進む際に必要な情報を求める。
得られた読取りと理由を同梱SKILLへ返し、エージェントが実ソースを観測する。
観測した事実の意味を確認する作業と、その入力から必要な区別を導く計算を接続する。

### 5.2 問いをまたいで構造を再利用する

再利用の中心に、**局所入力から核が生成する、共有部分の条件と内部の復元情報**を置く。
[n1016 §2.7][rs-v2]の構想では、局所方程式から常時変更できる内部変数を消去し、
共有部分と、変更許可を切り替える候補辺の座標に対する許容関係を作る。
内部の解の自由度と復元写像を部品側に保持する。変更範囲ごとの問いでは、共有値の一致と
変更禁止箇所の固定条件を加え、選んだ共有値から内部の修復を復元する。
同じ表現を、範囲の比較、局所案の統合、候補の具体化に使えることが設計上の要点である。

本体では、既存の有限候補と整数アフィンの計算から、この表現を生成する操作を具体化する。
有限候補では元の操作・割当てとの対応を保った関係として、アフィン系では扱う係数環に応じた
像・核・fiberと復元として設計する。n1016の有限体上の構成は、入力と適用条件を対応させる参照点となる。
全変更範囲の答えを利用者が用意する工程を置かず、宣言と原始事実から核が構成する。

この部品表現と、現在の同一run内の参照・保存入力の再検査を起点に、次を設計する。

- **対象と対応の引継ぎ。** 型、reading、候補域、操作名、成立条件、原始入力への参照を伴って、
  前段の成果を後続の構成へ渡す。別の表示や保存を経ても、何の対象に対する結果かを照合できるようにする。
- **変更に沿った再検査。** 再観測した事実と明示的な新旧対応から、引き継ぐ構造、作り直す構造、
  保存条件を再検査する箇所を導く。訂正された事実に依存する後続結果へ更新を伝える。
- **計算の共有。** 同じ局所構成、制限写像、候補域を複数の問いで使い、重複した構成と列挙を減らす。
  アフィン系で構造行列が同じまま定数項が変わる場合は、消去と復元の再利用条件を調べる。
  候補・操作・Lawの意味と結果を保ち、計算時間とメモリの変化は実測する。

これらの再利用は、現在の三入力から結論を導き直せることを核が確認する構成にする。
ソースの変更後は、再観測した事実と対応を使って新しい結果を構成する。
保存する表現、再検査の単位、公開する操作は、現行の
[結果形式](../tool/archsig_v0_6_0_io/results.md)と
[再利用の仕様](../tool/archsig_v0_6_0_io/execution.md#7-版正規化再利用)からの差分として具体化する。

### 5.3 最初の実装単位と、その後の拡張

最初の実装単位は、**固定部分を保つ局所修復を、一度生成した部品表現から変更範囲を変えて比較し、
選んだ全体案と対応を次の検査へ渡せる一周**とする。
Saleorの代替案とSQLAlchemyの局所・大域の対応を具体例に、まず有限候補域で、
必要な入力、生成する型付き結果、後続の問いが消費する値を定める。

1. 現行の候補域、解集合、局所系、写像を使い、固定部分・許す操作・共有する値を明示した一つの変更問題を記述する。
2. 核が局所の許容関係と、元の操作・割当てへ戻す対応を構成する。各部品の代替案を保持する。
3. 同じ部品表現を、複数の変更範囲に対する統合判定と全候補の構成で使う。
   範囲を広げて解が得られる場合は、その範囲と、より狭い範囲で解を妨げた条件を対応させる。
4. 選択した割当てから全体対象を構成し、再制限、元Lawへの再代入、操作の保存を検査する。
   生成した対象と対応を、次の変更の計算へ渡す。

この一周から、判定と具体的な修復に必要な追加観測、アフィン表現での計算共有、
局所的な新旧対応からの全体写像の組立て、輸送と合成へ広げる。
同じ値の見かけの一致に加え、操作を実行してから移す場合と、移してから対応する操作を実行する場合の
一致を、写像の保存条件として扱う。

既存の機能は接続して使い、新しい構成が必要な箇所を本体へ加える。
同梱SKILLと説明は、その操作を自然な開発依頼から利用できるように整える。
計算構造と適用条件の検査は核が担い、エージェントは要求の解釈、候補の提案、観測、実装を担う。

### 5.4 改善の成果を何で確認するか

本体の改善は、同じ開発上の問いに対して次の変化を確認する。

- 前段の型付き結果を後段が実際に消費し、手書きの再符号化を省けたか。
- 同じ部品表現から得る各変更範囲の全候補が、元の有限候補域を直接計算した結果と対応するか。
- 局所案、選択した全体案、操作、元要求の対応を、製品の結果から辿れるか。
- 候補の違い、統合できない理由、必要な追加情報が、次の設計判断へ使えるか。
- 判定と具体的な修復の構成それぞれで、既知情報を使い、必要な追加観測を求められるか。
- 再観測や観測訂正が、依存する対象・対応・判定の再検査へつながるか。
- 同じ条件と品質を保ちながら、入力作成、構成の反復、計算、引継ぎに要する作業がどう変わったか。

実験で得た入力と反例を、改善前後の計算と実装後の確認に使う。
共通構造を介して実際につながる仕事を増やし、その接続を利用者が扱う手間を減らすことを、
ArchSig本体の次の開発目標とする。
