# ArchSig v0.6.0 観測 SKILL PRD

## 問い

既存の OSS を理解・変更したい利用者に、コードの使用文脈や暗黙の関係まで読み取った
アーキテクチャの観測を、どの程度信頼して次の設計・検証へ使える形で渡せるか。

LLM の意味読解を ArchSig の Atom 定義・Law・ArchMap へ接続する製品 SKILL を作り、
実在する OSS 上で誤観測・見逃し・不明を分けて精度を測る。必要な区別を残しながら
観測を再利用し、利用者が根拠を確かめて設計判断へ進めることを目標とする。
本作業の target statement と受け入れ条件はこの PRD に置く。

## 作るものと責務

配布する Codex 向け製品 SKILL を `tools/archsig_v0.6.0/skills/` に置く。
利用の入口は、対象リポジトリと理解したいこと・実現したい変更である。
SKILL の名前、分割、補助資料は、実際の利用と評価から必要なものを選ぶ。
研究リポジトリ全体を利用者の実行環境へ要求せず、対象版の入力作成に必要な参照を配布に含める。

| 仕事 | 得るもの |
| --- | --- |
| 要求と既存仕様を読み、必要な区別を設計する | 独立して再利用できる Atom 定義と Law。要求の根拠と、人間の判断が必要な選択 |
| 実装の使用文脈、仕様モデル、設計候補を読む | 既存形式の ArchMap。原始事実・候補対応と、その由来 |
| 問いを選び、必要情報を読み直す | 計算への受渡し、追加観測、変更後の再観測と根拠の更新 |

LLM は呼出し元・分岐・データの利用・状態更新・他の操作との関係を読み、名前や宣言だけでは
定まらない意味を観測する。検索、位置・版・digest の照合、形式検査、数え上げを補助に使う。
AST や機械的抽出器で生成した関係を、そのまま意味観測の代わりにする実装は対象にしない。

ソフトウェア仕様、アーキテクチャ規約、プロダクトのふるまいを、共通の Atom 定義と Law で
扱えるようにする。次の三つは Law の作成と評価に用いる由来の観点であり、DSL の新しい種別や
排他的な固定分類ではない。同じ Law に複数の根拠があれば、その対応を保つ。

| Law の由来 | 作成・検証する意味 |
| --- | --- |
| 仕様に基づく Law | 要求や API 仕様等が定める条件・不変量を、適用範囲とともに記述し、実装の観測と照合する |
| 規約に基づく Law | 明示された設計判断やアーキテクチャ規約が求める依存・責務・操作の関係を記述し、該当する実装を検証する |
| ふるまいに基づく Law | コード・仕様から読む操作、条件、状態変化、順序や対応の意味関係を記述し、保つべき関係と実装との対応を検証する |

要求の根拠と観測の由来を保ち、現在の反復パターンは観測や問いとして扱う。
ふるまいから読んだ関係を変更後も保つ要求に採用する際も、明示された要求との対応を示すか、
人間の判断を求める。Atom 定義の意味と Law の要求を説明し、両者と実装の観測を独立に照合する。

[AAT の意味観測](../aat/algebraic_geometric_theory/part_1_atoms_objects_laws.md)と
[Rising Sea 第1章 §§1.8–1.10](../../outreach/paper/rising-sea/ja/04-relative-architecture.md)に従い、
ここでのふるまいは、操作の作用と使用文脈を持つ意味関係として読む。
[製品コンセプト §3](../tool/archsig_v0_6_0_concept.md#3-実コードとの接続archmapとlawpolicyによる抽象化)の範囲で、
コードに記述された I/O 操作の役割や依存も扱い、実行時の発生事実・性能・稼働監視は別の検証に分ける。

由来、未観測、不在、候補と実装の区別は入力仕様に従う。
実装観測は使用箇所へ結びつけ、仕様・要求・仮説もその役割で受け取る。
観測精度のために対象を依存グラフだけへ縮めず、テストコードや実行時の出来事を
実装構造の観測へ混ぜない。未知の情報は不足として保持し、確認できた部分を使える形で渡す。

## Atlas を使う機械的接続

[Rising Sea 第3章](../../outreach/paper/rising-sea/ja/06-resolution-invariance.md)の
§§3.1–3.2、3.5–3.6 と、次の Lean 宣言を対応させる。
ここで得るのは、指定した族と評価について情報を保存する条件である。

| 根拠 | この作業で使う内容 |
| --- | --- |
| [Reading.lean](../../research/lean/ResearchLean/AG/CanonicalResolution/Reading.lean) の `FiniteLawFamily.Adequate`、`adequate_iff_kernel` | 観測 `q` が同じになる二対象で、選択した全 Law 評価が一致することと、その評価が `q` を通じて降下することの同値 |
| [JointKernel.lean](../../research/lean/ResearchLean/AG/CanonicalResolution/JointKernel.lean) の `jointKernel_universal` | 全 Law 値の一致による商が、それらを保つ最も粗い reading となること |
| [Effective.lean](../../research/lean/ResearchLean/AG/CanonicalResolution/Effective.lean) の `computedClass_eq_iff`、`computed_adequate`、`computed_kernelEquivalent_jointKernel` | 有限で列挙可能な source、有限 Law 族、評価値の決定可能な等号の下で、実際の partition と標準商の一致を検査できること |
| [LawValueBlockComparisonBijectivity.lean](../../research/lean/ResearchLean/AG/ResolutionInvariance/LawValueBlockComparisonBijectivity.lean) の `generatedComparisonH1Map_bijective` | 両 reading の Law 十分性と、実際の nerve 比較に対する条件 C の下で、生成した H¹ 比較が全単射となること |

利用する場合は、同じ問いで比較する source または候補モデルの族 `S`、観測 `q`、Law 評価族
`v` を明示する。ファイル一覧を、そのまま数学上の `S` と見なさない。
LLM が得た意味上の区別をまとめる際は、指定した有限族で
`q(s) = q(t)` なのにいずれかの `v(s)` と `v(t)` が異なる対を調べる。
反例対があれば追加読解へ戻し、なければその族・Law についての圧縮や再利用へ接続する。
Law の追加や reading の変更時には、その十分性を見直す。

この検査には族全体の列挙・評価・等号判定を確保する。コードの意味と評価の対応は、
粗い観測 `q` からの再構成とは独立にソースで照合する。こうして得る指定族上の十分性と、
後述の経験的な観測精度を別々に示し、それぞれの対象範囲を保持する。

Law 評価の十分性から診断保存へ進むときは、被覆・係数・複体と実際の比較を別に確認する。
第3章の条件 C0–C6 は十分条件として用い、すべての利用に一律必須とはしない。
同章の実 H¹ 比較や、§3.6 の固定比較に対する核・余核の検査も、必要な主張に応じて選ぶ。
計算への受渡しは既存 I/O 仕様に従い、検査する保存条件は再利用する情報に合わせる。

## 実 OSS による観測精度の評価

### 対象の選定

次は実在するリポジトリと実装を確認した候補であり、固定した必須対象ではない。

| 候補 | 観測する意味の例 |
| --- | --- |
| [Train Ticket](https://github.com/FudanSELab/train-ticket) | [注文処理](https://github.com/FudanSELab/train-ticket/blob/master/ts-order-service/src/main/java/order/service/OrderServiceImpl.java)での状態・応答値の使用とサービス間の対応 |
| [eShop](https://github.com/dotnet/eShop) | [Order](https://github.com/dotnet/eShop/blob/main/src/Ordering.Domain/AggregatesModel/OrderAggregate/Order.cs)での状態遷移、操作の適用条件、イベント生成とデータの関係 |
| [Spring Petclinic](https://github.com/spring-projects/spring-petclinic) | [OwnerController](https://github.com/spring-projects/spring-petclinic/blob/main/src/main/java/org/springframework/samples/petclinic/owner/OwnerController.java)での入力・検索・更新の文脈と分岐ごとの意味 |

利用者の問いに関連する業務上の範囲と、参照判定に必要な周辺コードを選ぶ。
規模、言語・構成、意味の曖昧さ、読解費用を考慮し、対象の revision を固定する。
調整に使う部分と最終評価に使う部分を分け、最終評価には未使用の別 OSS または独立した
業務範囲を含める。同じ処理の複製や強く結びついた呼出し先を分割境界の両側へ置かない。
既存評価で読解済みの Train Ticket の断片は、その事実を考慮して割り当てる。

### 意味単位と独立した参照判定

評価は、選んだ reading の下でソースから確かめられる意味上の主張を単位とする。
たとえば、同名の送信操作の役割、状態値が選ぶ分岐、更新が保持する別の値、
複数箇所を読んで分かる同じ業務対象への対応を扱う。
適用条件や使用箇所が異なる主張は区別し、識別子や JSON の文字列一致で意味の一致を代用しない。
Law 作成は要求根拠と DSL の意味・適用域の対応を別に点検し、事実の観測精度と混ぜない。
実 OSS の評価事例には仕様・規約・ふるまいの三つの由来それぞれを含め、根拠資料と実装の
使用箇所から、共通の Law への記述が意味を保つか、観測と要求を区別できるかを確認する。
結果は由来ごとに示し、根拠不足や解釈が決まらない事例も保持する。

参照判定は候補出力を見ずに対象コードと要求の根拠資料を読む独立の読解から作る。
最終的な採否にはソース箇所と理由を持ち、判断の分かれる例は人間が確認する。
LLM の候補の和集合だけを参照集合にせず、候補が一つも触れなかった箇所も選択範囲から読む。
新たに正しい候補が見つかった場合はソースで確認し、参照の修正と当初の評価を区別する。

表現の分割・統合・別名を意味に沿って対応づけ、同じ事実の重複で回収数を増やさない。
対応づけや参照自体を決められない場合は未判定として残す。
外部の実行事実が必要で実装から決められない主張を、正しい観測の参照にしない。

### 測定と達成の判断

| 測るもの | 判断する内容 |
| --- | --- |
| 観測の precision | 判定できた出力中、ソースが支持する意味単位の割合。反する主張と根拠のない断定を誤観測として数える |
| 参照に対する recall | 独立した参照で確定した意味単位のうち、正しく回収した割合。棄権だけで未回収を消さない |
| 不明と判定の範囲 | SKILL の棄権、出力の未判定、参照の未判定、読めなかった範囲を区別し、各母数と件数を併記する |
| 再利用の妥当性 | Atlas を用いた明示的な族上の十分性、反例対、または条件未確認の理由 |

精度は不明の内訳・回答率と合わせて判断し、母数が零なら率は未定義と示す。
誤観測・見逃しの代表例をソースへ戻して説明し、
複数回の試行では試行数・モデルと条件を添えてばらつきも示す。
改善効果を主張する場合は、比較対象にも同じ範囲・予算・参照を適用する。

予備評価で読解費用と誤りの傾向を把握し、利用目的に応じた許容誤観測、見逃し、回答率の
採用水準を最終評価前に人間と合意する。これは一度の判断点とし、日々の読解・実装・補助処理は
合意した目的と範囲で自律的に進める。採用水準は予備評価を根拠に定め、最終評価では
合意した対象・母数・水準を使う。精度の実測範囲は OSS・問い・モデル条件とともに示す。

## CLI の完成から独立した検証

入力作成とソースへの忠実性は、CLI を完成させずに評価する。
既存の Counter・Reservations・Engine 等は、入力区分、欠測、候補対応、結果読解の適合確認に使う。
実 OSS の意味観測精度は、それらの仕様モデルの成功と別に測る。

前節の Atlas の検査は、明示した有限表を使う補助計算として行える。
共通の入力・問い・出力の接続は対象版の利用可能な `check/run` 等で確認し、未提供部分は
接続未検証として区別する。期待出力の例や模擬結果を、CLI の実計算の証拠にはしない。
`needed` を利用できる場合は不足 slot とその他の理由を読み分け、再観測へ戻ることを確認する。

補助スクリプトや評価用データは必要な範囲だけ作り、評価の証拠は実装の固定版と対応づける。
Rust の製品テストから SKILL 本文を検査したり、文書から期待値を抽出したりする依存は作らない。

## Acceptance Criteria

| 条件 | 確認する成果 |
| --- | --- |
| AC1 利用できる観測入口 | 配布用ディレクトリの Codex SKILL が、問いと対象リポジトリから意味読解、三入力の作成・再利用、追加観測までを導く。必要な参照が利用環境で読める |
| AC2 根拠付きの意味観測と Law 作成 | 実 OSS の使用文脈を読んだ出力が既存 I/O に適合する。仕様・規約・ふるまいそれぞれに基づく Law を共通の DSL で記述し、根拠への忠実性と実装との対応を検証する。要求・観測・仮説の由来、欠測、source revision と位置を確認でき、観測事実を要求や計算結果へ取り違えない |
| AC3 定量的な精度の達成 | 調整用と分離した実 OSS の評価で、独立参照に対する precision・recall、不明の内訳と母数、代表的な誤りを示し、事前合意した採用水準を満たす。形式検査や構文一致だけを精度としない |
| AC4 Atlas に基づく接続 | 明示した族・Law 評価について、十分な圧縮・再利用と、情報を落としすぎた反例対の両方を検証する。独立した source 照合と条件付き保証を区別し、診断保存を主張する部分では対応する比較条件を確認する |
| AC5 更新と計算への受渡し | 要求・Law・コードの変更で再読解が必要な箇所を判断し、古い観測を現状に読み替えず更新できる。CLI 接続の実測と未検証を区別して示す |
| AC6 全体構成との整合 | Rising Sea の貼り合わせ、診断比較、輸送・経路比較、変更の分類、再構成に必要な原始情報を保持する設計を確認する。現在の入力で表せるものと、核・仕様への追加が必要なものを具体的に示す |

AC6 は v0.6.0 全体の計算核をこの作業で完成させる要求ではない。
この作業ではその入口を、後段の構成で必要な意味と対応を消さずに作る。
観測 SKILL の受け入れと、未提供の CLI 計算の受け入れは分けて判断する。

## 実装のまとまり

1. **利用場面と評価の準備。** 実 OSS の候補と問いを選び、意味単位・独立参照・分離方法を
   小さな予備評価で確かめる。最終評価前に用途に合う採用水準を決める。
2. **意味観測と Law 作成。** 利用者向け入口、文脈を読む手順、三入力への接続を作る。
   使用文脈と要求根拠を読める製品 SKILL とし、仕様モデルだけで完了しない。
3. **再利用と再観測。** Atlas に対応する有限計算を必要な補助として接続し、圧縮・追加 Law・
   コード変更に対して情報の保持と再読解を確かめる。CLI の提供状況に応じて受渡しを実測する。
4. **分離した評価と改善。** 未使用範囲で精度を測り、意味の誤りを修正する。
   評価条件を変えた場合は別の評価として扱い、採用水準に対する結果を示す。

ファイル数、読解回数、常時の複数エージェント構成、全コードの事前列挙は固定しない。
入力・参照・評価に必要な証拠を残し、作業の進捗はリポジトリ文書へ書き込まない。

## 対象外と停止条件

Rust CLI・数学本文・Lean・既存のガイドライン・Claude 側の変更、ArchView/FieldSig の改修、
配布の公開、CI への新規 task 追加は、この観測 SKILL の実装範囲に含めない。

要求の意味や参照判定が解決できず、依存する実装・評価を進められない場合は、
該当する問いを人間へ返す。ソース取得不能や CLI 未提供は、その影響する部分を示し、
独立してできる意味読解の評価を続ける。
現行入力では必要な意味を表せない場合は、その原始情報と不足を具体化して仕様側へ返し、
観測や要求を計算都合へ合わせて弱めない。

## この作業の失敗判定

AC1–AC6 に対応する成果・検証の根拠が不足する場合、または実 OSS の精度が
合意した採用水準に届かない場合は未達とし、不足する成果や誤りを具体的に示す。
