# ArchSig v0.6.0 PRD: 名前の解決

## 問い

**名前の解決を一つの問い合わせにまとめると、型の受け継ぎを足しても、第2章の一周と既存のテストを保ったまま、受け継ぎの反例テストが経路ごとの直しなしで通るか。**

従う問いは三つある。

1. Atom に書かれた名前は、どの経路(式の道、書き込みの場所、名指し、選択、書いた場所より先、本体の比べ、局所)から問い合わせても、同じ答えになるか。
2. 反例を直すとき、直しは問い合わせの規則の中に収まり、経路ごとの特例を生まないか。
3. 名前の解決が沈黙するとき、読めば決まる所を返すか。

受け入れ要件とスコープ外は、この問いで採否を決める。

## 参照

- 振る舞い: [ArchSig v0.6.0 マニュアル](../tool/archsig_manual/README.md)(第3章、第4章、第5章 問い3・問い7、第6章)
- 内部の作り: [ArchSig v0.6.0 設計](../tool/archsig_v0_6_0_design.md)(§3.3 名前の解決、§3.5、§3.6、§5.4、§6)
- 作り方の規律: [Tool guideline](../tool/guideline.md)
- 進め方: `.claude/skills/prd-loop`、`.claude/skills/pr-review`
- 反例の材料: ブランチ `claude/archsig-v06-ac11-inherited`(head `80d27ce1a`。merge-base は main より古いので、取り込むときに今の main に合わせる)の `tests/plan_check.rs` と `tests/plan_split.rs` に足した52本のテスト。PR #5226 の監査コメント1〜20回目。

## 現状

- `tools/archsig-v06/` は、名前が指す要素と種類を、経路ごとに別の関数で決めている(`structure.rs` の `kind`、`undefined`、`expect`、`fields`、`trace`、`named_path`、`redefines_unread`、`engine.rs` の `fields_of`、`Below::known`、`geometry.rs` の `holder`、`owner`)。同じ名前でも、経路によって答えが違い得る。
- `inherits` を読まない。親の型から受け継いだフィールドを、子の型の値を丸ごと書く操作の下の場所に数えず、誤った `holds` を出す(Issue #5225)。
- 第2章の一周の e2e(`tests/chapter2.rs`)と、ほかのテストが通る。

## 受け入れ要件

各要件は、`tools/archsig-v06/` の `cargo test` で確かめる。

**AC1 名前の解決の実装単位**
設計 §3.3 の四つの問い合わせ(要素、段、道、フィールド一覧)と列の読み方を、一つのモジュールに置く。

- 式の道と書き込みの場所(§3.5)、名指しと消える要素の判定(§3.6)、選択(§4.4、§5.2)、書いた場所より先と本体の比べ(§5.4)、局所(§6)は、このモジュールの答えだけを使う。「現状」に挙げた関数は、問い合わせの呼び出しに置き換わる。
- 機械的に確かめる。このモジュールの外で、構造の `elements`・`resolves`・`observed`・受け継ぎ・定義し直した読んでいない要素を直接引く箇所と、名前の文字列を `.`・`->`・`.$`・`:`・`?` で読む箇所がない(`grep` で確かめ、PR 本文に結果を書く)。除くのは、式の字句(`expr`)、Atom の `at` と `file` のパスの読み、ArchMap の読み書き(`archmap`)、構造を作る所(`Structure::new` が `defines`・`params`・`sends`・`receives`・`calls` から要素を作る処理)である。

**AC2 受け継ぎ**
`inherits` をマニュアル第3章のとおり読み、段(§3.3)が受け継ぎを解く。次が通る。

- 子の型の値を丸ごと書く操作で、受け継いだフィールドの場所 `[m.O.s, m.P.t]` の違いが反例になる。親と子は別のソースに置く。
- `$c.t` と `writes m.C.t` が、同じ場所 `[m.P.t]` になる。
- 親の型の定義を読んでいなければ、親のソースを読む所として沈黙する。定義し直し、二つの親の定義、曖昧な親と子は `unresolved` で沈黙する。
- ひし形の受け継ぎは、一つの場所である。
- `plan split` で、受け継いだフィールドへの書き込みが、それを定義した型の局所と、頭の型の局所に属する。

**AC3 既存の実証を保つ**
`tests/chapter2.rs` の2本は、変えずに通る。ほかの既存のテストも、消さずに通る。期待を変えるテストは、設計で振る舞いを変えた次の所に限り、PR 本文に一つずつ、設計の節を添えて書く。

- 書き込みの場所を列の読み方で解く(§3.5)。
- 定義し直した読んでいない型の扱い。直下のフィールドも沈黙すること、変更前に外部だった型の定義し直しを候補の定義のすべてとすること(`conditions` に外部の型が並ばない)(§3.6、§5.4)。
- 本体の比べを、解いた場所で比べる(§5.4)。
- 受け継いだフィールドの局所と、Atom の局所に道の頭の型を数えること(§6)。
- 沈黙の読む所。道の `?` の型は `defines` の場所、構造にない呼び出しと `params` にない引数の読む所(§3.3)。

マニュアル第3章の形に反する fixture(`object` に式を書くなど)は、形に合わせて直してよい。直した fixture は PR 本文に書く。

**AC4 反例テスト**
「参照」のブランチの52本を取り込み、通す。期待を設計に合わせて変えるものは、PR 本文に、設計のどの文によるかを一つずつ書く。52本を減らさない。
反例が出るたびに、直しは §3.3 の問い合わせの中に収める。特定の経路でだけ使う例外(関数、条件)を足す直しは、「失敗の判定」へ進む。

**AC5 書き戻し**
実装で決めた外から見える振る舞いを、マニュアルに書く。次の文を、設計 §3.3・§3.6・§5.4・§6 に合わせる。

- 第3章「読んだ範囲」の、定義を読んでいない要素の読む所の箇条(`resolves` がない要素、外部の型のフィールド)。
- 第4章「局所と重なり」の、`<頭>.<名前>` の局所の文と、「Atom が名指す要素は、`subject`、`object`、`writes` の `via` のフィールドである」の文。
- 第5章 問い3 の「型のフィールドをたどるときは」の箇条(変更前に `resolves` が外部を指していた型の文を含む)、比べる場所の列挙、「使うかは、候補を重ねた後の構造でたどって決める」から「それが沈黙すればその読む所を返す」までの文(型の分からない道で型を決める要素を問い合わせる規則を含む)。
- 第5章 問い7 の、定義も `resolves` も持たない `<頭>.<名前>` の要素の文。
- 第6章の `unresolved` の理由の一覧と、「成り立つ条件」(受け継いだフィールドを定義した型の一つの場所と数えること)。

**AC6 沈黙の読む所**
名前の解決が返す `unread` の読む所は、読めば答えが決まるか別の読む所に進む所である。要素(名前)と段が `unread` を返す入力の種類ごとに(`resolves` の指すソース、型として名指された頭、`<T>.<f>` の名前、名前だけの要素の手前)、読む所の構造を読み足すと答えが決まるか読む所が変わることをテストで確かめる。同じ沈黙に戻る読む所があれば、設計の欠陥として止まる。

**AC7 穴の一覧の分け直し**
Issue #5104 の「直す」の未完了の項目と、Issue #5189 の項目を、設計に照らして分ける。名前の解決で決まる項目は、テストで確かめて印を付けるか、仕様の欠けとして理由を書いて残す。名前の解決の外の項目は、そのまま残す。結果を #5189 のコメントに書く。

## 実装の順

依存の順に Issue を切る。一つの Issue が一つの PR である。

1. 名前の解決のモジュールを作り、既存の経路を置き換える(AC1、AC3、AC6)。列の読み方、名前だけの要素、構造が持つ定義し直した読んでいない要素と `removes` の集合、局所の定義した所の順もこの周に入る。`inherits` は読むが、受け継がれる型のない段として動く。
2. 受け継ぎ(AC2、AC4)。この周で触るのは、名前の解決のモジュール、`inherits` を読む所、テストだけである。
3. 書き戻し(AC5)。
4. 穴の一覧の分け直し(AC7)。

## スコープ外

- #5104 の「直す」に残る次の項目を直すこと。`compare` の `fresh` の呼び出しの場所、意味の確かめの定義のない行き先と変更前の意味の読み残し、`removes` の沈黙を変更前の読み残しで数えること、局所ごとの意味 Atom、照合の `?`、`plan split` の決めていない対応。AC7 で分け直すだけである。
- #5189 の項目を直すこと。
- 問い1、2、4〜8 の新しい計算、製品として配る SKILL、性能の作り込み。AC2 の `plan split` の局所と、§4.4 の名前の解き方の文は含む。

## 失敗の判定

- 反例を通すのに、§3.3 の問い合わせの外に名前の規則(経路ごとの例外)が要る。設計の欠陥として止まる。
- 第2章の一周の期待を変えないと通らない。設計の欠陥として止まる。
- 実装の順の2で、名前の解決のモジュールと `inherits` を読む所とテスト以外を触る必要がある。止まって報告する。

## 停止条件

`.claude/skills/prd-loop` の停止条件と、`.claude/skills/pr-review` の中心の定義に従う。受け入れ要件にも責務範囲にも当たらない、周辺の入力での振る舞いの気づきは、#5189 に積み、AC7 で分け直す。
