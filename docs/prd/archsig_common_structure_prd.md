# ArchSig 共通構造の構成・再利用強化 PRD

## 1. 問いと目標

複数の要求を保つ変更について、なぜ局所案が全体へ延びないのか、どこまで変更を許せばよいのか、
具体的な変更を作るには何を読む必要があるのかを、同じ構造から求められるようにする。

目標は、**三入力から一度構成した対象・操作・対応を、変更範囲の比較、候補の選択と復元、
局所からの統合、再観測後の計算まで使い続けられる ArchSig 本体**である。
問いごとに同じ問題を作り直す費用を減らし、利用者が選んだ案を次の計算へ直接渡す。
Why を構造の性質として説明し、そのために必要な入力・計算・表示を実装する。

本作業の target statement と受け入れ条件はこの PRD に置く。
公開構文、型、保存形式、実行時の失敗通知は既存の I/O 仕様で定める。
実装に伴う仕様追加は該当する実装より先に行い、この PRD には要求と確認方法を置く。

## 2. 現状診断と参照先

### 2.1 現在使える構造と、追加する接続

調査基準は n1018 を取り込んだ main `cbb103ec5` とする。
現在の実装は `tools/archsig_v0.6.0/` にある。

| 現行の機能 | この作業で完成させる接続 |
| --- | --- |
| 同一 run の型付き結果参照、CandidateSpace、SolutionSet、Assignment | 同じ候補域の複数解を比較し、明示的に選んだ Assignment から対象を構成して後続の問いへ渡す。 |
| 既存 root の局所化、局所状態、matching と大域候補の前像 | 局所で生成した条件と復元情報を共有し、変更範囲を変えて同じ問題を解く。担当別の記述から対象・写像を組み立てる。 |
| 有限候補の計算、整数アフィンの全解表示・持上げ | 全候補の意味と元の割当てを保持する部品表現を作り、範囲の比較・具体化・定数項の更新に使う。 |
| `needed` による未観測位置と未決理由の取得 | 既知情報と求める出力を固定し、可否の判定と具体的な変更の構成に必要な追加観測を分けて求める。 |
| `map`・`compose`・`compare`、保存入力の再検査 | 新旧の対象と操作の対応を保持し、再観測の影響と、直接・段階的な変更の対応を調べる。 |

`repair` は元 Assignment の一意性を要求し、SolutionSet の表示行や表示用特解を
利用者が選んだ解として構成する入口を持たない。`--reuse` は現在の三入力との照合を行う。
定義・Law を継承したこと、同じ run で値を共有したこと、保存結果を検査したこと、
変更後の計算を省けたことは、それぞれ別の成果として確認する。

## 3. 利用者が完了できる仕事

最初の一周は、同じ要求・候補域について、固定部分を保つ局所修復を構成し、
変更を許す範囲を比較し、選んだ全体案を後続の検査へ渡すことである。

1. 三入力で、保つ Law、許す操作、固定部分、局所で共有する情報を記述する。
2. 核が局所の許容関係と内部の復元情報を生成する。
3. 同じ表現から複数の変更範囲を調べ、解の有無、代替案、解を妨げる条件を比較する。
4. 利用者が選んだ元 Assignment から全体対象を構成し、元 Law、固定部分、操作の保存を確かめる。
5. 対象と対応を後続の局所化・比較・次の変更へ渡す。
6. 必要な原始情報を追加観測し、実装後の再観測と新旧対応から、更新が必要な構成を求める。

各回答から、問いを固定した条件、効いた Law・原始情報、候補または成立を妨げる条件、
選択した候補と後続対象の対応を辿れるようにする。理由を短く示し、詳しい根拠は型付き参照で
接続する。これを、共通構造が開発判断を支える製品上の成果として AC10 で確認する。

全変更範囲の回答表、係数、貼り合わせ済みの全体案を外部で作って入力する工程は置かない。
局所案と全体案の関係を計算する部分を、スクリプトや製品 SKILL に移さない。

## 4. 機能要求

### R1. 局所の条件と復元情報を一度構成する

ここでいう部品表現は、局所入力から核が生成する「共有部分の許容関係」と
「元の操作・割当てへ戻す情報」の組である。公開型や保存 schema の名称はここでは固定しない。

- 常時変更できる内部の変数、共有する値、変更許可を切り替える単位、固定部分を区別する。
  変更範囲を後から比較するために必要な座標は、内部消去で失わない。
- 局所の代替案と内部の自由度を保持する。共有値が同じ複数の元 Assignment を、一解へ潰さない。
- Law の依存を調べ、複数部品にまたがる条件を共有側の条件として残す。
  分解できない条件は結合したまま扱い、局所で見えないことを理由に削除しない。
- 同じ未観測位置は全体で同じ未知として扱う。部品ごとに独立した値へ分裂させない。
- 分解・結合・復元には、元の reading、候補域、操作、束縛、原始位置との対応を保持する。

初段は有限候補域を扱う。局所関係の結合と必要な候補の復元を使い、
全体の直積を先に展開してから部品へ分ける実装を完成形としない。
小さい直接列挙は、結果の対応を確かめる独立の比較方法として用いる。

### R2. 同じ表現から変更範囲と全候補を比較する

- 要求した範囲だけを評価し、全範囲のべき集合を前処理として列挙しない。
- 範囲外の更新先は基準対象の値へ固定する。parameter の零を無条件に「変更なし」と読まない。
- 範囲ごとの解の存在、元 Assignment へ戻せる全解表示、失敗した条件を得る。
  可否だけを求める経路では、全候補の対象や表示を具体化しない。
- 範囲を広げたときの候補の対応を保持する。追加を許した操作と、新たに得た候補を辿れるようにする。
- 利用者が範囲の探索を求めた場合は、宣言された有限の変更単位について、包含極小の修復可能範囲を
  求める。包含極小と最小件数を区別する。全極小範囲を求めた場合も、一つ発見した時点で完了としない。
- 未完了の探索は、全解、解なし、極小範囲の完全一覧へ昇格させない。

全解の意味を保つことと、全候補を一度にメモリ・標準出力へ展開することを分ける。
保存・後続参照を含めて正確に扱える表現を選び、展開は要求された候補に対して行う。

### R3. 選んだ候補を対象へ戻し、次の問いが消費する

利用者の明示的な候補選択を、一意性に基づく `repair` と別の操作として実装する。
選択は核が生成した元 Assignment を指す型付き参照として扱い、値や対応表の手書き再入力を要しない。
公開構文と選択を保存する方法は、実行・結果仕様への追加として定める。

- 元の解集合、候補域、選択した Assignment、構成した対象を対応づける。
  他の候補へ戻れることと、今回どの候補を採用したかを両立させる。
- 所属、型、更新式、固定部分、元 Law への再代入を確認し、対象を構成する。
  構造保存の写像は、その保存条件も成立した場合に生成する。
- 表の順序、node ID、表示用特解による暗黙の採用を行わない。
  同じ状態を生む異なる元 Assignment も、選択の意味として保持する。
- 構成した対象と確認済みの対応を、既存の `check`、`localize`、`map`、`compose`、
  `compare`、次の変更計算へ直接渡す。表示 JSON の抽出・書換えを接続手順にしない。

### R4. 判定と具体的な構成に必要な追加観測を求める

既知の原始情報、許す追加読取り、変更範囲、求める出力を固定して計算する。
有限の入力候補族では、同じ読取り結果になる候補を比較し、次を分ける。

| 求める出力 | 十分性として確認すること |
| --- | --- |
| 修復できるかの判定 | 同じ観測結果を持つ入力候補で、修復の可否が一致する。 |
| 具体的な修復の構成 | 同じ観測結果に対して、全候補で有効な同じ具体的割当てを返せる、または全候補が修復不能である。可否の一致だけでは代用しない。 |

足りない場合は、可否が異なる候補対、または共通に使える具体的修復が存在しない候補群を理由にし、
追加で読む原始位置へ結びつける。観測結果を受け取った後は同じ修復問題を更新する。
全候補群での共通修復の存在は、各二候補に共通修復があることだけでは判定しない。

初段は有限候補族で十分な読取り集合を求め、その中の不要な読取りを除く。
最少問い合わせ数の一般的な最適化や全読取り集合の列挙を既定動作にしない。
整数アフィンでは、既知情報を含む正確な像・核・fiber の計算が適用できる条件を仕様へ定めて接続する。
ソース上の値を読むことと、その値の意味を確かめることは製品 SKILL が担う。

### R5. 再観測と変更に沿って構成・検査を更新する

- 型、Law、基準対象、束縛、候補域、操作、由来の依存を保持し、原始事実の追加・訂正・撤回から
  作り直す構成と、保持できる不変部分を求める。変更した支持を持つ結果は再検査する。
- 型・Law・操作・局所構成が変わる場合は、値だけの変更と区別して依存を失効させる。
  部分更新の対象に含まれない不正入力も、現在入力の通常の静的検査で検出する。
- 同一実行内の不変な値の共有と、保存後に外から読む結果の検査を分ける。
  保存を経た候補は、現在の三入力からの導出と照合する。digest や保存済みの成功表示だけで採用しない。
- 設計候補と実装再観測、旧版と新版の対応を保持する。古い source の由来を新版へ貼り替えない。
- 新規評価と再利用経路で、確定した値・条件・元 Assignment の意味が一致する。
  再利用の効果は、不変な構成を実際に引き継いだ箇所で確認する。

### R6. 整数アフィンで消去と復元を共有する

有限候補で完成した一周を、現行の整数アフィンの決定範囲へ広げる。
常時変更できる内部部分を消去し、共有部分と変更許可を切り替える座標について、
整数の像・整除条件と、内部の特解・核・元 parameter への復元を保持する。

構造行列と適用条件が同じで定数項だけが変わる場合、消去・復元の線形部分を共有する。
固定する位置、追加の guard、係数型が変わる場合は、再利用できる部分を改めて判定する。
整数を有理数や有限体で代用せず、表示基底の変更後も元の割当てを復元する。
内部の自由度があるときは全解を有限表示で保持し、一つの特解だけへ縮めない。

### R7. 局所のモデルと変更を組み立てる

Rising Sea 第8章を参照し、次の二つを製品の操作へ接続する。

- 担当別の型・操作・Law の記述と共有部分の対応から、全体の対象と名前付き操作を構成する。
- 担当別の新旧対応から全体の写像を構成し、局所へ戻した対応と操作・Law の保存を確認する。

既存 root の局所状態を統合することと、局所の記述から全体モデルを作ることを区別する。
入力は既存の三入力の役割へ置き、共有部分の対応と整合条件から核が組み立てる。
型や操作の衝突を、名前の類似や後勝ちの上書きで解決しない。
重なりでの再同定を使う場合は、その型・合成の整合と、変更禁止箇所の保存を確認する。

最初に扱うのは有限の生成データと現行の構造保存検査で完結する族とし、
その適用条件を計算仕様へ追加する。直接の変更と段階的な変更、組立て後の制限と
局所の対応からの組立てを、実際の写像で比較できるようにする。
生成操作の保存から合成の保存を得る構成を使い、任意長の操作語を列挙する工程は作らない。

## 5. 計算・検査・出力の費用に対する要求

新しい経路に以下を適用する。単なる高速化の希望ではなく、AC8 の確認対象とする。

| 箇所 | 求める実装上の性質 | 確認方法 |
| --- | --- | --- |
| 部品の生成 | 同じ意味入力の部品を一度生成し、複数範囲・複数の後続問いが参照する。 | 同じ部品に対する生成回数が範囲の数に比例して増えないことを、局所的な計数で確認する。 |
| 不変な値と支持 | 候補ごとに入力索引、支持、全 graph、既存の局所関係を深く複製しない。 | 所有経路と該当する複製箇所を確認し、代表入力の保持量を測る。 |
| 検査成功の引継ぎ | 型・式・束縛・原始値・生成条件と所有者が同じ検査結果を、同一の検査範囲内で使う。生成元・registry・可変状態の変更時には必要な検査を戻す。 | 不変な反復で重複検査が増えない例と、変更を見逃さない例を対にする。既存の検査 session を起点にし、並行する検査器を作らない。 |
| 候補の具体化 | 選択・後続計算に必要な候補を復元する。可否だけの問いで、全候補の Architecture を生成しない。 | 可否のみ、候補一つの構成、全候補表示の要求を区別し、生成対象を確認する。 |
| 要約と保存 | 要約は型付き結果から直接生成する。保存は必要な公開値の参照を共有し、到達した値を描画する。 | 保存なしで全量 JSON 生成が起動しないこと、同じ大きな値を回答ごとに複製しないことを確認する。 |
| 配送 | 計算・再利用照合で生成した値を使い、保存時に同じ表示や JSON 全文文字列を作り直さない。 | 現行の配送経路へ接続し、新経路の再描画と全量文字列の保持がないことを確認する。 |
| 中断 | 現行の軽量な signal 確認を、新しい結合・復元・探索・再検査にも接続する。 | 中断時に新しい導出を止め、確認済み回答を保持する。hot loop に時計・RSS・filesystem 呼出しを加えない。 |

同じ意味の値を共有しても、異なる Law 出現、操作名、原始位置の由来を消さない。
検査成功の再利用条件を満たさない値は通常の検査へ戻す。性能のために、候補の所属や
選択後の元 Law への再代入など、異なる不変条件の検査を削除しない。

短い回答と明示保存の使い分けは実行仕様 §5 に従う。
全候補の保持、全候補の件数計算、全候補の表示を同じ仕事にせず、要約だけのために
未要求の全列挙や件数計算を始めない。すでに確定した件数と、未展開の全解表示を区別して説明する。
新しい内部表現のダンプ、処理履歴、計数値を通常の公開出力へ追加しない。

## 7. 必要な検証と、その配置

### 7.1 意味を確認する小さい例

| 例 | 独立に確認する結果 | 主な要件 |
| --- | --- | --- |
| 有限の範囲比較 | Bool の更新先 x,y,z,a,b,c、基準値はすべて false。a,b,c は常時変更可、x,y,z は範囲で解禁する。Law は x=true、x=y、y=z。範囲 {x} と {x,y} は解なし、{x,y,z} は64候補中8解。部品 {x,y,a}、{y,z,b}、{z,c} から同じ8つの割当てを復元する。 | AC1–AC2 |
| 同じ状態を作る別の割当て | 更新を v=p とし、Bool parameter q は更新に影響しない。v=true を満たす元割当ては p=true と q の二通り。明示選択は対象を作り、自動 repair は非一意を保持する。 | AC3 |
| 部品をまたぐ条件 | 最初の例へ a=b を加える。内部に隠した a,b を独立に扱って8解を返さず、条件を保持した4解と一致する。 | AC1–AC2 |
| 判定と構成の情報差 | 未観測 Bool v と、変更可能な Bool h に h=v を課す。存在判定は v を読まず成立するが、具体的 h には v の観測が必要。h を false に固定した場合は存在判定にも v が必要。観測済みなら追加読取りは不要。 | AC4 |
| 共通修復の有無 | 三つの入力候補の有効な修復集合を {a,b}、{b,c}、{a,c} とする。同じ観測の下で各対に共通解があっても、具体的な共通出力は存在しないと判定する。 | AC4 |
| 整数と定数項の更新 | 2h=b で b=1 は解なし、b=2 は h=1。構造行列を共有し、内部に自由変数を持つ例ではその核も復元する。行列・固定条件を変えた場合を同じ再利用条件へ混ぜない。 | AC6 |
| 再観測・組立て・中断 | 局所入力の一箇所の訂正、重なりの矛盾、操作保存の破れを別の小例で検出する。整合する対象・写像は組立て後の再制限と一致する。途中停止は未完了の全解を確定せず、先行する検査済み回答を残す。 | AC5・AC7・AC8 |

表は区別すべき意味を定める。全例をすべての層・保存条件・signal・係数型との直積で反復しない。
有限例の期待値は小さい直接列挙や明示した割当てから得て、検査対象の部品構成器を呼んで作らない。
数値の正しさに加え、元の型、割当て、固定部分、操作、由来を必要な箇所で assert する。

### 7.2 実行経路と費用の確認

- 数学的な組合せと復元は computation の unit / 内部 integration、型付きの受渡しは公開 API の
  integration、引数・短い回答・保存・signal・配送は実バイナリの代表例に置く。
- 同じ公開動作を支える保存なし・保存あり・再利用を、すべての Law のテストへ掛け合わせない。
  正常系・反証・欠測・変更による失効は、その区別を所有する層で残す。
- 構成回数や描画の有無は、小さい例で必要な箇所だけを計数する。テスト専用の観測または
  ローカル計測を使い、恒久の計測 subsystem、公開 metric、別の常設テスト suite を追加しない。
- 局所検証は変更した責務に対応する範囲で行い、全 suite は既存 CI の実行経路を使う。
  正式レビューと修正後確認は Workflow guideline が参照する共有手順に従う。

費用の比較は、有限の一周を完成した時点と、後段の共有経路を完成した時点で行う。
Saleor または SQLAlchemy の既存の問いから、変更範囲・候補・後続利用の関係を残す一例を選ぶ。
原入力を使う場合と小さい適合例へ移した場合を記録で区別し、新規の OSS 横断実験へ広げない。

比較前に入力・問い・候補域・変更許可・期待する値・binary・保存条件・外側の停止時間を固定する。
基準側は同じ仕事を既存の操作で独立に構成する経路、新経路は部品を共有する経路とし、
型付きの結果を同じ意味で照合する。新しい機能の費用と、既存の同じ問いの費用を混ぜない。
共通する問いを比較単位にし、候補の手書き列挙や別の可否条件への置換を基準側に使わない。
各経路の入力整備と実行の手順を残し、手作業の差と機械の計算費用を分ける。

最初は固定条件の一対を測る。結果が矛盾する場合、ノイズが判断を妨げる場合、または
測定対象の実装を変更した場合だけ、その原因に対応する測定を追加する。
計数・診断を付けた実行と通常実行の時間を混ぜず、時間、CPU、最大 RSS、保存byte数を別々に記録する。
全解の復元確認のために全候補の巨大な JSON を保存せず、小例の集合比較を使う。
実行条件と結果、必要な入力と固定 head への短い参照は実装 Issue / PR に置く。

### 7.3 論文につながる判断と証拠

Issue #6260 へ渡す成果は、共通構造を採用したという説明から、どの構造がどの判断を支え、
どの仕事を共有できたかまで辿れる一例である。§7.1–7.2 と同じ実装・検証を使い、
次の対応を実装 Issue / PR の短い索引にまとめる。

| 確かめる内容 | 残す証拠 |
| --- | --- |
| 同じ問題を解いていること | reading、候補域、固定部分と問いを特定し、小例の直接計算と部品表現からの復元が同じ元 Assignment・対象を与える参照。 |
| 構造が判断を支えたこと | 追加観測が必要な理由、範囲が不足する条件と拡張後の候補、明示選択、後続の検査、再観測後の更新への接続。核が確認した成立根拠と、利用者がその候補を採用した理由を分ける。 |
| 共通部分を実際に使い続けたこと | 複数の問いが共有した構成・支持・検査結果の箇所と、小さい例の生成・検査・描画回数。意味が同じことだけを再利用の証拠にしない。 |
| 費用がどう変わったか | §7.2の固定条件、各経路の意味の対応、時間・CPU・最大RSS・出力量の実測値。改善した項目と増加した項目を同じ比較で示す。 |

各索引は入力、実装 head、該当テストまたは実行結果への参照を持つ。
失敗と修正が生じた場合は、どの条件で何が起き、修正後に何が変わったかを同じ参照で辿れるようにする。
証拠の置き場を増やすための新 schema、全内部値の保存、論文専用の重複テストは追加しない。
この一例から述べる範囲は固定した入力と問いに合わせ、先行研究との差や他問題での効果は
Issue #6260 の論文検討へ渡す。

## 9. 変更範囲と停止条件

対象は `tools/archsig_v0.6.0/` の核・run・CLI・必要な tests と同梱 SKILL、
`docs/tool/archsig_v0_6_0_io/` と製品の使い方に必要な文書である。
既存の版や入力を変更する場合は、意味の変更と保存表現の変更を分けて仕様へ記載する。

数学本文・Lean の新定理、ArchView / FieldSig の改修、release・tag・配布公開、
CI の task 追加、新しい OSS 群の精度・工数比較は本作業の範囲に含めない。
一般の非線形整数可解性や任意長の操作語の探索も要求しない。
実験対象の全ソース観測や人間作業時間の削減を、核の完了条件へ追加しない。

三入力で必要な原始情報や候補の明示選択を表せない場合は、具体例と必要な意味を示し、
該当する仕様を決めてから依存する実装へ進む。結論や保存証拠を新しい入力欄へ逃がさない。
独立した小例と既存の型・計算で進められる部分は継続する。
測定が外側の停止条件へ達した場合は、到達箇所を調べて重複・保持・展開を直し、
上限の引上げだけで AC8 を満たしたことにしない。

## 10. この作業の失敗判定

次のいずれかが残る場合、この PRD は未達である。

- 部品表現を作っても、範囲比較・候補の構成・後続の問いが使わず、それぞれが同じ問題を作り直す。
- 全体直積や全範囲の回答表を先に作ることが、局所の一周を使う必須条件になっている。
- 候補、元 Assignment、固定部分、共有条件、操作、由来を捨てて、計算量や出力量を小さくする。
- 判定に十分な観測を具体的修復にも十分と扱う、または候補選択を自動修復の一意性へ読み替える。
- 同じ不変な構成の複製・再検査・再描画が後続利用のたびに増え、§5の共有が実体として成立しない。
- 短い回答を返すために全量出力を作る、保存に内部の処理履歴を追加する、要約を意味計算へ戻す。
- 判断の理由が説明文だけにあり、元入力・計算結果・選択・後続対象への対応を辿れない。
- テストを削って必要な意味の区別を失う、または同じ確認を複数層で反復することを品質の根拠にする。
- 成果を文書や SKILL の手順だけで説明し、AC1–AC10の計算・受渡し・検証が製品に実装されていない。
