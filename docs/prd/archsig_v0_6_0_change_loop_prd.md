# ArchSig v0.6.0 PRD: 変更の一周

## 問い

**エージェントは、型の分割のような変更について、ArchSig の結果だけを頼りに、実装する前に Law を保つかを確かめ、反例を直し、担当に分け、実装の後に候補どおりかを確かめられるか。**

この問いに答える場面は、マニュアル第2章「一つの変更を最初から最後まで」の一周である。従う問いは三つある。

1. 読んでいない所があるとき、ArchSig は結論を出さず、次に読む所を返せるか。
2. 変更が Law を破るとき、ArchSig は、誰でもたどって確かめられる反例を返せるか。
3. ここで作る構造、Law DSL、操作の実行のエンジンは、設計どおりに、言語を知らずに動くか。

受け入れ要件とスコープ外は、この問いで採否を決める。第2章の一周に要らないものは入れない。

## 受け入れ要件

各要件は、`tools/archsig-v06/` のテストで確かめる。テストはコマンドを実行して結果を確かめる。

**AC1 ArchMap**
`archsig record` と `archsig status` が、マニュアル第3章と設計 §3.1 のとおりに動く。

- ソースと観測の範囲ごとに Atom を置き換える。
- 版と `observed` を補う。
- `--drop` で消えたソースを外す。
- `status` は次を返す。
  - 古い範囲:版の違い、意味 Atom の `uses` の変化
  - 読んでいない範囲

**AC2 Law DSL**
マニュアル第4章の例のファイルを、`archsig law check` が読める。設計 §4 の解決の誤り(宣言されていない意味や読み、`about` のない規則、`values` にない値)を、ファイルと行とともに返す。
`changes` 以外の規則の Law は、計算する問いのサマリの `not_computed` に並ぶ。

**AC3 構造**
設計 §3.2〜3.5 のとおりに構造を作る。次の回帰例が通る。

- `g(0); g(1)` と呼ぶ操作で、二つの呼び出しと、それぞれの `passes` が区別される。最後の値は `g(1)` のものになる。
- `x=0; x=1; x=0` と書く操作で、最後の値が `0` になり、三つの書き込みが記録に残る。
- 種類の違う `defines` を持つ要素が関わる計算は、`unresolved` で沈黙する。
- `$order.shipping_address.country` と `$new.country` を、設計 §3.5 の場所として読む。

**AC4 候補を重ねる**
設計 §3.6 のとおりに、候補を ArchMap に重ね、対応を作る。次の回帰例が通る。

- 候補が操作 `h` を足して `g` を呼び、`resolves(g)` を書いても、変えていない `g` の定義と書き込みが残る。
- `removes` した型のフィールドは、変更後の構造から消える。
- 書き直していない操作が消える要素を使えば、`missing` として挙がる。
- 名前の変わる引数は、`corresponds` で対応する。同じ名前の要素と引数は、自分自身に対応する。

**AC5 変更の後も保たれるか(`plan check`)**
`changes commute with operations` と `changes keep` を、設計 §5.4 のとおりに計算する。

- 反例は、マニュアル第5章 問い3と第6章の検算データを持つ。
  - 入力が満たす条件。`when` の字句と場所も付ける。
  - 二つの順番でたどった書き込みの列
  - それぞれの最後の値
  - 食い違いの元の書き込み
- 成り立つときは、比べた分岐と、分岐ごとの値を持つ。
- 読んでいない呼び出し先があれば、`unread` で沈黙する。
  - `resolves` がソースを指せば、そのソースを `next` の `read` に返す。
  - `resolves` がなければ、要素の名前を `next` の `element` に返す。
- 外部の要素の呼び出しは書き込みなしとして扱い、`conditions` に書く。
- 分岐と展開の上限を超えたら、`limit` で沈黙する。

**AC6 仕事を分ける(`plan split`)**
マニュアル第5章 問い7の「分ける」のとおりに、読みの局所ごとの候補と、共有の条件を `.archsig/plans/<候補>/<局所>/` に書き出す。
共有の条件には、局所をまたぐ呼び出し、引数渡し、`corresponds` が入る。
行き先が一つに決まらない対応があれば、`conflict` を返して書き出さない。

**AC7 実装後に比べる(`compare`)**
`compare` が、候補を与えたときも与えないときも、マニュアル第5章 問い3の「実装後に比べる」のとおりに動く。

- 変更前は、与えた ArchMap とする。どの時点の ArchMap を変更前にするかは、使う側が決める。
- 変更後の ArchMap で `changes` の規則を計算し直す。変更後の要素の意味は、観測し直した意味 Atom で確かめる。
- 候補の構造 Atom が、出現の数まで観測されているかを確かめる。足りなければ `mismatch` を返す。
- 候補にない書き込みも `mismatch` として返す。

**AC8 結果**
マニュアル第6章のとおりに、結果を返して残す。

- 実行を `.archsig/runs/r-<番号>/` に、サマリと結論ごとの詳細として残す。
- `archsig show` で詳細を返す。
- 沈黙の `next` を、サマリで読む所ごとにまとめる。

**AC9 第2章の一周**
第2章の `shop` の例を fixture にし、次の順の e2e テストが通る。

1. 最初の `plan check` が `unread` で沈黙し、`shop/shipping/address.py` を返す。
2. 読み足すと、国をまたぐ分岐で反例が出る。
3. `reset_authorization` を呼ぶ候補では、2分岐とも成り立つ。
4. `plan split` が三つの局所に分け、`update_shipping` から `reset_authorization` への呼び出しと引数渡しが共有に入る。
5. 実装後の `compare --plan` がすべて成り立つ。
6. 決済側が空文字を書く実装では、反例と `mismatch` が出る。

**AC10 言語を知らない中核**
設計 §2 と §9 のとおり、エンジンは構造、幾何、解決した Law だけを受け取る。

- 要素の名前からソースのパスを推すコードを、中核に持たない。
- ファイルと git に触るのは、`archmap` と `cli` だけである。

`pr-review` の「責務範囲」の観点で確かめる。

**AC11 マニュアルと設計への書き戻し**
第2章の計算の結果、三値と沈黙の意味、入力トライアドは、マニュアルと設計のとおりに実装する。
周辺の振る舞い(誤りの扱い、入力の拒否、出力の細かい形、文法の緩さ)と、中核の中でもマニュアルと設計が決めていない振る舞いは、各 PR では決めきらず、穴の一覧の Issue(`ArchSig v0.6.0 穴の一覧`)に積む。
AC9 の後に穴の一覧を潰し、実装で決めた振る舞いを、マニュアルと設計に書く。

## 実装の順

依存の順に Issue を切る。一つの Issue が一つの PR である。

1. クレートの骨組み、Atom と式、ArchMap(AC1)、CI のジョブ
2. Law DSL(AC2)
3. 構造(AC3)
4. 候補を重ねる、対応(AC4)
5. 操作の実行のエンジン、`plan check`、結果(AC5、AC8)
6. `plan split`(AC6)
7. `compare`(AC7)
8. 第2章の一周の e2e(AC9)
9. 穴の一覧を潰し、マニュアルと設計を実装に合わせる(AC11)

AC10 は、どの PR でも確かめる。

## スコープ外

- 問い1、2、4〜8 の計算。ただし AC6 の `plan split`(問い7の「分ける」)は含む。`check`(`no`、`each`、`agrees`)、`roundtrips`、`paths`、`plan choices`、`plan glue`、`next`、`view`、`verify`、`diff` は含めない。
- 製品として配る SKILL と、エージェントによる実際の観測。fixture の Atom は手で書く。
- v0.5.4 の撤去と、`tools/archsig/` への移設。
- 性能の作り込み。

## 失敗の判定

- 第2章の一周に、マニュアルと設計のどちらにも書かれていない振る舞いが要り、書き足すと既存の記述と矛盾する。このときは PRD の欠陥として止まる。
- 受け入れ要件を満たすために、スコープ外の問いの計算が要る。このときも PRD の欠陥として止まる。
