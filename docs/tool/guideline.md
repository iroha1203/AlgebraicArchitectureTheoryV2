# Tooling 編集ガイドライン

この文書は、`tools/` と `docs/tool` を編集するときの作業方針を定める。

## 位置づけ

- ArchSig の製品像は [ArchSig v0.6.0 製品コンセプト](archsig_v0_6_0_concept.md) にある。
- このガイドラインには作り方の規律だけを書き、コマンド・フィールド・計算仕様の詳細はマニュアルに置く。
- 文書と作業記録の分担は [Workflow guideline](../workflow/guideline.md) の
  「ドキュメントをステートレスに保つ規則」に、PRD の扱いは [PRD guideline](../prd/guideline.md) に従う。
- ArchView と FieldSig は ArchSig の出力を読む側のツールであり、ArchSig の結論を独自に作らない。

## 責務範囲(入力トライアドの正本)

- ArchSig の意味上の入力は、Atom 定義・Law・ArchMap の3つである。Atom 定義は共通の語彙・型・意味を
  持つ独立した定義元であり、Law と ArchMap の両方から参照する。ファイル形式としてのまとめ方と、
  意味上の入力の役割は区別する。
- ArchMap にはコードから観測した Atom だけを書く。判定、結論、局所の分け方は書かない。
- Law は設計上の出発点として必要な区別を定め、Atom 定義を参照して関係・制約・読み方を宣言する。
  特定のコードで観測した値は書かない。複数の Law が同じ Atom 定義を共有できる。
- AAT の理論本体の所在は
  [AGENTS.md「理論本文の参照先」](../../AGENTS.md#理論本文の参照先)にある。
- ArchSig が保証するのは、Atom 定義・Law・ArchMap から結論が正しく導かれたことまでである。
  観測自体がコードに忠実かどうかは観測を行う側（製品の SKILL）が担い、ツールや CI では担保しない。
  語彙を共有しているだけでは観測結果の一致は保証されない。
- エンジンは定義・宣言・観測事実の型と参照を検査し、計算構造・equation realization・写像を構成する。
  計算パイプラインの責務を Law の作者へ押し付けたり、処理系の検証を AAT の追加の定理義務へ転嫁したりしない。
- 入力から決まらない事項は、判断不能（沈黙）として理由とともに返す。沈黙を失敗や残タスクとして扱わない。
- 計算の中核はプログラミング言語やフレームワークに依存しない。
  命名規則やファイルとモジュールの対応といった言語固有の知識は、解析器と製品の SKILL の側に置く。
- 観測の対象は実装コードの構造であり、テストコードと実行時の挙動は扱わない。
- ArchSig の説明では、何を入力して何を計算するかを肯定形で書く。「〜ではない」という否定を主文にしない。

## 作り方

- マニュアルに書かれていない振る舞いを実装で決めたら、同じ変更の中でマニュアルにも反映する。
  仕様をコードの中だけに閉じ込めない。
- 実装は、マニュアルにある具体的な使い方の一つ（第2章の一連の流れなど）を単位として進め、
  その使い方に必要なものだけを入れる。
- CI との連携、終了コード、エラー形式、キャッシュ、入力の拒否や防御的な制約は、
  実際に動かして必要性がはっきりしてから追加する。
- レビューは Issue の受け入れ要件とこのガイドラインの品質規約に照らして行う。
  具体的な不変条件違反・逆向き依存・不正なテストは修正するが、仮想の将来要件や個人の好みで設計を広げない。
- Claude による実装は PRD に沿って進め、手順は `.claude/skills/prd-loop` と `.claude/skills/pr-review` に従う。
- PRD の完了は、PRD の受け入れ要件と実装済みのテストで判定する。
  PRD が求めていない一般的な主張を残タスクにしない。

## Rust 品質規約

### 設計と実装

- 数学・判定の中核は CLI、ファイルシステム、OS 計測に依存させない。責務と依存の向きが明確な構成を選び、
  分離すること自体を目的に層やクレートを増やさない。
- 意味のある状態と不変条件は、型や検証済みの構築経路で表現する。未観測と観測済みの零、未検証と検証済みを
  区別し、検証済みの値を外部から不正な状態へ書き換えられる API を作らない。
- API の入力・出力・エラー・副作用を明確にし、利用者に必要な失敗条件を説明する。
  不正な入力を既定値・無制限予算・成功へ黙って変換しない。
- 想定される入力エラーや I/O 失敗は `Result` で返す。`panic!`、`unwrap`、`expect` は成立根拠のある
  不変条件に限る（テストの準備失敗を `expect` で明示することは妨げない）。
- 所有権と借用を素直に使い、不要な `clone`、`Arc`、`Mutex` を増やさない。
  一方で、小さなコピーを一つ避けるためだけに lifetime や API を複雑にしない。
- `unsafe` は必要性を説明できる最小範囲に限定し、安全条件とその成立根拠を明記する。
- `rustfmt` を使い、変更に関係する Clippy lint を選んで確認する。全 restriction lint の一括有効化や、
  警告の一括抑制を品質の代用にしない。

### 簡素化と引き算

- 現在の要求で使わない機能・設定・将来用の拡張点を残さない。既存の検証や変換を再利用し、
  同じ責務の並行実装を増やさない。
- trait、ラッパー、層は、実際の依存分離・再利用・読みやすさの観点から必要性を説明できる場合に置く。
  仮想の別バックエンドだけを理由に一般化しない。
- 不要な公開範囲・依存・保持状態・キャッシュ・出力を減らす。行数ではなく、理解・変更・運用の負担で判断する。
  必要な振る舞いや安全検査は維持し、削除件数そのものを目標にしない。

### レビューでの扱い

- 指摘では、該当箇所・具体的な問題・最小の修正案を簡潔に示す。問題がなければ指摘を作らない。
  既存の独立査読と共有の review protocol が求める反証根拠や未確認範囲は、必要な分だけ残す。
- 簡素化の確認は既存レビューの観点の一つとして行い、別の必須工程や削除ノルマを作らない。
  個人の書き方の好みだけでマージを止めない。

## テスト責務と実行経路

- ツールのテストは、そのツールの計算と出力だけを確かめる。
  ArchSig のテストから ArchView、website、SKILL、ドキュメントを検査しない。
- README、マニュアル、website の文言・見出し・配置を製品テストで固定しない。
  文書本文をテスト入力や期待値の保存先にしたり、本文から抽出してテストしたりする構成にしない。
  文書の編集によって製品テストが落ちる依存を作らない。
- ArchSig のテストは、マニュアルに書かれた振る舞いと公開仕様（contract）を、文書から独立した
  フィクスチャ・明示的な引数・期待値で検証する。マニュアルの例を基にテストを設計し、
  コマンドを実行して結果を確かめる。

### テストの書き方

- 検査できる最も狭い層を選ぶ。数学・判定の組合せは単体テストまたは内部統合テスト、コンポーネントや公開 API の
  仕様は統合テスト、引数・終了状態・出力・保存・再利用は実バイナリの E2E テストで確認する。
  同じ網羅ケースを各層で重複させない。下層へ移す場合も、E2E でしか確かめられない確認は残す。
- 関連する値・状態・エラー種別を検証する。件数や成功可否だけでは仕様を確認できない場合、
  それだけで済ませない。期待値は、検査対象と同じ誤実装を再現するような方法で作らない。
- 回帰テストは、可能な範囲で修正前に失敗し、修正後に成功することを確かめる。
  偶然の呼び出し順序よりも振る舞いと仕様を検査し、フィクスチャやテスト補助コードは条件と期待値が読み取れる最小構成にする。
- ファイルやプロセス環境を隔離し、時刻や乱数を制御する。固定の sleep を同期の根拠にせず、
  自分が起動した子プロセスには独立した待機上限を設けて確実に終了・回収する。
- アサーションの弱化、スナップショットの無検討な更新、製品予算の緩和でテストを通さない。
  重複を除き、適切な層へ配置する。性能測定と正しさの検査は区別する。

### CI への追加

CI への追加は [Workflow guideline](../workflow/guideline.md#ci-への恒久追加の禁止) の承認規律に加え、
想定する CI 環境で準備・コンパイル・テストの合計が3分以内である実測を条件とする。
この時間条件は本プロジェクト固有の要件であり、Rust の一般的な標準ではない。

上記は本プロジェクトで採用する規約である。以下の資料から設計・検査の考え方を参照しているが、

  [表現の隠蔽](https://rust-lang.github.io/api-guidelines/future-proofing.html)、[失敗条件の文書化](https://rust-lang.github.io/api-guidelines/documentation.html)。
- rust-analyzer: [依存分離](https://rust-analyzer.github.io/book/contributing/architecture.html)、
  [style review](https://rust-analyzer.github.io/book/contributing/style.html)。
- Rust Book: [Result と panic](https://doc.rust-lang.org/book/ch09-03-to-panic-or-not-to-panic.html)、
  [テスト構成](https://doc.rust-lang.org/book/ch11-03-test-organization.html)、[実行と共有環境](https://doc.rust-lang.org/book/ch11-02-running-tests.html)。
  Rust Compiler Development Guide の[回帰テスト](https://rustc-dev-guide.rust-lang.org/tests/adding.html)、
  [Clippy の lint 選択](https://doc.rust-lang.org/clippy/usage.html)も参照する。

PR 前の共通確認は [Workflow guideline](../workflow/guideline.md) の「PR 前の共通確認」に従う。
