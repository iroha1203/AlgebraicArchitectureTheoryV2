# Tooling 編集ガイドライン

この文書は、`tools/`（主対象は ArchSig v0.6.0: `tools/archsig_v0.6.0/`、および `tools/archview/`・`tools/fieldsig/`）と `docs/tool` を編集するときの作業方針を定める。

## 位置づけ

- ArchSig の製品像は [ArchSig v0.6.0 製品コンセプト](archsig_v0_6_0_concept.md) に、コマンド・入出力・計算仕様の詳細は [ArchSig v0.6.0 I/O 仕様](archsig_v0_6_0_io/README.md) と [クレート README](../../tools/archsig_v0.6.0/README.md) に置く。
- このガイドラインには作り方の規律を書き、仕様の詳細は上記仕様書群に置く。
- 文書と作業記録の分担は [Workflow guideline](../workflow/guideline.md) の
  「ドキュメントをステートレスに保つ規則」に、PRD の扱いは [PRD guideline](../prd/guideline.md) に従う。
- ArchView と FieldSig は ArchSig の出力を読み、AAT の構造解析の判定・結論には ArchSig の計算結果を用いる。

## 責務範囲(入力トライアドの正本)

- ArchSig の意味上の入力は、**Atom 定義・Law・ArchMap** の3つであり、調べる対象や段階の選択は実行指定の**問い**として分ける。Atom 定義は共通の語彙・型・意味を持つ独立した定義元であり、Law と ArchMap の両方から参照する。ファイル形式としてのまとめ方と、意味上の入力の役割は区別する。
- **ArchMap** にはコードから観測した原始事実（Atom）だけを記述し、判定・結論・局所の分け方は計算側・Law 側の責務とする。
  - 各観測事実には、**由来（静的解析・実行観測・LLM 読解候補・人間採用の区別）**とソース参照を保持する。
  - 観測と整合する解釈が複数残る場合は、単一の解釈へ恣意的に潰さず、**実現族**として候補を保持する。
- **Law** は特定のコード実体の観測値から独立に、設計上の出発点として必要な区別を定め、Atom 定義を参照して関係・制約・reading・局所公開情報を宣言する。複数の Law が同じ Atom 定義を共有できる。
  - 変更探索・修復・設計比較で用いる**許容変換仕様**と、保存 Law とは別に達成したい**目的評価条件**も、特定コード実体に依存しない規則側（Law 側）に帰属させる。
- **結論注入と由来混同の禁止**: 成立・不整合・障害類・修復解・比較同型そのものなど、計算の結論に相当するデータを外部入力として注入してはならない。また、LLM の読解候補・観測事実・計算結果・数学的証明の種別を混ぜない。
- AAT の理論本体の所在は
  [AGENTS.md「理論本文の参照先」](../../AGENTS.md#理論本文の参照先)にある。
- ArchSig は、与えられた Atom 定義・Law・ArchMap から結論が正しく導かれたことを保証する。
  観測自体がコードに忠実であることの担保は、観測を行う側（同梱 SKILL 等）の責務とする。
- エンジンは定義・宣言・観測事実の型と参照を検査し、計算構造・方程式の生成・写像の構成・復元までを処理系側の責務として完結させる。
- **数学・Lean との対応規律**: 論文・SHIGURE GOAL（G-139〜G-142）・Lean 定理の有限特殊化を実装する場合は、次を明示して検証する。
  1. 対応する数学定義・定理の参照先。
  2. 有限還元・停止性・評価同値・係数環などの適用条件をコード上で明示的に検査すること。
  3. 適用条件を外れる入力は誤った判定や暗黙の近似を返さず、正常出力の一種である**判断不能（沈黙）**または未対応として理由とともに返すこと。
  4. 計算結果（解・比較射・移行手順等）の実コードへの復元と、変更後の再観測による確認を、数学的計算と区別して扱うこと。
- 計算の中核はプログラミング言語やフレームワークから独立に設計し、命名規則やファイルとモジュールの対応といった言語固有の知識は解析器と同梱 SKILL の側に置く。
- 観測の対象は実装コードの構造とする。
- ArchSig の説明では、何を入力して何を計算するかを肯定形で書く。

## 作り方

- **仕様との同期**: [ArchSig v0.6.0 I/O 仕様](archsig_v0_6_0_io/README.md) に書かれていない振る舞いを実装で決めたら、同じ変更の中で仕様書にも反映し、仕様を文書と同期して保つ。
- **表現先決めと垂直スライス**: 新しい計算領域（SHIGURE の一般構成など）に着手するときは、個別ケースを横並び実装する前に、**中心データ構造・中間表現（IR）・モジュール境界**を先に固定し、最小の垂直スライスを入口から出力まで一気通貫させてから対象を広げる。
- **先回り実装の抑止**: キャッシュ（再利用）、予算制御、パッケージング、終了コードやエラー形式の細かな作り込みは、代表題材を同梱 SKILL から通しで動かして必要性を実測するまで PRD に入れない。
- **開発ループとレビューの統一経路**: ツール開発の実装・レビュー・リファクタリング・実測 QA は、すべて `.codex/skills/`（`prd-loop`・`issue-to-pr`・`review-pr`・`tool-review`・`prd-completion-review`・`refactoring-loop`・`archsig-qa-loop`）に一本化する。
- PRD の完了は、PRD の受け入れ要件・問いへの回答・一次証拠（コード・テスト・実測結果）で判定する
  （判定範囲は [Workflow guideline](../workflow/guideline.md#完了レビューの判定範囲) に従う）。ツール専用 PRD の最終完了レビューは、`prd-completion-review` の同一基準による独立 2 lane で行う。

## Rust 品質規約

### 設計と実装

- 数学・判定の中核は CLI、ファイルシステム、OS 計測から独立させ、責務と依存の向きが明確で自然な粒度の構成を選ぶ。
- **直交分解（組合せ爆発の抑止）**: 「型 × 演算 × 問いの種類 × 局所/大域 × 欠測・補完」のような直交する軸を、個別ケースの特例分岐やファイル複製で展開しない。同種パターンの複製が増える前に、共通の表現・代数的演算へ還元する。
- **肥大化停止線と既存モジュール境界**:
  - 単一ファイルが目安 1,000 行を超えている箇所へ新しい機能・分岐を無条件に追記しない。追加が必要になった時点で増築を止め、責務分割または共通表現への整理を先に行う。
  - SHIGURE の一般構成など新しい計算核を導入するときは、既存の肥大化した `observed/` へ直接継ぎ足さず、独立したモジュールまたはクレート境界として小さく設計し、既存機能とは明示的な変換層で接続する。
- 意味のある状態と不変条件は、型や検証済みの構築経路で表現する。未観測と観測済みの零、未検証と検証済みを型で区別し、検証済みの不変条件が外部から保たれる API を設計する。
- API の入力・出力・エラー・副作用を明確にし、利用者に必要な失敗条件を説明する。不正な入力は既定値・無制限予算・成功へ黙って変換せず、明示的なエラーとして返す。
- 想定される入力エラーや I/O 失敗は `Result` で返す。`panic!`、`unwrap`、`expect` は成立根拠のある不変条件やテストの準備失敗に限る。
- 所有権と借用は素直に扱い、不要な `clone`・`Arc`・`Mutex` と過度な lifetime 複雑化のバランスを読みやすさ基準で取る。
- `unsafe` は必要性を説明できる最小範囲に限定し、安全条件とその成立根拠を明記する。
- `rustfmt` を使い、変更に関係する Clippy lint を選んで品質を確認する。

### 簡素化と引き算

- 現在の要求で使う機能・設定・拡張点に絞り、既存の検証や変換を再利用して実装を一本化する。
- trait、ラッパー、層は、実際の依存分離・再利用・読みやすさへの具体的な効果がある場所に置く。
- 必要な振る舞いや安全検査を保ったうえで、理解・変更・運用の負担を下げる方向で公開範囲・依存・保持状態・キャッシュ・出力をスリムに保つ。

### レビューでの扱い

- ツール PR の内容レビュー（`tool-review`）は、実装セッションから独立した **1 lane** の査読者が全体を通して一貫して行う。
- 指摘では、該当箇所・具体的な問題・最小の修正案を簡潔に示す。既存の独立査読と共有の review protocol が求める反証根拠や未確認範囲は、必要な分だけ残す。
- 仕様書に未定義の境界や設計判断が必要な論点は、レビューと実装の往復で場当たり的に埋めず、設計判断事項として止めて人間へ戻す。
- 簡素化と肥大化抑止の確認はレビューの主要観点の一つとして、具体的な設計・保守・計算量の負担を基準に行う。

## テスト責務と実行経路

- ツールのテストは、そのツール自身の計算と出力を確かめる。
- テスト入力と期待値は、README・仕様書・website の本文から独立したフィクスチャと明示的な引数で用意し、文書の編集から独立して製品テストが成立する構成を保つ。
- ArchSig のテストは、[ArchSig v0.6.0 I/O 仕様](archsig_v0_6_0_io/README.md) と公開仕様（contract）に定められた振る舞いを検証する。
- 検証コマンドは変更したワークスペースの manifest を対象とする（ArchSig v0.6.0 は `tools/archsig_v0.6.0/Cargo.toml`、FieldSig は `tools/fieldsig/Cargo.toml`）。

### テストの書き方

- 検査できる最も狭い層を選び、役割を分担する。数学・判定の組合せは単体テストまたは内部統合テスト、コンポーネントや公開 API の仕様は統合テスト、引数・終了状態・出力・保存・再利用は実バイナリの E2E テストで確認する。
- **テスト増殖の抑止**: 仕様の組合せごとに巨大な統合／CLI テストファイルを複製しない。計算核の代数的性質（保存性・対称性・結合律・再観測一致・欠測や条件外入力での沈黙等）は、単体テストと少数のパラメトリックテストまたは property-based testing で覆い、実バイナリ E2E は公開 CLI の代表経路に絞る。
- **代表規模ベンチマーク（実行時間・最大 RSS の実測）**: 計算核の大きな変更、PRD の節目・完了時、および性能改善では、数百対象・数千 Atom 級の固定代表入力で実行時間と最大 RSS を変更前後で実測比較する。コード読解による静的見積もりだけで性能の妥当性を保証しない。
- 仕様の成立に直結する値・状態・エラー種別を検証し、期待値は検査対象から独立した根拠に基づいて構成する。
- 回帰テストは、可能な範囲で修正前に失敗し、修正後に成功することを確かめる。振る舞いと仕様を検査対象とし、フィクスチャやテスト補助コードは条件と期待値が読み取れる最小構成にする。
- ファイルやプロセス環境を隔離し、時刻や乱数を制御する。同期は状態遷移や完了通知で行い、自分が起動した子プロセスには独立した待機上限を設けて確実に終了・回収する。
- アサーションの弱化、スナップショットの無検討な更新、製品予算の緩和でテストを通してはならない。重複を除いて適切な層へ配置し、性能測定と正しさの検査を区別する。

### CI への追加

CI への追加は [Workflow guideline](../workflow/guideline.md#ci-への恒久追加の禁止) の承認規律に加え、
想定する CI 環境で準備・コンパイル・テストの合計が3分以内である実測を条件とする。
この時間条件は本プロジェクト固有の要件である。
