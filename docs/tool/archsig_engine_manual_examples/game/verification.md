# ゲーム操作の有限計算と検証

[完全な入力・出力と再計算](README.md) · [利用者向けの手順](../../archsig_engine_manual.md)

## 1. 原始事実と役割の束縛

game.archmap.json は30宣言と7使用箇所を、88個の原始 Atom で記録する。
宣言の存在と本体は別の Atom とし、本体が欠けても対象は残る。
32個のソース参照が、コードの各宣言と MODEL_PORTS・RECORDERS の登録を指す。

観測者は、型・有限な値域・式・参照・使用箇所を確認する。
入力に保存の合否、依存グラフ、同値類、作用表、必要な記録の一覧はない。
候補 encoder は原始式として提示する。その具体的な記録表現を核が自動発明したとはしない。

Law の vocabulary に一致する原始事実から使用箇所を集め、
slot と target により G・U・P・V・E を束縛する。
単一であるべき役割が欠ければ missing_binding、複数あれば ambiguous_binding となる。
記録候補は recording の全使用箇所から選び、定義の欠落した候補を集合から除外しない。

G と U の列挙項、P の原始状態更新、V の読取り、E の候補本体を解釈する。
calculate.py にはゲームの宣言名・盤面・体力・期待する件数・候補名を埋め込んでいない。
Law には生成と比較の規則があり、対象固有の値は ArchMap にある。

## 2. 有限域

状態は位置 (x,y)、プレイヤーの体力 h、敵の体力 m からなる。
盤面は8マス、h と m は {0,1,2} であり、
両者死亡と、生きた敵のいる位置にプレイヤーが重なる割当てを除く。

| 状態 | 個数 |
| --- | ---: |
| 双方生存 | 7位置 × 2体力 × 2体力 = 28 |
| プレイヤー死亡 | 7位置 × 敵の2体力 = 14 |
| 敵死亡 | 8位置 × プレイヤーの2体力 = 16 |
| 合計 | 58 |

これは選んだ admissible の全割当てであり、ある開始状態からの到達集合ではない。
終端状態では更新項が状態を変えない。全入力について次状態もこの域にあることを別途確認する。

入力 U は、キー6種 × カメラ4方向 × 色2種 × アニメーション2段階 × 乱数結果2種の192通り。
時計、ネットワーク、乱数生成器は含めない。確率や平均結果ではなく、各論理的乱数結果を扱う。

## 3. Law から操作仕様を構成する

状態集合を G、一手の作用を P:G×U→G、状態の読取りを V とする。
評価は Law の宣言どおり、

~~~text
v_g(u) = V(P(g,u))    (g ∈ G)
~~~

である。有限な評価族の同値関係を、

~~~text
u ~L u'  ⇔  すべての g ∈ G について v_g(u) = v_g(u')
~~~

と置く。[Rising Sea 第3章・定義3.1〜定理3.4](../../../../outreach/paper/rising-sea/ja/06-resolution-invariance.md#31-lawの評価を保つ標準解像度)
の source を U、Law 添字を G とした標準解像度である。

まず各入力の評価タプルを計算し、一致する入力をまとめる。
この段階で候補 encoder は呼ばない。結果は四方向の移動、乱数結果別の二攻撃、待機の7類になる。
記録候補がこの商を実現するかは、同章§3.2の有限 partition 比較に対応する別の検査である。

V が G 上で単射であることと、P の値が G に留まることを検査する。
さらに各類の全要素を再評価し、次の作用が代表に依存しないことを直接照合する。

~~~text
Q = U/~L
q : U → Q
F : G×Q → G
F(g,q(u)) = P(g,u)
~~~

出力の action が F の全406行である。クラスの代表から行を作っただけで済ませず、
全11,136組で因子化の等式を確認する。必要な条件が揃わなければ、
G を値域とする作用の構成を成立として返さない。

この意味で、機器や視点を操作仕様の外側へ置ける。
ここで決まるのは、全状態での作用の分類と、記録が保つ情報である。
具体的なモジュールへの配置は設計者が選ぶ。

## 4. 記録候補と識別対

候補 E:U→R に課す factors_action は、全 g,u,u' について、

~~~text
E(u)=E(u')  ⇒  F(g,q(u))=F(g,q(u'))
~~~

という Law である。各 E-fiber が q-fiber に含まれるかを比較する。
違反するときは同じ記録値になる入力二つと、それらを区別する状態・次状態を返す。

- キーのみの候補は、同じキーを異なるカメラ方向で解釈する場合を区別できない。
- コマンドのみの候補は、同じ攻撃で乱数結果が異なる場合を区別できない。
- events 候補は、q と同じ fiber を持つ。

最後の結果は単なる十分性より強い。この有限評価族について過不足のない記録である。
フィールド名・JSON の配置や、任意のゲームの最小記録量を一意に定めたわけではない。

各入力を q(u) に置き換えた一手が一致し、G が閉じているため、帰納的に
任意の g₀∈G と有限入力列 u₁,…,uₙ で、各段階の状態が一致する。
視点を途中で変える場合も、各 uᵢ の視点を含めて q を計算する。
ルール・量化域・入力の意味が変わった場合に、この主張をそのまま移さない。

order は異なる操作クラスの全21組について合成順序を比較する。
この例では各組に順序が結果を変える状態がある。
任意の一つのプレイで、すべての順序交換が必ず結果を変えるという意味ではない。

## 5. 再現検査

verify.py は以下を実行する。

| 検査 | 確認するもの |
| --- | --- |
| 二入力の隔離再計算 | calculate.py と二 JSON だけを置き、ソース・期待出力なしで同じ全出力を生成する |
| 観測との照合 | 登録の target とソース位置を確認し、11,136組で原始項と説明用コードを比較する |
| 参照 ID の改名 | Atom・subject・source と全参照157 IDを置換し、配列も逆転する。同じ Law で結果が対応する |
| 本体の欠落 | 候補を残して undetermined を返す。操作の分類と他の候補の反例は維持する |
| 非対応・不正入力 | 非対応の項は unsupported、解決不能な参照は invalid_input と区別する |
| 原始式の変更 | 攻撃式から乱数への依存を除く。同じ Law で6類になり、commands が十分になる |

ID 改名では、意味を持つ列挙値、レコード内の field 名、局所変数を変更しない。
コード上の意味そのものを変える編集と、参照の改名を区別する。
出力の参照を逆に対応づけると、状態・入力・類・作用表・判定・反例・根拠が一致する。

補助計算は、この項語彙と有限作用の例を再現するものである。
汎用エンジンの型検査・コンパイラ・中断・保存・再利用の全仕様を実装したものではない。
ArchSig 自身のコンパイル保存については[別の二入力例](../README.md#コンパイル保存)で扱う。

## 6. 他の AAT 計算への接続

この例で構成したものは、Law に相対的な商、作用、因子化、候補の保存条件と識別対である。
計算結果を次の比較へ渡す際には、元の Atom・Law と構成の根拠を保つ。

障害類の対応を調べる場合は、被覆・交差・係数・制限・cochain 比較と具体的な類が別に必要である。
Law の評価保存だけから H¹ の同型や特定の類の零性を結論しない。
意味的修復へ進む際にも、修復状態との対応と貼り合わせ条件を構成する。
これらは[エンジン設計の拡張条件](../../archsig_atom_law_engine/decisions.md#2-拡張を成立させるための判断)に従う。
