# 6. 結果の読み方

ArchSig の出力を最初に読むのはエージェントだ。人は、エージェントの報告を通して結果を見る。

## 実行と置き場所

ArchSig を一度呼ぶと、一つの実行ができる。実行には `r-0193` のような名前が付き、`.archsig/runs/<実行の名前>/` に残る。

```text
.archsig/runs/r-0193/
  summary.json     サマリ
  detail/          結果ごとの詳細
```

実行は、何を入力にしたかを持つ。

- コマンドと、その引数。
- コミットと、使った ArchMap の hash。
- Law の hash と、使った読み。
- 候補を使ったなら、その候補の hash。

`.archsig/runs/` は記録であり、ArchSig の入力ではない。コミットするかどうかはリポジトリごとに決めてよい。

## サマリと詳細

サマリは、結論と場所だけを短く並べる。エージェントは、まずサマリを読む。

```json
{
  "run": "r-0193",
  "command": "plan check split-order",
  "commit": "a1b2c3d",
  "law": "sha256:41ac…",
  "results": [
    {"id": "r-0193/1", "question": "change", "law": "payment-follows-order",
     "subject": "shop.shipping.service.update_shipping", "outcome": "fails", "kind": "counterexample",
     "at": ["shop/shipping/service.py:4"]},
    {"id": "r-0193/2", "question": "law", "law": "identity-mail-from-auth",
     "subject": "shop.order.confirm.confirm->mail.send", "outcome": "silent", "reason": "unread",
     "at": ["shop/order/confirm.py:61"]}
  ],
  "counts": {"holds": 13, "fails": 1, "silent": 1},
  "next": [
    {"read": "shop/order/confirm.py", "scope": "meaning:role", "decides": ["r-0193/2"]}
  ]
}
```

詳細は、結果一つごとに一つのファイルになる。

```text
archsig show r-0193/1
```

`show` で一つの結果の詳細を読む。`--detail` を付けて実行すると、すべての詳細をまとめて書き出す。

表示の形は `--format` で選ぶ。

- `json`:エージェント向け。何も指定しなければこれになる。
- `text`:人が端末で読む形。
- `github`:プルリクエストのコメントと、行への注記の形。

## 結果に共通する欄

- `id`:結果の名前。実行の名前と番号でできている。
- `question`:どの問いの結果か。`law`、`glue`、`change`、`paths`、`reading`、`choices`、`split`、`next` のどれか。
- `law`:どの Law の結果か。
- `subject`:何についての結果か。要素、候補、局所の名前。
- `outcome`:`holds`(成り立つ)、`fails`(成り立たない)、`silent`(沈黙)のどれか。
- `kind`:成り立たないときの形。次のどれかである。
  - `violation`:Law の違反。局所の中の矛盾もこれに入る。
  - `obstruction`:貼り合わせの障害。
  - `counterexample`:変更の反例。
  - `missing`:変更後に対応する要素がない。
  - `mismatch`:候補と実装の食い違い。
  - `divergence`:経路による食い違い。
  - `conflict`:局所の候補どうしが食い違う、または条件が局所に閉じない。
- `reason`:沈黙の理由。`outcome` が `silent` のときだけ付く。
- `at`:ソースの場所。候補の中なら `plan:<名前>`。

`choices`、`split`、`next` の結果は、ほかの問いの判定ではなく、一覧を返す。`outcome` は `holds` で、一覧は詳細に入る。

詳細には、さらに次の欄が入る。

- `basis`:根拠にした Atom の同一性と、Law の定義。
- `check`:検算データ。
- `conditions`:成り立つ条件。
- `theory`:計算が立っている Rising Sea の節。
- `repairs`:貼り合わせの障害を直す場所の候補(第5章の問い2)。
- `next`:沈黙したとき、何を読めば決まるか。

サマリの `next` は、読む場所(`read`)、読む中身(`scope`)、読めば決まる結果(`decides`)の組の列である。

## 検算データ

どの結論にも、算術で確かめられる具体的な値が付く。これを検算データと呼ぶ。
検算データを確かめれば、ArchSig の計算の中身を追わなくても、結論が正しいかが分かる。

| 結論 | 検算データ |
| --- | --- |
| Law の違反 | 当てはまった要素と、当てはまった理由になる Atom |
| 貼り合わせの障害 | 輪か道の流れの列、各流れの向きと換算の整数、足し引きした和 |
| 全体で貼り合う | 各要素に割り当てた単位、または要素どうしの単位の差 |
| 直す場所の候補 | 直した後の換算と、そのときの単位の割り当て |
| 変更の反例 | 入力が満たす条件、二つの順番でたどった書き込みの列、それぞれの最後の値 |
| 変更が成り立つ | 比べた分岐と、分岐ごとの二つの値 |
| 対応の欠け | 対応のない要素 |
| 経路の食い違い | 要素と、二つの経路でそれぞれ移った先 |
| 経路が一致する | 二つの経路でつないだ対応の表 |
| 粒度の対応 | 局所ごとに比べた意味の値、比較写像の行列、その核と余核の次元 |
| 変更の決め方 | Law を保つ組み合わせの一覧と、それぞれで比べた値 |
| 仕事の分け方 | 局所ごとの Atom と共有の条件。合わせると候補全体になること |
| 組み立ての食い違い | 食い違う要素と、それぞれの候補の Atom |

ArchSig は、結果を書き出す前に、検算データを別の小さな検査器で確かめる。
確かめられなかったら、その結果を書き出さず、内部エラーで止まる。
エージェントや CI も、同じ検査器を呼べる。

```text
archsig verify r-0193
```

いちばん少ない本数であること、すべて挙げたことのように、数え上げで決めた性質は、検算の対象ではない。
それらは `conditions` に、数え上げの範囲とともに書く。

## 沈黙

入力から決められないとき、ArchSig は結論を出さない。沈黙の理由は四つある。

- `unread`:結論に関わる範囲を読んでいない。
- `unresolved`:結論に関わる名前や値が `?` である。
- `unchecked`:計算の前提になる条件を、入力の上で確かめられない。粗い読みで Law の値を読み戻せるかを確かめられない場合などである。
- `limit`:計算の量が上限を超えた。分岐や組み合わせの数え上げ、呼び出しの展開で起きる。

`unread` と `unresolved` には、何を読めば決まるかが付く。
沈黙した結果も一つずつ `results` に入り、`counts` で数えられる。

## 成り立つ条件

結論は、どれも次の条件の下で成り立つ。

- ArchMap に記録された Atom の上で計算したこと。コードとの対応は、Atom の `at` と、観測し直すことで確かめる。
- 選んだ読みと Law の下での結論であること。
- 操作の呼び出しの結果は、`fresh` を除き、同じ操作に同じ値を渡せば同じ結果が返るものとして扱ったこと。

Rising Sea の定理を使う計算では、その定理の条件のうち、入力の上で確かめたものを `conditions` に並べる。
確かめられない条件があれば、その結論は出さずに `unchecked` で沈黙する。

## 実行の終わり方

ArchSig は、終了コードで実行の結果を返す。

- `0`:成り立たない結果がない。
- `1`:成り立たない結果がある。
- `2`:入力を受け付けなかった。
- `3`:内部エラー。検算データを確かめられなかった場合も含む。

沈黙だけなら `0` になる。`--require-decided` を付けると、沈黙も `1` になる。
CI では `--require-decided` を付ける。観測を省いたまま、沈黙で CI を通すことを防ぐためだ。

入力を受け付けなかったときは、次の形で返す。

```json
{"error": "rejected",
 "items": [{"file": ".archsig/map/shop/order/model.py.jsonl", "line": 12,
            "rule": "meaning-needs-two-observers", "message": "by に観測者が一人しかいない"}]}
```

`rule` の一覧は `archsig schema error` で返す。

## 結果を使い回す

結果を使い回す鍵は、次の四つである。

- Law の hash と、使った読み。
- その Law が見る Atom(規則に出てくる種類と意味の Atom)すべての hash。
- 候補を使ったなら、その候補の hash。
- 読んだ範囲の hash。

鍵がどれも同じなら、ArchSig は結果を計算し直さずに使う。
使う前に、検算データを `verify` と同じ検査で確かめ直し、検算データが今の ArchMap の Atom から出ることも確かめる。
確かめられない結果は捨てて、計算し直す。

今のコードについての結果として返すのは、鍵が今の入力と同じ結果だけである。
`archsig status` は、鍵が変わって古くなった結果も返す。

## 二つの実行を比べる

```text
archsig diff <実行> <実行>
```

変更前のコミットと変更後のコミットでの実行を比べ、新しく成り立たなくなった結果と、成り立つようになった結果を返す。

二つの結果が同じかどうかは、`question`、`law`、`subject`、`kind` と、形をそろえた証拠で決める。
証拠は、違反なら当てはまった要素、障害なら輪の流れの集まり、反例なら分岐の条件である。行がずれても、同じ違反は同じ違反である。

二つの実行で Law の hash が違うとき、`diff` は結果を三つに分けて返す。

- コードの変更で変わった結果。
- Law の変更で変わった結果。
- 両方にまたがる結果。

見分けるために、`diff` は新しいコードを古い Law でも計算する。
Law の変更で消えた違反は、成り立つようになった結果には数えない。
プルリクエストのレビューでは、この差分を使う。
