# 6. 結果の読み方

ArchSig の出力を最初に読むのはエージェントだ。人は、エージェントの報告を通して結果を見る。
この章では、結果の置き場所、サマリと詳細、結果に共通する欄、検算データ、沈黙、結果の使い回しを扱う。

## 実行と置き場所

ArchSig を一度呼ぶと、一つの実行ができる。実行には `r-0193` のような名前が付き、`.archsig/runs/<実行の名前>/` に残る。

```text
.archsig/runs/r-0193/
  summary.json     サマリ
  detail/          結果ごとの詳細
```

実行は、何を入力にしたかを持つ。

- コマンドと、その引数。
- コミットと、使った ArchMap の hash。
- Law の hash と、使った読み。
- 候補を使ったなら、その候補の hash。

## サマリと詳細

サマリは、結論と場所だけを短く並べる。エージェントは、まずサマリを読む。

```json
{
  "run": "r-0193",
  "command": "plan check split-order",
  "commit": "a1b2c3d",
  "law": "sha256:41ac…",
  "results": [
    {"id": "r-0193/1", "question": "change", "law": "payment-follows-order",
     "subject": "shipping.update_shipping", "outcome": "fails", "kind": "counterexample",
     "at": ["shop/shipping/service.py:4"]}
  ],
  "counts": {"holds": 13, "fails": 1, "silent": 0},
  "next": []
}
```

詳細は、結果一つごとに一つのファイルになる。

```text
archsig show r-0193/1
```

`show` で一つの結果の詳細を読む。`--detail` を付けて実行すると、すべての詳細をまとめて書き出す。

表示の形は `--format` で選ぶ。

- `json`:エージェント向け。何も指定しなければこれになる。
- `text`:人が端末で読む形。
- `github`:プルリクエストのコメントと、行への注記の形。

## 結果に共通する欄

- `id`:結果の名前。実行の名前と番号でできている。
- `question`:どの問いの結果か。`law`、`glue`、`change`、`paths`、`reading`、`choices`、`split`、`next` のどれか。
- `law`:どの Law の結果か。
- `subject`:何についての結果か。要素、候補、局所の名前。
- `outcome`:`holds`(成り立つ)、`fails`(成り立たない)、`silent`(沈黙)のどれか。
- `kind`:成り立たないときの形。`violation`(違反)、`obstruction`(貼り合わせの障害)、`counterexample`(反例)、`mismatch`(候補と実装の食い違い)、`divergence`(経路による食い違い)のどれか。
- `at`:ソースの場所。候補の中なら `plan:<名前>`。

詳細には、さらに次の欄が入る。

- `basis`:根拠にした Atom の同一性と、Law の定義。
- `check`:検算データ。
- `conditions`:成り立つ条件。
- `theory`:計算が立っている Rising Sea の節。
- `next`:沈黙したとき、何を読めば決まるか。

## 検算データ

どの結論にも、算術で確かめられる具体的な値が付く。これを検算データと呼ぶ。
結論が正しいかは、検算データを確かめれば分かる。ArchSig の計算の中身を信じる必要はない。

| 結論 | 検算データ |
| --- | --- |
| Law の違反 | 当てはまった要素と、当てはまった理由になる Atom |
| 貼り合わせの障害 | 流れの列、各流れの換算の整数、その合計 |
| 全体で貼り合う | 各フィールドに割り当てた単位 |
| 変更の反例 | 入力が満たす条件、二つの順番でたどった書き込みの列、それぞれの最後の値 |
| 変更が成り立つ | 比べた分岐と、分岐ごとの二つの値 |
| 経路の食い違い | 要素と、二つの経路でそれぞれ移った先 |
| 粒度の対応 | 局所ごとに確かめた、粗い読みと細かい読みの Law の値 |
| 変更の決め方 | Law を保つ対応の一覧と、それぞれで比べた値 |

ArchSig は、結果を書き出す前に、検算データを別の小さな検査器で確かめる。
確かめられなかったら、その結果を書き出さず、内部エラーで止まる。
エージェントや CI も、同じ検査器を呼べる。

```text
archsig verify r-0193
```

## 沈黙

入力から決められないとき、ArchSig は結論を出さない。沈黙には、理由が四つある。

- `unread`:結論に関わる範囲を読んでいない。
- `unresolved`:結論に関わる名前や値が `?` である。
- `unchecked`:計算の前提になる条件を、入力の上で確かめられない。粗い読みが Law を読めているか確かめられない場合などである。
- `limit`:計算の量が上限を超えた。分岐や組み合わせの数え上げで起きる。

`unread` と `unresolved` には、何を読めば決まるかが付く。
沈黙は数に入り、サマリにも詳細にも残る。結論が出なかったことが見えなくなることはない。

## 成り立つ条件

結論は、どれも次の条件の下で成り立つ。

- ArchMap に記録された Atom の上で計算したこと。コードとの対応は、Atom の `at` と観測し直しで確かめる。
- 選んだ読みと Law の下での結論であること。
- 呼び出しの結果は、同じ操作に同じ値を渡せば同じ結果が返るものとして扱ったこと。

Rising Sea の定理を使う計算では、その定理の条件のうち、入力の上で確かめたものを `conditions` に並べる。
確かめられない条件があれば、その結論は出さずに `unchecked` で沈黙する。

## 実行の終わり方

ArchSig は、終了コードで実行の結果を返す。

- `0`:成り立たない結果が無い。
- `1`:成り立たない結果がある。
- `2`:入力を受け付けなかった。受け付けなかった行を返す。
- `3`:内部エラー。検算データを確かめられなかった場合も含む。

沈黙だけなら `0` になる。`--require-decided` を付けると、沈黙も `1` になる。
CI では `--require-decided` を付ける。観測を省けば沈黙で通れる、という抜け道を塞ぐためだ。

## 結果を使い回す

どの結果も、根拠にした Atom のソースの hash、Law の hash、読み、候補の hash を覚えている。
次の実行で、それらがどれも変わっていなければ、ArchSig は結果を計算し直さずに使う。
一つでも変わっていれば、計算し直す。

`archsig status` は、根拠が変わって古くなった結果も返す。
古くなった結果を、今のコードについての結果として出すことはない。

## 二つの実行を比べる

```text
archsig diff <実行> <実行>
```

変更前のコミットと変更後のコミットでの実行を比べ、新しく成り立たなくなった結果と、成り立つようになった結果を返す。
二つの結果が同じかどうかは、問い、Law、根拠にした Atom の同一性で決める。行がずれても、同じ違反は同じ違反である。
プルリクエストのレビューでは、この差分を使う。
