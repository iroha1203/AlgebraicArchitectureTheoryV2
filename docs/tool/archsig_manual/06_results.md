# 6. 結果の読み方

ArchSig の出力を最初に読むのはエージェントだ。人は、エージェントの報告を通して結果を見る。

## サマリと詳細

出力はサマリと詳細に分かれる。サマリは、結論と場所だけを短く並べる。

```json
{
  "run": "r-0201",
  "command": "check",
  "results": [
    {"id": "r-0201/1", "question": "law", "law": "identity-mail-from-auth",
     "subject": "shop.order.signup.register->mail.send", "outcome": "fails", "kind": "violation",
     "at": ["shop/order/signup.py:30"]},
    {"id": "r-0201/2", "question": "law", "law": "identity-mail-from-auth",
     "subject": "shop.shipping.notify.notify->mail.send", "outcome": "silent", "reason": "unread",
     "at": ["shop/shipping/notify.py:12"]}
  ],
  "next": [
    {"read": "shop/shipping/notify.py", "scope": "meaning:role", "decides": ["r-0201/2"]}
  ]
}
```

詳細は、結論一つごとに `archsig show <id>` で取り出す。

## 結果の欄

- `question`:どの問いの結果か。`law`、`agree`、`change`、`roundtrip`、`paths`、`reading`、`choices`、`split`、`assemble`、`next` のどれか。
- `law`、`subject`、`at`:どの Law の、何についての結果で、ソースのどこか。
- `outcome`:`holds`(成り立つ)、`fails`(成り立たない)、`silent`(沈黙)のどれか。
- `kind`:成り立たないときの形。
  - `violation`:Law の違反。局所の中の矛盾もこれに入る。
  - `obstruction`:貼り合わせの障害。
  - `counterexample`:変更の反例。
  - `missing`:変更後に対応する要素がない。または、消える要素を使う操作を候補が書き直していない。
  - `mismatch`:候補と実装の食い違い。
  - `divergence`:経路による食い違い。
  - `conflict`:局所の候補どうしが食い違う、または条件が局所に閉じない。
  - `refine`:粗い読みでは Law の値か障害が保たれない。
- `reason`:沈黙の理由。

詳細には、根拠にした Atom と Law(`basis`)、検算データ(`check`)、成り立つ条件(`conditions`)、計算が立っている Rising Sea の節(`theory`)が入る。
貼り合わせの障害には直す場所の候補(`repairs`)が、沈黙には何を読めば決まるか(`next`)が付く。
`next` の一つ一つは、読むソースを `read` に持つ。ソースが決まらないときは、代わりに定義を読むべき要素の名前を `element` に持つ。

## 検算データ

どの結論にも、算術で確かめられる具体的な値が付く。これを検算データと呼ぶ。
検算データを確かめれば、ArchSig の計算の中身を追わなくても、結論が ArchMap の Atom から正しく導かれたかが分かる。
ArchSig が保証するのはここまでである。観測が正しいかは、観測する SKILL が担う。

| 結論 | 検算データ |
| --- | --- |
| Law の違反 | 当てはまった要素と、当てはまった理由になる Atom |
| 貼り合わせの障害 | 輪か道の流れの列、各流れの向きと換算の整数、足し引きした和 |
| 全体で貼り合う | 各要素に割り当てた単位、または要素どうしの単位の差 |
| 直す場所の候補 | 直した後の換算と、そのときの単位の割り当て |
| 変更の反例 | 入力が満たす条件、二つの順番でたどった書き込みの列、それぞれの最後の値 |
| 変更が成り立つ | 比べた分岐と、分岐ごとの二つの値 |
| 経路の食い違い | 要素と、二つの経路でそれぞれ移った先 |
| 粒度の対応 | 局所ごとに比べた意味の値、比較写像の行列、その核と余核の次元 |
| 変更の決め方 | Law を保つ組み合わせの一覧と、それぞれで比べた値 |
| 仕事の分け方 | 局所ごとの Atom と共有の条件。合わせると候補全体になること |

`archsig verify` で、検算データを別の小さな検査器で確かめられる。

## 沈黙

入力から決められないとき、ArchSig は結論を出さない。沈黙の理由は四つある。

- `unread`:結論に関わる範囲を読んでいない。
- `unresolved`:結論に関わる名前や値が `?` である。展開する操作の手順の式に `?` がある(第3章)。種類の違う `defines`、`value` のない `defines`、二か所以上の同じ種類の `defines` を持つ要素が関わる。指す先の違う `resolves` が二つ以上ある名前が関わる。外部の型のフィールドを読むか書く。外部でない呼び出しで、呼び出し先の引数にない引数へ値を渡すか、渡す値が一つに決まらない呼び出しを展開する。`resolves` が読んだソースを指すのに定義がない要素を問い合わせた。または、`convert` にない定数で換算が決まらない。
- `unchecked`:計算の前提になる条件を、入力の上で確かめられない。
- `limit`:数え上げや展開の量、式の字句の数、値の項の大きさが上限を超えた。

`unread` と、`?` による `unresolved` には、何を読めば決まるかが付く。

## 成り立つ条件

結論は、ArchMap に記録された Atom の上で、選んだ読みと Law の下で計算したものである。
次は、結論の意味を変える単純化で、関わるものを結果の `conditions` に並べる。

- フィールドは型ごとに一つの値として扱い、同じ型の別々の実体(二つの注文など)は区別しない。
- 条件どうしの関係は見ない。
- 操作の呼び出しの結果は、`fresh` を除き、同じ操作に同じ値を渡せば同じ結果が返るものとみなす。変更前と変更後で呼び出し先の本体(そこから呼ぶ操作を含む)が違えば、この前提を確かめられないので、その呼び出しが関わる比べは `unchecked` で沈黙する(第5章 問い3)。
- 外部の要素(`resolves` が外部を指す要素)の呼び出しは、観測した要素へ書き込まないものとみなす。
- 外部の型(`resolves` が外部を指す型)は、意味を持つフィールドを持たないものとみなす(`changes commute` で、書いたフィールドの型をたどるとき)。

Rising Sea の定理を使う計算では、その定理の条件のうち、入力の上で確かめたものも `conditions` に並べる。
確かめられない条件があれば、その結論は出さずに `unchecked` で沈黙する。

## 二つの実行を比べる

`archsig diff <実行> <実行>` は、変更前と変更後のコミットでの実行を比べ、新しく成り立たなくなった結果と、成り立つようになった結果を返す。
二つの結果が同じかどうかは、問い、Law、対象、形と、証拠(違反なら当てはまった要素、障害なら輪の流れ、反例なら分岐の条件)で決める。行がずれても、同じ違反は同じ違反である。
