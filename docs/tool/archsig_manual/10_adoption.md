# 10. 導入と運用

## 入れるもの

- ArchSig の実行ファイル。
- 四つの SKILL(第7章)。使っているエージェント基盤の、SKILL を置く場所に入れる。
- `archsig init` で作る `.archsig/`。

エージェント基盤には、次のことができる必要がある。

- 別々のエージェントを、互いの結果を見せずに二つ走らせる。意味 Atom の二回の観測に使う。
- 仕事によってモデルを使い分ける。Law を書く仕事には強いモデル、意味の観測には軽いモデルを使う。

## 小さく始める

最初から全部を使う必要はない。問いを一つ決めて、それに要る所だけを観測し、必要になったら広げる。

1. 守りたいことを一つ決め、`no` か `each` の Law を一つ書く。最初は、意味を使わない Law がよい。
2. `sources` は、その Law が関わる範囲だけにする。
3. その範囲の構造を観測し、`archsig record` で ArchMap に書く。
4. `archsig check` を実行する。

読んでいない所が結論に関わると、ArchSig は沈黙して、次に読む場所を返す。そこを読めば結論が出る。
こうして、問いに要る所から ArchMap が育っていく。

次の段で、意味を使う Law を足す。
大きな変更を頼むようになったら、変更の候補(`plan check`)と、仕事の分け方と組み立て(`plan split`、`plan glue`)を使う。
経路の比較、粒度の比較、決め方の数え上げは、その問いが出てきたときに使えばよい。

## 観測の費用

観測の費用は、読むソースの数と、読む意味の数に比例する。`archsig status` は、読んでいないソースの数と、読む意味の数を返す。

- 構造の観測は、解析器で機械的に取り出すので安い。
- 意味の観測は、軽いモデルのエージェント二つが読むので、構造より高い。一致しなかった所は、強いモデルが読む。
- `values` を持つ語彙は、局所ごとにまとめて読める。まとめてよいかは、第5章の問い5で確かめる。
- 二回目からは、変わったソースと、使われ方が変わった要素だけを読み直す。

## CI

CI では、プルリクエストが触った所について結論を求める。

```text
archsig check --changed <変更前のコミット>
```

`--changed` を付けると、変わったソースに関わる結果だけが終了コードに効く。
リポジトリ全体を読んでいなくても、触った所に読んでいない範囲があれば沈黙で失敗する。
変わったソースの観測は、プルリクエストを作るエージェントが archsig-observe で行う。
レビューでは archsig-review が、`archsig diff` で変更前との差分を報告する。

## git での扱い

- `.archsig/law/` と `.archsig/map/` はコミットする。`.archsig/plans/` は、変更を進めている間はブランチにコミットしてよい。
- `.archsig/runs/` は記録なので、コミットしてもしなくてもよい。実行の名前は時刻と乱数から作るので、ブランチの間で重ならない。
- Atom の `at` は、コミットではなくソースの内容の hash で場所を指す。squash merge や rebase の後もたどれる。
- `.archsig/map/` のファイルがブランチどうしで衝突したら、どちらかを採って `archsig status` を実行し、古いと出た所を観測し直す。
