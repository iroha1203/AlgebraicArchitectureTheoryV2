# 5. ArchSig に聞けること

どの問いにも、呼び出すコマンド、ArchSig が何を計算するか、何が返るか、どんなときに沈黙するかを書く。問いは八つある。

1. Law を守っているか
2. 全体で貼り合うか
3. 変更の後も保たれるか
4. 経路や順序で結果が変わるか
5. 粒度を変えても診断は変わらないか
6. 条件を満たす変更は何通りあるか
7. 仕事をどう分け、どう組み立てるか
8. 次にどこを読むか

## 1. Law を守っているか

```text
archsig check
```

`no` と `each` の規則を、今の ArchMap の上で計算する。

- `no` は、当てはまる要素をすべて挙げる。
- `each` は、一行目に当てはまって二行目を満たさない要素をすべて挙げる。

違反の一つ一つが、当てはまった要素と、その根拠の Atom を持つ。Atom の `at` をたどれば、ソースの行に着く。

「ない」ことを確かめるには、その範囲を読んでいる必要がある。
`no` が成り立つと言えるのは、`sources` のソースをすべて、構造も、規則が使う意味も読んでいるときだけである。
`each` の二行目(呼んでいるか、書いているか)も、読んだ範囲でしか確かめられない。
読んでいない範囲があれば、ArchSig は `unread` で沈黙し、その範囲を返す。

背後の数学は、Rising Sea §1.4 の有限の検出と、§2.2 の Law の評価である。

## 2. 全体で貼り合うか

```text
archsig check
```

`agrees along` の規則を計算する。金額の単位を例にとる。

### 値の流れを作る

ArchSig は、Atom から値の流れを作る。流れは、値を渡す元の要素から、受け取る先の要素への矢印で、換算の整数を一つ持つ。

- `writes`、`passes`、`sends`、`returns` の値が、要素そのもの(`$payment.amount`)なら、その要素から書き込み先への流れで、換算は 0。
- 値が `<要素> * <定数>` か `<要素> / <定数>` で、`convert` に同じ演算があれば、その換算の流れ。
- 値が `<要素> + <要素>` か `<要素> - <要素>` なら、両方の要素からの流れで、換算は 0。
- 値が操作の呼び出しなら、呼び出し先の `returns` を、引数を置き換えて展開する。呼び出し先を読んでいなければ `unread` で沈黙する。
- 値が要素と別の要素の掛け算(`$price * $qty`)なら、流れを作らない。量が変わる計算で、単位の換算ではないからだ。
- 値が `convert` にない定数との掛け算や割り算なら、書き込み先について `unresolved` で沈黙する。
- `?` が関わる書き込み先も `unresolved` で沈黙する。
- `receives` の値の式は、受け取ったチャネルの項目そのものとして扱う。

換算の整数は、`convert` から決まる。`convert major -> minor by * 100` なら、minor は major より 2 大きい。
`* 100` の流れの換算は +2、`/ 100` の流れの換算は -2 である。

計算の対象は、`about` の意味を読んだ要素と、そこから流れでつながる要素である。

### 割り当てを求める

ArchSig は、対象の要素すべてに単位の整数を割り当てて、どの流れでも「先の単位 − 元の単位 = 換算」となるようにできるかを調べる。
単位を読んだ要素は、その単位に固定する。読んでいない要素は、割り当ての対象として残す。割り当てができれば、全体で貼り合う。

割り当てができないとき、原因は二つの形のどちらかで現れる。

- 流れを向きを問わずたどって一周し、流れの向きに進むときは換算を足し、逆向きに進むときは引く。その和が 0 でない輪がある。
- 単位を読んだ二つの要素を結ぶ道で、同じように足し引きした和が、二つの単位の差と合わない。

どちらも、流れの列、各流れの向きと換算、足し引きした和を検算データとして返す。整数の足し算で確かめられる。

ArchSig は、まず局所ごとに、その局所に属する流れだけで割り当てを求める。
割り当てができない局所があれば、その局所の中の輪か道を返す。局所の中の矛盾で、`kind` は `violation` になる。
どの局所でも割り当てができるのに、全体では割り当てができないとき、これが貼り合わせの障害で、`kind` は `obstruction` になる。
局所の中の矛盾があるあいだは、貼り合わせの障害の判定は、前提を満たさないので `unchecked` で沈黙する。
一つの局所の中だけを読むレビューでは見つからない。

全体で貼り合うときは、割り当てた単位を返す。これも検算データで、どの流れでも換算と単位の差が合うことを確かめられる。
単位を読んだ要素を一つも含まない流れのつながりでは、単位そのものは決まらない。要素どうしの単位の差だけを返し、単位は沈黙する。

### 直す場所の候補

障害があるとき、ArchSig は直す場所の候補も返す。

- どの流れの換算を変えればすべての障害が消えるか。候補ごとに、直した後の換算と、そのときの単位の割り当てを付ける。これは算術で確かめられる。
- 読んだ単位が道の端にある障害では、その単位の観測を読み直す候補も入る。

候補は、変える流れの本数が少ない順に並べる。どれを選ぶかは仕様の判断である。

### 作り直してはならない値

`values` のない意味の `agrees along` は、取引 ID のような値に使う。
その意味を持つ値を受け取る操作(引数かチャネルの項目がその意味を持つ)が、同じ意味のフィールドに `fresh` の操作の値を書いていれば、違反になる。
受け取った値があるのに、作り直しているからだ。
その意味の値が流れの途中で演算を通るときも、違反になる。

背後の数学は、Rising Sea §2.4 の Čech 障害類、§2.6 の閉路による検出、§2.8 の整数係数の障害である。
直す場所の候補は、§2.8 例2.42 の遷移の変更に当たる。

## 3. 変更の後も保たれるか

```text
archsig plan check <候補>
archsig compare --before <根> --plan <候補>
```

`plan check` は、変更後の構造の上で、すべての Law を計算する。`changes` の規則は、変更前と変更後を比べて計算する。
`plan check` は、`about` の意味が変更前の ArchMap で局所ごとの意味 Atom(第3章)で観測されていれば、`changes` の計算は局所を使わないので、その Law を `unchecked` で沈黙させる。

### 操作を書き込みの列にする

操作は、書き込みの列として表す。操作 f の列は、次のように作る。

- f の `writes` と、f が呼ぶ操作の列を、行の順に並べる。
- 呼び出し先の列の中の引数は、その呼び出しの `passes` の値で置き換える。渡す値は、呼び出しの時点の状態で読む。
- 呼び出しに `when` があれば、呼び出しの時点の状態で一度だけ読む。呼び出し先の書き込みは、その呼び出しが行われた分岐でだけ行う。
- `returns` の後の手順は、その `returns` を行わなかった分岐でだけ行う(第3章)。
- 再帰と、深さか並べた手順の数が上限を超える展開は、`limit` で沈黙する。手順の数は、呼び出しを展開する前にだけ、それまでに並べた手順で数える。呼び出し先を読んでいなければ `unread` で沈黙する。書き込み、条件、渡す値で作る値の項の大きさが上限を超えても、`limit` で沈黙する。外部でない呼び出しの `passes` の受け取る引数が呼び出し先の引数になければ、または渡す値が一つに決まらなければ、`unresolved` で沈黙する(第3章)。

書き込まれていないフィールドは、入力の値を持つ。入力の値は、フィールドの名前を付けた記号で表す。

### 二つの順番を比べる

`changes commute with operations` では、対応させた操作の組ごとに、二つの順番を比べる。
組にするのは、両端が操作と決まる対応だけである。端の片方が操作でないと決まれば組にせず、端の種類が決まらなければ、その組は沈黙する。
`sources` に構造を読んでいないソースがあれば、そこにある操作は組に挙がらないので、Law ごとに一つの `unread` の沈黙を返し、そのソースを並べる。この沈黙は、組があってもなくても返す。すべて読んでいて組が一つもなければ、比べるものがないので成り立つ。

- 変更前の操作をしてから、変更後の型へ移す。
- 変更後の型へ移してから、変更後の操作をする。

移すというのは、`corresponds` に従って、変更前のフィールドの値を変更後のフィールドへ写すことだ。
比べるときは、変更後の値と条件に出てくる名前を、対応の元の変更前の名前にそろえる。結果に出す比べた値(`values`、`diverging`)と分岐の条件の項は、行き先が一つの名前だけを変更後の名前に読み替えて示す(条件の字句 `when` は書いたとおりに示す)。
一つのフィールドを二つに分けた対応では、どちらの行き先の値も、元の変更前のフィールドの値として比べる。二つ以上のフィールドを一つにまとめた対応は、変更前の名前で置けないので、それが結論に関われば `unresolved` で沈黙する。

ArchSig は、`about` の意味を持つフィールドについて、二つの順番で最後に入っている値を求める。
値は、引数からフィールドをたどった先の値として求める。検算データの `place` は、たどったフィールドの列である。
`about` の意味を持つフィールドのほかに、書き込みで変わる次の値も比べる。

- 書いたフィールドの値。
- フィールドの値の中のフィールドに書く(`writes` の `via`)とき、途中までたどったフィールドの値。
- 書いたフィールドから、その型のフィールドをたどった先の値。変更前の操作の書き込みは、変更前の型でたどって `corresponds` で変更後の名前に読み替えた値と、読み替えた書き込み先から変更後の型でたどった値の、両方を比べる。

このうち、たどった最後のフィールドが `about` の意味を持つものを比べる。
そのフィールドが意味を持つかを読んでいなければ、`unread` で沈黙し、そのフィールドを定義したソースの `meaning:<意味>` を返す。
候補が定義したフィールドの意味は、`corresponds` の元のフィールドの意味を移したもの(第3章)なので、元のフィールドが意味を持つかを読んでいなければ、同じく `unread` で沈黙し、元のフィールドを定義したソースの `meaning:<意味>` を返す。

型のフィールドをたどるときは、型を次のように扱う。

- 定義を読んだ型は、そのフィールドをたどる。ArchMap が `<型>.<名前>` を名指しているのに、そのフィールドの定義を読んでいなければ、フィールドは分からないので、定義を読んでいない要素として沈黙する。候補が `removes` した要素は、名指されていても、この沈黙の対象にしない。ただし、候補が型の定義を書き直しても、変更前の ArchMap がその型を名指していて(Atom の名前と `value`・`when` の式、フィールドや引数の型、`resolves` のどこかで)その定義を読んでいなければ、元のフィールドは分からないので、定義を読んでいない型として、下の「定義を読んでいない型は」の箇条のとおりに沈黙する。変更前に `resolves` が外部を指していた型は、外部の型として扱う。変更前が名指していない型は、候補が新しく定義した型としてたどる。
- 型のないフィールドは、その先が決まらないので、`unresolved` で沈黙する。
- 名前が `?` で始まる型、種類の違う `defines`、`value` のない `defines`、二か所以上の同じ種類の `defines` を持つ型、型でない要素は、`unresolved` で沈黙する。`?` の型では、その型を書いたフィールドの定義の場所を返す。
- 定義を読んでいない型は、第3章の「読んだ範囲」のとおりに沈黙する。`resolves` が読んでいないソースを指せば、`unread` で沈黙し、そのソースを返す。`resolves` がなければ、`unread` で沈黙し、その型の名前を返す。`resolves` が読んだソースを指すのに、そこに型の定義がなければ、`unresolved` で沈黙する。指す先の違う `resolves` が二つ以上あれば、解決が決まらないので、`unresolved` で沈黙する。
- `resolves` が外部を指す型は、たどらない。その型は意味を持つフィールドを持たないとみなし、結果の `conditions` にそう書く(第6章)。

型がめぐり、その先に意味を持つフィールドがあれば、たどる先が限りなく続くので、`limit` で沈黙する。一つの書き込みの場所からたどったフィールドの数が上限を超えたときも、`limit` で沈黙する。
型をたどる所の沈黙と、変更前の型でたどって読み替えた場所の沈黙は、ほかの場所で二つの順番の値が食い違えば結論に関わらないので、そのときは反例を返す。同じ書き込みからたどった場所でも、沈黙した場所と食い違う場所が別なら、反例を返す。
書き込みの場所とその頭の部分の場所で意味を持つかが決まらない沈黙と、比べる場所の値を読む所の沈黙(下の `unchecked` など)も同じで、ほかの場所で値が食い違えば反例を返す。意味 Atom を持つフィールドでも、意味を持つかを読んでいなければ(候補が定義したフィールドで、元のフィールドを読んでいないときを含む)、その場所は比べない。操作を実行する所の沈黙と、分岐の組を作る所の沈黙は、比べる分岐が決まらないので、その場で沈黙する。
変更前と変更後で本体の違う呼び出し先の呼び出しを値に含む場所は、同じ値とみなせないので比べず、`unchecked` の沈黙を持つ。ほかの場所で値が食い違えば反例を返す。その呼び出しを条件に含めば、比べる分岐が決まらないので、その場で `unchecked` で沈黙する。

あるフィールド X の値の中のフィールドに書いた後で、X か、引数から X までの途中のフィールドを丸ごと書き直していなければ、X の値の求め方は決めていない。
その値を使う計算は `unchecked` で沈黙する。後の手順の値や条件でその値を読むときと、`about` の意味を持つ途中のフィールドとして比べるときである。
条件は、比べる前に形をそろえる。`a != b` は `a == b` の否定として扱い、同じ形の条件は同じ真偽になる。
条件で分かれる分岐をすべて数え上げ、分岐ごとに比べる。

どの分岐でも一致すれば、成り立つ。比べた分岐と、分岐ごとの値が検算データになる。
一致しない分岐があれば、反例を返す。反例は、入力が満たす条件、二つの順番でたどった書き込みの列、それぞれの最後の値を持つ。反例は、操作の組ごとに、最初に食い違った分岐を一つだけ返す。
ArchSig は条件どうしの関係を見ないので、実際には同時に成り立たない条件の組み合わせで反例が出ることがある。反例の条件を見れば、その分岐を通るかを確かめられる。

### 対応と意味が保たれるか

`changes keep` では、`about` の意味を持つ変更前の要素がどれも、`corresponds` で変更後の要素を持つかを見る。対応のない要素を `missing` として挙げる。
`sources` に、その意味を読んでいないソースがあれば、`unread` で沈黙し、そのソースと `meaning:<意味>` を返す。意味を持つ変更前の要素の定義を読んでいなければ、その要素は、定義を読んでいない要素として沈黙する。対応の行き先に種類の決まるものがなく、種類の決まらないものがあれば、その要素は沈黙する。
実装後に比べるとき、対応のない要素(定義を持つ要素、引数、呼び出し。引数と呼び出しは持ち主の操作の定義のソースで見る)を定義した変更前のソースが変更後の Law の `sources` にあり、観測し直した変更後でその構造を読んでいなければ、その要素が変更後にないとは言えないので、`missing` にせず `unread` で沈黙し、そのソースを返す。そのソースが変更後の `sources` にない(変更後で消した)なら、読む所にならないので、これまでどおり `missing` である。候補が `removes` した要素は、消えることが候補で決まっているので `missing` である。
操作の引数は、対応で結んだ操作どうしで同じ名前どうしが対応する(第3章)。対応の行き先の操作の定義を読んでいなければ、同じ名前の引数があるかが決まらないので、その引数は `missing` にせず、`unread` で沈黙し、その定義の読む所を返す。種類が決まらない操作では `unresolved` で沈黙する。

`plan check` は、候補が書き直していない操作が `removes` した要素を使っていれば、その操作も `missing` として挙げる。書き直す範囲はここで分かる。
本体の構造 Atom(`writes`、`reads`、`calls`、`sends`、`receives`、`returns`、`passes`)の `subject` に現れる名前は、定義を読んでいなくても操作として扱い、消える要素を使えば `missing` とする。名前が `?` で始まる操作と、種類が決まらない操作は、`missing` にせずに沈黙する。操作でないと決まった名前は、結論にしない。
`changes commute` で、対応の行き先の操作が消える要素を使えば、その組は比べず、その Law の `missing` として挙げる。
`removes` のある候補で、定義を読んでいない操作か呼び出し先がある、または `sources` に構造を読んでいないソースがあれば、それらが消える要素を使うかは決まらない。それらは、`subject` が `removes` の一つの沈黙にまとめ、読む所をすべて並べる。
使うかは、候補を重ねた後の構造でたどって決める。候補がフィールドの型を書き換えれば、式の中でそのフィールドから先をたどる道(`$o.a.x`)は、書き換えた型のフィールドを使う。ただし、名前が `?` で始まる型と、変更前に定義を読んでいなかった型を候補が定義し直したもの(変更前に `resolves` が外部を指していた型を除く)は、その先をたどれないので、消える要素を使うかが決まらず沈黙する(定義し直した型の直下のフィールドの名前は決まるので、それを消せば `missing` である)。`?` の型では、道の上でその型を書いた定義(フィールドか、引数を持つ操作)の場所を返す。定義し直した型では、変更前の構造で、定義を読んでいない型として読む所を返す。
書き直していない操作の Atom に、`?` で始まる名前か呼び出し、`?` の値、構文として読めない式、型の分からない道があれば、その先で何を名指すかは決まらない。`removes` のある候補では、その操作は、消える要素を使うと決まっていなければ沈黙する。型の分からない道では、型を決める要素(型のない引数ならその操作、定義のないフィールドならその持ち主の型、型のないフィールドならそのフィールド)を問い合わせ、それが沈黙すればその読む所を返す。
変更後の要素が同じ意味を持つかは、実装後に観測し直した意味 Atom で、`compare --plan` が確かめる。`changes` の Law ごとに、`about` の意味を持つ変更前の要素の対応の行き先を定義したソースでその意味を読んでいて、観測し直した意味 Atom でその行き先がその意味を持たなければ、その行き先を `missing` として返す。そのソースでその意味を読んでいなければ、`unread` で沈黙し、そのソースと `meaning:<意味>` を返す。対応の行き先の定義を読んでいないか、種類が決まらなければ、その行き先が意味を持つかが決まらないので、外さずに沈黙する(読んでいなければ `unread` で読む所を返す)。

### 往復の規則

`roundtrips` の規則も、同じ書き込みの列で計算する。`check` は今のコードで、`plan check` と `compare --plan` は変更後の構造で計算する。

- 読み取りの操作の `returns` を、書き戻しの操作の引数に置き換えて書き込みの列を作り、`about` の意味を持つフィールドの最後の値が入力の値と同じかを見る。
- 書き戻しの後に読み取りの `returns` を求め、書き戻した値と同じかを見る。

一致しない分岐があれば、`kind` を `counterexample` として、問い3と同じ形の反例を返す。

### 実装後に比べる

`compare --plan` は、実装後のコードを観測し直した ArchMap で、同じ計算をする。
変更前は `--before` に渡した変更前のリポジトリの根(その `.archsig/` の ArchMap とソース)、変更後は今の ArchMap である。Law は、今のリポジトリの `.archsig/law/` を使う。
変更前の読んでいない範囲は、`--before` の根のソースで数える。変更後で構造を読んでいないソースがあれば、`changes commute` の Law に `unread` の沈黙を足し、そのソースを返す。消える要素を使う操作は、観測し直した変更後の ArchMap の操作でたどる。
そのうえで、候補の構造 Atom のそれぞれに、同じ Atom が観測されているかを確かめる。同じ Atom かは、第3章の同一性の欄を字句で比べて決める(値と条件を式として読まない)。同じ Atom が候補に二度あれば、観測にも二度要る。
観測されていないと言えるのは、その Atom が観測されるはずのソース(`file` があればそのソース、なければ `subject` の持ち主の要素を候補か変更後で定義したソース)の構造を、観測し直した変更後で読んでいるときだけである。読んでいなければ `unread` で沈黙してそのソースを返し、ソースが決まらなければ(候補の `resolves` など)沈黙する。
候補に書いた要素に、候補にない書き込みが現れたときも、その場所を返す。どちらも `kind` は `mismatch` である。
候補の構造 Atom がすべて観測され、候補にない書き込みもなければ、候補について成り立つを返す。

候補に `plan`、`corresponds`、`removes` の行しかなければ、実装を先にして、対応だけで確かめる使い方になる。
名前を変えない変更なら、候補は要らず、`compare --before <根>` だけでよい。

背後の数学は、Rising Sea §1.8〜1.9 の lens とプロトコルの射の条件、§4.10〜4.11 の可換図式である。
§7.8 例7.28 は、注文を二つに分けて配送先の更新の後も決済データを引き継ぐ例で、第2章の題材と同じ形をしている。

## 4. 経路や順序で結果が変わるか

```text
archsig paths <経路> <経路>
```

一つの変更を、別々の経路でたどったとき、同じ所へ着くかを調べる。
たとえば、API を新しい版へ直接移す候補 `api-direct` と、中間の版を経由する二つの候補 `api-v2`、`api-v3` がある。

```text
archsig paths api-direct api-v2,api-v3
```

経路は候補を `,` でつないで書く。

- 二つの経路は、同じコミットから始める。
- 経路の中の後の候補は、前の候補の上に重ねて適用する。
- 順序を比べるときは、`archsig paths a,b b,a` のように、同じ候補を逆の順で並べる。

ArchSig は、各経路の対応をつなげて、変更前の要素から変更後の要素への対応を作る。
書いていない要素は自分自身に対応するので、途中の候補が触らない要素もつながる。
行って戻る変更(名前を変えて、また戻す)も、そのままつないで比べる。

そのうえで、二つの経路の終点を比べる。

- 同じ要素が、経路によって別の要素へ移っていないか。
- 両方の終点にある同じ名前の操作が、分岐ごとに同じ値を書くか。比べ方は問い3と同じだ。
- `changes` の規則が、どちらの経路でも成り立つか。

食い違いがあれば、`kind` を `divergence` として、要素と、二つの経路での移り先を返す。
食い違いは経路の組に付くもので、どちらかの候補一つのせいとは決まらない。
ArchSig は、経路の中のどの候補の対応を選び直せば食い違いが消えるかも返す。

背後の数学は、Rising Sea §4.4〜4.6 の輸送の合成と比較、辺の選び直し(定理4.23)、§4.7 の面を貼り合わせる条件である。

## 5. 粒度を変えても診断は変わらないか

```text
archsig check --reading <粗い読み> --against <細かい読み>
archsig view --reading <粗い読み>
```

同じ Law を、粗い読みと細かい読みの二つで比べる。
粗い読みで同じ診断が出るなら、その粒度で意味をまとめて観測でき、構造もまとめて扱える。

ArchSig は二つのことを確かめる。

- **Law の値を読み戻せるか。** 粗い局所ごとの意味 Atom と、その局所の中で要素ごとに読んだ意味 Atom が、どれも一致するかを見る。
  要素ごとの意味 Atom は、SKILL が抜き取りで読む。一致しない局所は、細かく読む局所として返す。抜き取りのない局所は `unchecked` で沈黙する。
- **局所の分け方を粗くしても、障害が保たれるか。** `agrees along` の規則では、局所の分け方で輪の数え方が変わる。
  ArchSig は、細かい読みと粗い読みのそれぞれで障害の群を作り、その間の比較写像を行列で求めて、核と余核が 0 かを確かめる。これは読み全体についての計算で、局所ごとの確認では決まらない。

`no` と `each` は、一つ目だけで足りる。`agrees along` は二つとも要る。
`inside` と `outside` に書いた局所は、読みの細かさの関係で移す。移せなければ `unchecked` で沈黙する。

確かめられなかった局所を細かくしたら、その局所だけ細かい読み(`groups` で書く)で、もう一度比べる。

検算データは、局所ごとに比べた意味の値と、比較写像の行列、その核と余核の次元である。

`view` は、粗い読みでまとめた構造を返す。
確かめられた局所では、要素を意味の値ごとにまとめ、局所をまたぐ流れと呼び出しだけを残す。確かめられなかった局所は、まとめずに残す。
どの要素も、元の Atom の `at` へたどれる。

背後の数学は、Rising Sea §3.1 の標準解像度、§3.5 の条件 C による診断不変性、§3.6 の全 Law に対する判定、§3.11 の被覆の細分である。
§3.7 は、局所的な接続情報だけでは判定できない例を示す。`view` のまとめ方は、§6.1〜6.2 の、代表を一つ選ぶ正規化に当たる。

## 6. 条件を満たす変更は何通りあるか

```text
archsig plan choices <候補>
```

候補の対応を全部決めずに書いておくと、ArchSig は Law を保つ決め方を数え上げる。

```json
{"kind": "corresponds", "subject": "shop.order.model.Order.note",
 "object": "shop.shipping.model.OrderShipping.note | shop.payment.model.OrderPayment.note",
 "at": "plan:split-order"}
```

`|` で並べた行き先のどれにするかを決めていない。
ArchSig は、決めていない対応の組み合わせのうち、どの Law も保つものを挙げ、その数を返す。
同じ Law の計算に関わる `|` の集まりごとに、別々に数える。
どの組み合わせも Law を保たなければ、組み合わせごとに、破れる Law と反例を返す。

決め方が二つ以上残るとき、ArchSig は一つに絞るための情報を返す。

- 残った組み合わせの間で、選び方が分かれる `|` の一覧。
- 組み合わせの結論が読んでいない範囲のせいで決まらないなら、その範囲。

残った組み合わせがどれも決まっていて、Law の上で違いが見えないなら、Atom を読み足しても絞れない。人が決めるか、Law を足す。

背後の数学は、Rising Sea §7.3 の観測で見分けるための条件(定理7.9)と、§7.6〜7.7 の変更の分類である。
対応が一対一で、操作が状態をそのまま運ぶ場合は、§7.7 のとおり、操作でつながる成分ごとに決め方が独立で、数は成分ごとの積になる。ArchSig はこの積で数を検算する。

## 7. 仕事をどう分け、どう組み立てるか

### 分ける

```text
archsig plan split <候補> [--reading <読み>]
```

候補を、読みの局所ごとの候補に分ける。読みを省くと、最初に宣言した読みを使う。読みが一つも宣言されていないか、`--reading` の読みが宣言されていなければ、誤りを返す。
分けるのは、その候補に書いた Atom だけで、元の候補の Atom は分けない。

ArchSig は、局所ごとの候補を `.archsig/plans/<候補>/<局所>/plan.jsonl` に書き出す。最初の行は `{"kind": "plan", "subject": "<候補>/<局所>", "base": <分けた候補の base>}` である。前に分けたときの局所のディレクトリは消さない。
局所の名前に `.`、`..`、空の段があれば、候補の下に書き出せないので、どの局所も書き出さずに誤りを返す(根にあるファイルの局所 `.` など)。
中身は、その局所の Atom と、共有の条件である。共有の条件というのは、局所の重なりに属する条件のこと。

- 局所をまたぐ呼び出し、引数渡し、チャネルの項目。
- 局所をまたぐ `corresponds`。
- `agrees along` の規則では、まず全体の単位の割り当てを求め、重なりの要素の単位を共有の条件にする。割り当てができなければ、分けずに障害を返す。
- `changes` の規則では、`corresponds` が全体で一つの対応になる(行き先が二つ以上の要素がない)ことも確かめる。`|` で行き先を並べた対応は、行き先が一つしか残らなくても `conflict` になる。
- どの局所にも属さない Atom(`resolves` が外部だけを指す要素だけを名指す Atom など)。

どの局所も自分の条件を満たし、共有の条件がそろえば、候補全体の Law が成り立つ。
ArchSig はこれを確かめてから書き出す。確かめられなければ、局所に閉じない条件を `kind` `conflict` で返す。
候補の Atom が、定義がなく `resolves` が外部だけを指すのでない要素(外部でないソースを指す、または指す先の違う `resolves` が二つ以上ある。引数と呼び出しの要素は持ち主の操作で見る。定義も `resolves` も持たない `<頭>.<名前>` の要素は頭で見る。第4章)を名指すと、その Atom がどの局所に属するかが決まらないので、分けずに沈黙する。沈黙は第3章「読んだ範囲」の決まりのとおりである。`resolves` の指すソースの構造を読んでいなければ `unread` でそのソースを返し、読んだのに定義がなければ、または指す先の違う `resolves` が二つ以上あれば `unresolved` で沈黙する。
名前が `?` で始まる要素を名指す Atom があれば、分けずに `unresolved` で沈黙し、その Atom の `subject` を要素の名前として返す(問い8)。

担当には、局所の候補を渡す。
局所の候補には、その局所の Atom と共有の条件が、元の候補に書いた順のまま入る(手順の順は Atom の順である。第3章)。局所の候補を `plan check` すると、それを元のコードに重ねた変更として計算する。ほかの局所の Atom は重ならない。ほかの局所で書き直す要素や消す要素は、元のコードのまま計算する(第3章「変更の候補」)。ただし、共有の条件の構造 Atom を `subject` に書いた要素は元の Atom が外れるので、その本体を書き直す局所の Atom がなければ、それが関わる結論は決まらず沈黙する。ほかの局所でだけ定義する要素は定義を読んでいない要素として扱い、それが関わる結論は沈黙する。そのため局所の候補の結論は、その局所の変更を単独で入れたときの結論で、変更全体の結論とは違うことがある(全体では成り立つのに反例を返すこともある)。変更全体が成り立つかは、候補全体を `plan check` して確かめる。

### 組み立てる

```text
archsig plan glue <候補> <候補> … --as <名前>
```

同じコミットを元にする候補を、一つの候補に組み立てる。
担当が局所の候補を詳しく書き直したとき、別々のエージェントやセッションが同じ所から候補を作ったときに使う。

ArchSig は、二つの候補が同じ要素に書いた Atom と、`corresponds` の行き先を比べる。
どれも一致し、組み立てた候補の上ですべての Law が成り立てば、候補 `<名前>` を書き出す。
一致しなければ、`kind` を `conflict` として、食い違う要素と、それぞれの候補の Atom を返す。

背後の数学は、Rising Sea §2.5 の障害類の消滅から貼り合わせへ、§5.1 の対応する入力の fiber product、§8.6 の設計変更への適用である。

## 8. 次にどこを読むか

```text
archsig next [--for <結果、候補、Law>]
```

問いに答えるために、次に観測すべき所を返す。挙がるのは次の四種類だ。

- 読んでいない範囲のせいで沈黙した結論がある。その範囲を返す。
- `?` の名前や値のせいで沈黙した結論がある。その Atom の場所を返す。候補の中の Atom は行を持たないので、`changes keep` と `plan split` は、場所の代わりに、その Atom の `subject` を要素の名前として返す(対応の Atom では、対応の元の要素)。候補の `?` は、観測を足すのではなく、候補を直して決める。
- 古くなった範囲や意味 Atom が、結論に関わっている。その範囲を返す。
- 候補の決め方が二つ以上残り、読んでいない範囲で区別できる。その範囲を返す(問い6)。

どれにも、読むソース(ソースが決まらなければ要素の名前)、読む中身(構造か、どの意味か)、読めば決まる結論が付く。決まる結論の多い順に並ぶ。

Law を足したり変えたりした後も、`next` で新しく必要になった観測を確かめる。
