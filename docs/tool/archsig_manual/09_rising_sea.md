# 9. Rising Sea との対応

ArchSig の計算は、AAT の基礎論文 Rising Sea の構成と結果にもとづく。
ArchSig のどの部分が論文のどこに対応するかと、ツールの都合で変えた所を示す。
節番号は Rising Sea 初版(arXiv v1)の日本語原稿による。

| 読み、局所 | §1.3 局所文脈、§1.5 被覆から site へ |

ArchSig の読みは、論文の被覆、つまり局所文脈の族に当たる。
論文の §1.7 の Reading は、抽出、対象の作り方、操作、方程式を含む読み全体で、ArchSig の読みより広い。

## 問いごとの対応

**Law を守っているか。** §1.4 の有限の検出(命題1.16)に当たる。
`each … calls` の違反は、定義1.14 の「二つの Atom はあるのに、その間に指定した関係がない」という検出の形そのものである。
「ない」ことの検出は、その範囲を読んでいることを前提にする。`unread` の沈黙がこれに当たる。

**全体で貼り合うか。** 要素を chart、値の流れを重なりの辺と遷移、単位の割り当てを局所状態とみて、§2.8 の局所状態とアフィン遷移から障害を計算する形である。
障害は §2.4 の Čech 障害類で、§2.6 命題2.28 の閉路の和、観測済みの端点があるときは命題2.29 の、端点での値の差として示す。
直す場所の候補は、§2.8 例2.42 の遷移の変更に当たる。§2.9〜2.10 の意味的な修復は、遷移を変えずに補正で貼り合わせるもので、障害類が 0 のときに限って存在する。ArchSig の直す場所の候補とは別のものである。

**変更の後も保たれるか。** §1.8〜1.9 の lens とプロトコルの射の条件、§4.10〜4.11 の読み取り・更新・操作の可換図式に当たる。
§7.8 例7.28 は、注文を二つに分けて配送先の更新の後も決済データを引き継ぐ例で、第2章の題材と同じ形をしている。
`roundtrips` は、§1.8 の lens の読み取りと更新の法則を、書き込みの列の上で確かめる形である。

**経路や順序で結果が変わるか。** §4.4〜4.6 の輸送の単位と合成、指定した比較と標準比較の差、辺の選び直し(定理4.23)、§4.7 の面を貼り合わせる条件に当たる。

**粒度を変えても診断は変わらないか。** §3.1 の標準解像度(Law の値を読み戻せること)、§3.5 の条件 C による診断不変性、§3.6 の全 Law に対する判定、§3.11 の被覆の細分に当たる。
§3.7 が示すとおり、局所的な接続情報だけでは判定できない。ArchSig が比較写像を読み全体で計算するのはこのためである。
`view` のまとめ方は、§6.1〜6.2 の、代表を一つ選ぶ正規化に当たる。

**条件を満たす変更は何通りあるか。** §7.3 の観測で見分けるための条件(定理7.9)、§7.6 のすべての持ち上げ、§7.7 の操作のつながりによる分類に当たる。

**仕事をどう分け、どう組み立てるか。** §2.5 の障害類の消滅から貼り合わせへ、§5.1 の対応する入力の fiber product、§8.6 の設計変更への適用に当たる。
第8章の「局所」は、有限個の型・値・等式の読み取りを指し、ArchSig の読みの局所とは別のものである。

**次にどこを読むか。** §7.3 の観測で見分けるための条件が、候補を見分ける観測の根拠になる。
`?` による沈黙と、次に読む場所の並べ方は、ツールの側の決まりである。

## ツールの都合で変えた所

- 対象は有限に限る。Atom、要素、局所、候補はどれも有限個である。
- 係数は整数に限る。
- 読みの形は `dir`、`file`、`groups` の三つに限る。
- Law の規則は `no`、`each`、`agrees along`、`changes`、`roundtrips` の五つの形に限る。
- 一致の障害は、要素を頂点、値の流れを辺とする、面を持たない形の上で計算する。どの輪も障害の候補になる。読みの局所は、矛盾が局所の中にあるか、局所をまたぐかの分類に使う。
- 換算は、宣言した `convert` による 10 の冪の掛け算と割り算に限り、指数の整数で表す。
- 直す場所の候補は、遷移(換算)を変える組として求める。本数の少なさで並べるのはツールの定めで、論文の修復とは別のものである。
- フィールドは型ごとに一つの値として扱い、同じ型の別々の実体(二つの注文など)は区別しない。
- 外部の要素の呼び出しは、観測した要素へ書き込まないものとして扱う。
- 操作は、書き込みの列として表す。呼び出しの結果は、`fresh` を除き、同じ操作に同じ値を渡せば同じ結果が返るものとして扱う。
- 条件は、形をそろえたうえで、成り立つ場合と成り立たない場合の二つの分岐として扱い、条件どうしの関係は見ない。そのため、実際には同時に成り立たない条件の組み合わせで反例が出ることがある。反例には入力が満たす条件が付くので、その分岐を通るかは読み手が確かめられる。
- 変更の候補は、要素の分割、削除、追加を含むので、一般には §4.2 の exact な変更ではない。輸送の普遍性や幾何への持ち上げ(§4.1〜4.3)は使わず、可換図式の等式だけを確かめる。
- 経路の比較では、行って戻る変更をそのまま合成して比べる。第6章の正規化は使わない。
- 変更の決め方は、有限の数え上げで求める。§7.1〜7.7 の群による分類は、対応が一対一のときの意味づけと検算に使う。
- 粒度の比較では、Law の値の読み戻し(§3.1)を抜き取りで確かめ、被覆の比較(§3.5〜3.6)を比較写像の核と余核で確かめる。
- 数え上げと展開には上限がある。上限を超えたら、`limit` で沈黙する。

## v0.6.0 で扱わない節

- §2.7 の構造相と意味相の比較。
- §5.2〜5.10 の基底変換による生成比較。§5.1 の fiber product は、候補の組み立てにだけ使う。
- §6.3〜6.8 の冪等完備化と、正規化後の圏。
- §8.1〜8.5 の有限表示と完全幾何の局所再構成。§8.6 の設計変更への適用は、仕事の分け方と組み立ての意味づけに使う。

## 結論が語ること

ArchSig の結論は、ArchMap に記録された Atom の上での計算結果である。
それが実際のコードについて言えるかは、Atom の `at` でソースへたどること、コードが変わったら観測し直すことで確かめる。
計算の結果と、コードとの対応の確認は、別のものとして扱う。

どの結果も、計算が立っている節を `theory` に持つ。
定理の条件を入力の上で確かめたものは `conditions` に並び、確かめられないものがあれば沈黙する。
