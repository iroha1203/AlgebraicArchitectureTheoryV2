# 7. SKILL

ArchSig の入口は、AI エージェントの SKILL である。
人は普段使うエージェントに、目的と制約を伝える。エージェントは SKILL に従って ArchSig を呼び、結果を人に報告する。
ArchSig と一緒に配る SKILL は四つある。

SKILL は、仕事によってモデルを使い分ける。

- 強いモデル:推論の力が大きく、費用も高いモデル。Law を書く仕事と、観測が割れたときに決める仕事に使う。
- 軽いモデル:速く、費用の安いモデル。意味 Atom の観測に使う。観測の量はコードの規模と変更の回数に比例して増えるので、ここを安くする。

## 四つの SKILL

### archsig-law:Law を書く

守りたいことを、Law ファイルにする SKILL だ。

1. 人から、守りたいことを聞く。
2. コードを読み、観測する範囲、読み、意味の語彙、Law を書く。
3. `archsig law check` で、書けているかを確かめる。
4. `archsig law diff` の結果を人に見せ、承認を受ける。
5. `archsig next` で、新しく観測が必要になった所を確かめ、archsig-observe へ渡す。

Law は強いモデルが書く。版をまたいで使う資産なので、書く手間より正しさを優先する。

### archsig-observe:観測する

ArchMap を作り、今のコードに追いつかせる SKILL だ。

1. `archsig status` で、古い範囲と、読んでいない範囲を確かめる。
2. 構造 Atom は、エージェントが選んだ解析器で取り出し、`archsig record` で ArchMap に書く(この章の「構造の観測と解析器」)。
3. 意味 Atom は、`archsig observe task` で観測の仕事を作り、軽いモデルのエージェント二つに別々に渡す。
4. 二つの観測を `archsig observe merge` で突き合わせる。一致しなかった Atom は、強いモデルが元のコードを読んで決める。
5. 解析器が `?` を残した所のうち、フレームワークの配線のように読めば決まる所は、エージェントが解決する。解決した Atom も、二つの観測で記録する。
6. `archsig validate` で、ArchMap が受け付けられるかを確かめる。

観測の仕事には、読むソースと範囲、意味の語彙と観測の手がかり、書き出す Atom の形だけが入る。Law の規則は入らない。
二つの観測者には、互いの結果を見せない。

観測は粗い読みから始める。局所ごとの意味 Atom で観測し、抜き取りで要素ごとにも読む。
`archsig check --reading <粗い読み> --against <細かい読み>` で、粗くては足りない局所が分かったら、そこだけを細かく読む。

### archsig-change:変更を進める

機能の追加や内部構造の変更を進める SKILL だ。第2章で追った流れがこれに当たる。

1. 人から、したいことと、変えたくないことを聞く。
2. 変えたくないことに当たる Law があるかを確かめる。なければ archsig-law へ。
3. archsig-observe で、観測を今のコードに追いつかせる。
4. 変更の候補を書き、`archsig plan check` で検査する。
   沈黙したら、`next` の所を archsig-observe で観測する。反例が出たら、候補を直すか、人に仕様を聞く。
5. 決め方が複数あれば、`archsig plan choices` で数え上げ、絞るための判断を人に聞く。
6. `archsig plan split` で仕事を分け、各担当に局所の候補の名前を渡す。
7. 担当が局所の候補を書き直したら、`archsig plan glue` で組み立て直し、もう一度検査する。
8. 実装後、変わったソースを観測し直し、`archsig compare --plan` で候補と比べる。ビルドとテストも実行する。
9. 人に報告する。

### archsig-review:変更をレビューする

プルリクエストをレビューする SKILL だ。

1. `archsig law diff <変更前のコミット>` で、Law が変わっていないかを確かめる。変わっていれば、報告の最初にそれを置く。
2. 変更前と変更後のコミットで、変わったソースを観測する。
3. 両方で `archsig check` を実行し、`archsig diff` で差分をとる。
4. 新しく成り立たなくなった結果を、ソースの場所とともに報告する。Law の変更で変わった結果は、コードの変更で変わった結果と分けて報告する。
5. プルリクエストに候補が付いていれば、`archsig compare --plan` の結果も報告する。

## エージェントが守ること

ArchSig を呼ぶエージェントも、手間を減らそうとする。Law を弱めれば違反は消え、観測を省けば沈黙で済む。
SKILL は、次の決まりでこれに備える。

- Law を書き換えるのは archsig-law だけである。ほかの SKILL は Law を変えない。違反が出たら、コードか候補を直すか、人に聞く。
- Law の変更は、コードの変更とは別に人がレビューする。`diff` も、Law の変更で変わった結果を分けて返す。
- 沈黙を結論として報告しない。沈黙は数と理由を添えて報告し、`next` の所を観測する。CI では `--require-decided` を付ける。
- 意味 Atom は、二つの観測者で記録する。一人で書いた意味 Atom を、ArchSig は受け付けない。
- 候補には意味 Atom を書かない。変更後の意味は、実装してから観測し直して確かめる。
- 観測するエージェントには、Law の規則を見せない。

## 人への報告

人への報告は、次の順に書く。

1. 問いへの答え。成り立つか、成り立たないか。
2. 成り立たない所。平易な言葉で書き、ソースの場所へのリンクを付ける。
3. 人に決めてほしいこと。仕様の判断、決め方の選択、Law の承認。
4. 沈黙の数と理由。

成り立たない所は、形ごとに次のように書く。

- 反例:「国をまたいで配送先を変えたとき、移行と更新の順番で決済情報が変わる。元は `service.py:4` の書き込み」のように、入力の条件と二つの結果で書く。
- 貼り合わせの障害:「`A` から `B`、`C` を通って `A` に戻ると、金額が 100 倍ずれる。直すならこの三か所のどれか一つ」のように、ずれの倍率と直す場所の候補で書く。
- 経路の食い違い:「`User.name` は、直接移すと `family_name` に、v2 を経由すると `given_name` になる」のように、要素と行き先で書く。
- 仕事の分け方:担当ごとの条件と、担当の間でそろえる対応を並べる。

計算の欄の名前や、Rising Sea の用語は、報告の本文に出さない。

## 構造の観測と解析器

構造 Atom をどの解析器で取り出すかは、SKILL では決めない。実行するエージェントが、リポジトリの言語とフレームワークを見て選ぶ。
構文木を作るライブラリ、言語サーバ、コンパイラや型検査器の出力のうち、そのコードに合うものを使う。
合うものがなければ、エージェントが小さな抽出スクリプトを書いてもよい。
SKILL に書くのは、考え方と手順である。

考え方は次のとおり。

- 構造 Atom には、構文から決まる事実だけを書く。意味は書かない。
- 名前、値、条件は第3章の形に直す。解決できないものは `?` と書き、推測で埋めない。
- 同じコードからは、何度取り出しても同じ Atom が出るようにする。使った解析器と版を `by` に書く。
- 読んだソースは、Atom が一つもなくても読んだ範囲として記録する。

手順は次のとおり。

1. `sources` の範囲のソースについて、言語とフレームワークを確かめ、解析器を選ぶ。
2. 解析器の出力を、第3章の九種類の構造 Atom に直す。
3. `archsig record` で ArchMap に書く。ArchSig は形を検査し、ソースの hash を付けて読んだ範囲を記録する。
4. `?` が多い所を見て、解析器の設定やフレームワークの配線の読み方を足せるなら足し、取り出し直す。
   残った `?` のうち読めば決まる所は、archsig-observe の手順5で解決する。

ArchSig 本体は言語を知らない。受け取るのは第3章の形の Atom だけである。
