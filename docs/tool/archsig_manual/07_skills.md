# 7. SKILL

ArchSig の入口は、AI エージェントの SKILL である。
人は普段使うエージェントに、目的と制約を伝える。エージェントは SKILL に従って ArchSig を呼び、結果を人に報告する。
ArchSig と一緒に配る SKILL は四つある。

Law を書く仕事には、強いモデル(推論の力が大きく、費用も高いモデル)を使う。
意味 Atom の観測には、Sonnet や GPT 6 Luna のような軽いモデル(速く、費用の安いモデル)を使う。
Law はプロジェクトに一度書けば、版をまたいで使い回せる。観測は、コードの規模と変更の回数に比例して増える。だから、増える側を軽いモデルに任せる。

## archsig-law:Law を書く

1. 人から、守りたいことを聞く。
2. コードを読み、観測する範囲、読み、意味の語彙、Law を書く。
3. `archsig law check` で、書けているかを確かめる。
4. 人に Law を見せ、承認を受ける。

## archsig-observe:観測する

1. `archsig status` で、古い範囲と、読んでいない範囲を確かめる。
2. 構造 Atom を取り出し、`archsig record` で ArchMap に書く(次の節)。
3. 意味 Atom は、軽いモデルのエージェントに、意味の語彙と観測の手がかりを渡して観測させ、`archsig record` で ArchMap に書く。

観測が正しいかは、この SKILL が担う。

## archsig-change:変更を進める

第2章で追った流れがこれに当たる。

1. 人から、したいことと、変えたくないことを聞く。
2. 変えたくないことに当たる Law があるかを確かめる。なければ archsig-law へ。
3. archsig-observe で、観測を今のコードに追いつかせる。
4. 変更の候補を書き、`archsig plan check` で検査する。
   沈黙したら `next` の所を観測する。反例が出たら、候補を直すか、人に仕様を聞く。
5. `archsig plan split` で仕事を分け、各担当に条件を渡す。
6. 実装後、変わったソースを観測し直し、`archsig compare --plan` で候補と比べる。
7. 人に報告する。

## archsig-review:変更をレビューする

1. 変更前と変更後のコミットで、変わったソースを観測する。
2. 両方で `archsig check` を実行し、`archsig diff` で差分をとる。
3. 新しく成り立たなくなった結果を、ソースの場所とともに報告する。

## 構造の観測と解析器

構造 Atom をどの解析器で取り出すかは、SKILL では決めない。実行するエージェントが、リポジトリの言語とフレームワークを見て選ぶ。
構文木を作るライブラリ、言語サーバ、コンパイラや型検査器の出力のうち、そのコードに合うものを使う。合うものがなければ、小さな抽出スクリプトを書いてもよい。

- 構造 Atom には、構文から決まる事実だけを書く。意味は書かない。
- 名前、値、条件は第3章の形に直す。解決できないものは `?` と書く。
- 呼び出し先や型の名前を解決できたら、定義したソースか外部かを `resolves` で書く。
- 戻り値の式の中の呼び出しは、`calls` と `passes` を `returns` より前に書き、`returns` の `at` は return 文の最後の行にする(第3章の `returns`)。
- 使った解析器と版を `by` に書く。

ArchSig 本体は言語を知らない。受け取るのは第3章の形の Atom だけである。
