# ArchSig v0.6.0 設計

この文書は、ArchSig v0.6.0 の内部の作りを定める。
何を入力に何を計算し何を返すかは [マニュアル](archsig_manual/README.md) にあり、この文書はそれをどう計算するかを書く。
外から見える振る舞いはマニュアルを正とする。この文書で決めた振る舞いのうち外から見えるものは、マニュアルにも書く。

中心は三つある。ArchMap を読んで作る構造、Law DSL、その上で問いを計算するエンジンである。

## 1. 全体の流れ

```text
ArchMap(.archsig/map, local)  候補(.archsig/plans)  Law ファイル(.archsig/law)
        │                      │                      │
        ▼                      ▼                      ▼
     Atom の列 ──重ねる──▶ Atom の列               Law の構文木
        │                                             │ 名前を解決する
        ▼                                             ▼
     構造(Structure) ◀─────── 読み ─────────── 解決した Law
        │  局所と重なり(Geometry)
        ▼
     エンジン: 選択 / 値の流れ / 操作の実行 / 対応
        │
        ▼
     結果(Finding)──▶ .archsig/runs/<実行>/
```

- 入力の層は、ファイルを読んで Atom の列と Law の構文木を作る。
- 構造の層は、Atom の列から要素、関係、操作、意味、読んだ範囲をまとめる。読みには依存しない。
- 幾何の層は、構造と一つの読みから、局所と重なりを作る。
- エンジンは、構造と幾何と解決した Law から結果を計算する。エンジンが入力のファイルを直接読むことはない。
- 結果の層は、結論ごとに根拠、検算データ、成り立つ条件、次に読む所をまとめ、実行として保存する。

どの層も、同じ入力から同じ結果を返す。集合と写像は名前の順に並べ、実行の順に依らない出力を作る。

## 2. 言語を知らない境界

計算の中核は、プログラミング言語を知らない。中核が受け取るのは、マニュアル第3章の形の Atom だけである。

中核は次のことをしない。

- ソースコードを読む。
- 要素の名前から、それを定義したソースのパスを推す。
- モジュールの名前とファイルの対応を仮定する。
- 標準ライブラリや外部パッケージの名前を知っている前提で動く。

これらはどれも言語の知識で、解析器と、観測する SKILL の側にある。
中核が要素とソースを結びつけるのは、Atom に書かれた `at`、`file`、`resolves` だけである(3.3)。定義も `resolves` も持たない要素で、名前が `<頭>.<名前>` の形のものは、頭の Atom のそれで結びつける(4.4、6)。

## 3. ArchMap と構造

### 3.1 保存

- ArchMap は、ソースのファイルごとに `.archsig/map/<ソースのパス>.jsonl` に置く。
- 一つのファイルには、そのソースの `observed` と、そのソースで観測した Atom が入る。
- `archsig record` は、入力の Atom をソースと観測の範囲(`structure` か `meaning:<名前>`)でまとめ、その組の元の Atom をすべて置き換える。
  - `at`、`uses`、`observed` の `subject`、外部を指さない `resolves` の `object`、`--drop` のパスは、リポジトリの根からの相対パスにそろえる。`./` と空の区切りは落とし、`..` はたどる。根の外を指すパスは書かない。局所ごとの意味 Atom の局所の名前も同じくそろえる。
  - `at` と `uses` に版がなければ、今のソースの版を補う。
  - `observed` は、`subject` のソースに置き、`at` をそのソースと版にそろえる。
  - 補う `observed` の版は、組の Atom の版がそろっていればその版とする。そろっていなければ今の版と違う版で補い、その範囲を古いとみなす。
  - 局所ごとの意味 Atom は、ソースの代わりに局所の名前ごとに置き換え、ソースのファイルとぶつからないように `.archsig/local/<読み>/<局所>.jsonl` に置く。`at` に版を補わず、`observed` も補わない。古いかは `uses` で決まる。
  - その組の `observed` がなければ補う。読んだが Atom がなかった範囲は、`observed` だけを渡して記録する。
- 版は、ソースの中身の git blob hash である。`at` の最後の `@` の後ろが `blob:<hex>` か 7 文字以上の `<hex>` のときだけ版と読み、パスの中の `@` と区別する。7文字以上の前方一致で、大文字と小文字を区別せずに同じ版とみなす。
- 消えたソースは `archsig record --drop <ソース>` で、そのソースのファイルごと ArchMap から外す。

### 3.2 構造を作る

構造は、Atom の列から次を作る。読みには依存しない。

| 構造 | 中身 | 元の Atom |
| --- | --- | --- |
| 要素 | 名前、種類、操作の引数と型、フィールドの型 | `defines` と、`params` から作る引数 |
| 関係 | 呼び出し、読み、書き込み、引数渡し、送受信、戻り値、取り込み | 同名の構造 Atom |
| 操作の本体 | 操作ごとの手順の列(3.4) | `writes`、`calls`、`sends`、`returns` |
| 解決 | 名前と、それを定義したソースか外部 | `resolves` |
| 意味 | 要素ごとの意味と値、使用箇所 | `meaning` |
| 読んだ範囲 | ソースと範囲の組 | `observed` |

- 構造は、Atom の出現をすべて持つ。同一性(マニュアル第3章)で重複を除かない。
  一つの操作の中で同じ Atom が二度出れば、それは二つの手順である(`g(0); g(1)` の二つの `calls`、`x=0; x=1; x=0` の二つの `x=0`)。
- 同一性は、二つの Atom の列を比べるときに使う(`compare --plan`、`diff`)。比べるときは、同一性ごとの出現の数も比べる。
- 読んだ範囲の版は、`status` が古さを返すのに使う。計算は、与えた ArchMap の読んだ範囲を、古いかによらず読んだ範囲として扱う。
- チャネルとその項目は、`sends` と `receives` に現れた名前から要素になる。`:` で四つ以上に分かれる名前は、最後を項目とし、残りをチャネルとする。
- 呼び出しの要素 `<呼び出し元>-><呼び出し先>` は、同じ組の `calls` を行の順に並べて `#2`、`#3` を付ける。候補の中では Atom の順である。
- 一つの要素に種類の違う `defines` があれば、その要素は曖昧である。`value` のない `defines` を持つ要素と、同じ種類の `defines` を二か所(`at` が違う)以上に持つ要素も、種類か定義が決まらないので同じに扱う。曖昧な要素が関わる計算は `unresolved` で沈黙する。
- 局所ごとの意味 Atom(`local:<読み>:<局所>`)は、その読みの幾何を作るときに、局所の中の対象の要素へ配る。要素ごとの意味 Atom があれば、そちらを使う。

### 3.3 解決と外部

呼び出し先や型の名前が、どのソースで定義されているかは、解析器が知っている。解析器はそれを `resolves` で記録する。

```json
{"kind": "resolves", "subject": "shop.shipping.address.normalize_address",
 "object": "shop/shipping/address.py", "at": "shop/shipping/service.py:2@blob:087942b", "by": "tool:…"}
{"kind": "resolves", "subject": "requests.post", "object": "external:requests",
 "at": "shop/payment/charge.py:1@blob:5e0c1aa", "by": "tool:…"}
```

`object` は、定義したソースのパスか、`external:<パッケージ>` である。構造 Atom の一種で、`at` のソースの `structure` の範囲に入る。

定義を読んでいない要素について、中核は次のように決める。

- `resolves` がソースを指し、そのソースを読んでいない: `unread` で沈黙し、そのソースを次に読む所として返す。
- 問い合わせた要素そのものの `resolves` がソースを指し、そのソースの構造を読んでいるのに定義がない: `unresolved` で沈黙する。
- `resolves` が外部を指す: 外部の要素として扱う(呼び出しは 3.4、型は 5.4)。
- `resolves` がない: `unread` で沈黙し、その要素の名前を次に読む所として返す。どのソースを読むかは SKILL が決める。
- 一つの名前に、指す先(`object`)の違う `resolves` が二つ以上ある: 解決が決まらないので、`unresolved` で沈黙する。指す先が同じ `resolves` の重なりは、一つと同じに扱う。
- 外部の型(`resolves` が外部を指し、定義のない型)のフィールドを読むか書く: そのフィールドが分からないので、`unresolved` で沈黙する。読む所は返さない。

### 3.4 操作の本体

操作の本体は、手順の列である。手順は次の四つで、どれも条件(`when`)を持てる。

- 書き込み: 場所に値を置く。
- 呼び出し: 呼び出し先の本体を、引数を置き換えて展開する。
- 送信: チャネルの項目へ値を送る。
- 戻り値: 値を返す。

手順は、観測した Atom では `at` の行の順、同じ行では Atom の順に並べる。候補の中では Atom の順である。

戻り値の手順の後の手順(同じ本体の中で後に並ぶ手順)は、その戻り値の手順を行わなかった分岐でだけ行う。戻り値の手順の条件は、戻り値の手順の時点の状態で一度だけ読む。条件のない戻り値の手順の後の手順は、どの分岐でも行わない。戻り値は、その手順を持つ本体だけを終え、呼び出し先の戻り値は呼び出し元の手順を止めない。`changes` の計算が比べるのは、フィールドの場所の値である。
操作の本体と、その呼び出し先の本体の、書き込み・送信・戻り値の `value` と、手順の `when` に `?` が一つでもあれば、その操作の展開は沈黙する。

外部の要素の呼び出しは、観測した要素へ書き込まない呼び出しとして扱う。この扱いは、関わる結論の `conditions` に並べる。

### 3.5 値と場所

`value` と `when` の式(マニュアル第3章)は、構文木に直してから計算する。
式は、定数、引数からたどる道、呼び出し、四則演算、比較、`and`・`or`・`not`、括弧、単項の `-` からなる。`$` も `?` も付かない名前は定数である。構文として読めない式は `?` と同じに扱う。式の読みは再帰で下るので、字句に分けた式の字句の数が上限を超えれば、構文として読めるかや `?` を含むかを確かめる前に、値を求めずに `limit` で沈黙する。その式の中で名指す道、名前、呼び出しは、字句から再帰せずに拾い、型のフィールドをたどるときの名指しに数える。構文として読めるかを確かめていないので、消える要素を使うかの判定(3.6 の `missing` の元)では、`limit` で沈黙する。読む所は付けない。

フィールドの値は「場所」に置く。場所は、フィールドの要素の列である。

- `$p.f` は、引数 `p` の型 `T` のフィールド `T.f` を先頭とする場所 `[T.f]` を読む。
- `$p.f.g` は、場所 `[T.f, U.g]` を読む。`U` は `T.f` の型である。
- 書き込みの場所は `[via…, object]` である。`via` は書き込み先までにたどるフィールドの列で、なければ場所は `[object]` である。`via` と `object` のフィールドは、どれも種類を構造の三値の問い合わせで確かめ、定義を読んでいなければ沈黙する。
- 場所を読むとき、その場所の頭の部分に書き込みがあれば、書き込んだ値からの残りの射影を返す。なければ、その場所の入力の値を返す。
- その場所の先(`via` を通った書き込みの場所)に書き込みがあれば、その場所の値は決めていないので、`unchecked` で沈黙する。

引数は、その型のただ一つの実体を指す。同じ型の別々の実体(二つの注文)は区別しない。
これはマニュアル第6章の単純化「フィールドは型ごとに一つの値として扱う」に当たる。
引数そのもの(`$order_id`)は、呼び出しで渡された値に置き換える。渡す値は、呼び出しの時点の状態で読む。渡されていなければ、その引数の記号である。
外部でない呼び出しの `passes` の受け取る引数が、呼び出し先の引数(`<呼び出し先>.$<名前>` で、`params` にある名前)になければ、その呼び出しを展開する操作は `unresolved` で沈黙し、呼び出しの場所を返す。
`when` のない `passes` と、呼び出しの `calls` と同じ `when` を持つ `passes` は、呼び出しの条件で渡す値である。`passes` に呼び出しと違う `when` があるか、一つの引数に値の違う `passes` が二つ以上あれば、渡す値が一つに決まらないので、その呼び出しを展開する操作は `unresolved` で沈黙する。

### 3.6 候補を重ねる

候補(マニュアル第3章)は、ArchMap の Atom の列に重ねて、変更後の Atom の列を作る。

1. 候補が `subject` に構造 Atom を書いた要素は、元の Atom をすべて外す。`<要素>->…` の呼び出しの Atom も外す。
   `resolves` は、`subject` が参照先の名前なので、置き換える要素を決めない。候補の `resolves` は、その名前の解決として加える。
2. `removes` した要素 `X` と、`X.…`、`X->…`、`X.$…` の名前の要素の Atom を外す。
3. 候補の構造 Atom を加える。
4. `corresponds` の行き先へ、元の要素の意味 Atom を移す。

対応は次の順に作る。

1. `corresponds` に書いた対応。行き先に `|` があれば、決めていない対応として別に持つ。
2. 書いた対応で結んだ操作どうしの、同じ名前の引数。持ち主の操作か対応の行き先の操作の種類が決まらなければ(曖昧、`value` のない `defines`、定義を読んでいない)、同じ名前の引数があるかが決まらないので、引数の対応があるかも決まらない(5.1)。
3. 変更前と変更後の両方にある同じ名前の要素は、自分自身に対応する。

候補を重ねる処理は、Atom から決まる事実だけを返す。変更後の Atom の列、対応、決めていない対応、書き直していない Atom が `removes` した要素を名指す操作(`missing` の元)である。
ここで操作の Atom が名指す要素は、操作の引数の型、構造 Atom の `object` と `writes` の `via` のフィールド(`via` を通る `writes` の `via` と `object` は、最初のフィールド `T.f` から、残りのフィールドの名前(最後の `.` の後)を変更後の構造で前のフィールドの型でたどった道のフィールド。`?` の名前の先は名指す要素が決まらない)、`value` と `when` の式の中でたどるフィールドと呼び出す操作である。
書き直していない Atom は変更後にも残るので、式の中の道は変更後の構造でたどる(候補がフィールドの型を書き換えれば、書き換えた型のフィールドを名指す)。`?` の型の先は名指す要素が決まらないので、たどれなかった所とし、読む所は道の上でその型を持つ要素(フィールドか、引数を持つ操作)の定義の場所とする。候補が定義し直した型で、変更前の構造が名指していて定義を読んでいなかったもの(変更前に `resolves` が外部を指していた型を除く)も、元のフィールドが分からないので、直下のフィールドの名前(`<型>.<名前>`)だけを数えてその先をたどらず、変更前の構造で定義を読んでいない要素として沈黙する(5.4 の型と同じ)。変更前に `resolves` が外部を指していた型は、ここでは候補の定義でたどる(5.4 では外部の型として、その先をたどらない)。たどれなかった所の沈黙と読む所も、変更後の構造で問い合わせる。
どれを `missing` と結論し、どこで沈黙するかは、エンジンが構造の三値の問い合わせで決める(5.1)。

## 4. Law DSL

### 4.1 字句と宣言

- 一行が一つの文である。字下げした行は、上の字下げしていない宣言に属する。
- `#` から行末はコメントである。`"…"` の中の `#` は文字である。
- 語は、文字、数字、`_`、`.`、`^`、`-` からなる。`->` は記号である。
- 記号は `,`、`|`、`=`、`(`、`)`、`:`、`*`、`/`、`->` である。

```text
file        := decl*
decl        := sources | reading | fresh | meaning | law | def | include
sources     := "sources" patterns (INDENT "except" patterns)?
reading     := "reading" NAME "=" ( "dir" "(" "depth" ":" INT ")" | "file"
                                  | "groups" (INDENT NAME ":" patterns)+ )
fresh       := "fresh" patterns
meaning     := "meaning" NAME "on" kind ("," kind)* ("to" STRING)?
               (INDENT "values" NAME ("|" NAME)*)? INDENT STRING
law         := "law" NAME INDENT STRING (INDENT "on" NAME)? (INDENT "about" NAME)? INDENT rule
def         := "def" NAME "=" selector
include     := "include" STRING
patterns    := STRING ("," STRING)*
kind        := "operation" | "type" | "field" | "param" | "call" | "channel"
```

### 4.2 規則

```text
rule        := "no" selector
             | "each" selector INDENT cond+
             | "agrees" "along" "flows" (INDENT "convert" NAME "->" NAME "by" ("*"|"/") INT)*
             | "changes" "commute" "with" "operations"
             | "changes" "keep"
             | "roundtrips" "read" STRING "update" STRING
selector    := base ("that" cond+)?
base        := kind ("to" STRING)? STRING? | STRING | NAME
cond        := "and"? ( rel base | "has" NAME NAME? | "inside" STRING | "outside" STRING )
rel         := "writes" | "reads" | "calls" | "sends" | "receives" | "reaches"
```

- `base` の `NAME` は、意味の語彙の名前か `def` の名前である。どちらかは、ファイルをすべて読んでから決める。
- `and` は省いてよい。条件の語が次の条件の始まりになる。
- `has <意味>` の次の語は、条件の語(`rel` の語、`has`、`inside`、`outside`、`and`、`that`、`to`)でなければ値として読む。条件の語と同じ値は `has` に書けない。
- 読み方を保証するのは、この文法の形で書いた入力である。字句と文法の読み取りは、これより緩い入力(区切りの `,` の省略、行の順の入れ替えなど)も受け付けることがある。
- `def` の中で `def` は使えない。

### 4.3 解決

Law ファイルを読んだら、名前を解決して、計算に使う形にする。解決で失敗したら、`law check` が理由と行を返す。

- `about`、`has`、`base` の意味の名前が、語彙にある。`has` の値が、その語彙の `values` にある。`values` のない語彙の `has` には値を書かない。
- `convert` の二つの値が、`about` の語彙の `values` にある。倍率は 10 以上の 10 の冪(`10`、`100`、…)である。
- 読み、意味、`def`、Law の名前は、それぞれ一度だけ宣言する。`def` に意味の語彙と同じ名前は付けない。
- `sources`、`except`、`fresh`、`groups` のパターンが、パターンとして読める。
- `on` の読みが宣言されている。Law が `on` を省けば、最初に宣言した読みを使う。読みが一つも宣言されていなければ、その Law を誤りとする。
- `agrees`、`changes`、`roundtrips` の規則は `about` を持つ。
- `def` を展開する。
- `include` は、取り込む側のファイルの場所から読み、一つのファイルを二度読まない。
- `sources` と `fresh` は、読んだファイルすべての和をとる。
- 字句や文法で解けない宣言と、解決の誤りは、ファイルと行とともに誤りとして返す。パターンが読めるかと `convert` の倍率は、宣言を読むときに確かめ、字句や文法の誤りと同じ所に並べる。
- 宣言を読むときに誤りになった宣言(字句や文法、パターン、倍率)の名前は、宣言されていないものとして扱う。その名前を使う側にも、宣言されていないという誤りが出る。
- `include` のパスを `..` でそろえてリポジトリの根を越えるか、根そのものになれば、誤りとする。パスは字面だけでそろえる。
- 誤りが一つでもあれば、Law は計算に使えない。計算する問いは、計算せずに Law の誤りを返す。エンジンが受け取るのは、誤りのない Law だけである。
- `status` は、Law に誤りがあっても、解けた `sources` と意味の語彙で動き、Law の誤りを `law_errors` に返す。

### 4.4 選択の意味

選択(`selector`)は、構造の要素の上の述語である。値は三つある。当てはまる、当てはまらない、分からない。
分からないときは、何を読めば決まるかを一緒に持つ。

| 条件 | 当てはまる | 当てはまらない | 分からない |
| --- | --- | --- | --- |
| 種類、名前のパターン、`to` | 構造の上で決まる | 構造の上で決まる | 名前が `?` で始まる |
| `writes`、`reads`、`calls`、`sends`、`receives` | その関係の Atom がある | 要素のソースの `structure` を読んでいて、Atom がない | ソースを読んでいない |
| `reaches` | 呼び出しをたどって着く | たどれる先をすべて読んでいて、着かない | 途中に読んでいない呼び出し先がある |
| `has <意味> <値>` | その意味 Atom がある | ソースの `meaning:<意味>` を読んでいて、Atom がないか値が違う | ソースのその意味を読んでいない |
| `inside`、`outside` | 要素の局所で決まる | 要素の局所で決まる | 要素がどの局所にも属さない |

`and` は三値の「かつ」である。
要素のソースは、定義したソースである。呼び出しの要素では呼び出し元のソース、引数では持ち主の操作のソース、チャネルではそこへ送る操作と受け取る操作のソースすべてである。定義も `resolves` も持たない要素で、名前が `<頭>.<名前>` の形のもの(型のフィールドやメソッド)は、頭の定義を観測していれば頭のソースで見る。

## 5. エンジン

エンジンは四つある。どの問いも、このどれかの上で計算する。

### 5.1 三値と沈黙

エンジンの問い合わせは、どれも三値で返る。分からないときは、理由(`unread`、`unresolved`、`unchecked`、`limit`)と、何を読めば決まるかを持つ。

- 「ない」ことは、その範囲を読んでいるときだけ言える。エンジンは Atom の不在を、読んだ範囲と合わせて問い合わせる。Atom の列を直接見て不在を結論しない。
- 分からない問い合わせが結論に関わるとき、その結論は沈黙になる。何を読めば決まるかは、結果の `next` になる。
- 数え上げと展開には上限がある。上限は定数で持ち、超えたら `limit` で沈黙する。

### 5.2 選択エンジン

`no` と `each` を計算する。

- `no S`: `S` に当てはまる要素がそれぞれ違反になる。分からない要素は沈黙になる。
  当てはまる要素も分からない要素もなく、`sources` のソースをすべて、構造と、規則が使う意味の範囲で読んでいれば、成り立つ。読んでいない範囲があれば、`unread` で沈黙する。
- `each S C`: `S` に当てはまる要素ごとに `C` を計算する。当てはまらなければ違反、分からなければ沈黙になる。

### 5.3 値の流れのエンジン

`agrees along` を計算する。

1. 要素を頂点、値の流れを辺とするグラフを作る。辺は換算の整数を持つ(マニュアル第5章 問い2)。値の要素は、場所の最後のフィールドである。
2. 意味の値を読んだ要素は、仮の頂点「基準」への辺で結び、値に当たる整数を換算とする。
3. 局所ごとに、その局所に属する辺だけで割り当てを求める。重み付きの union-find で各頂点に整数を割り当て、食い違う辺が出たら、その局所の中の木の道とその辺でできる輪を `violation` として返す。輪の辺はすべてその局所に属する。
4. どの局所にも `violation` がなければ、すべての辺で同じように割り当てを求める。食い違う辺が出たら、その輪を `obstruction` として返す。局所ごとには割り当てができるので、この輪はどの一つの局所にも収まらない。
5. `violation` がある局所があれば、`obstruction` の判定は前提(局所ごとに割り当てができること)を満たさないので、`unchecked` で沈黙する。
6. 基準を通る輪は、観測した値の間の道として返す。
7. 直す場所の候補は、換算を変える辺の組を、本数の少ない順に上限まで数え上げ、すべての輪の和が 0 になるものを返す。

検算データは、輪の辺の列、向き、換算、和である。

### 5.4 操作の実行のエンジン

`changes`、`roundtrips`、経路の比較を計算する。操作を書き込みの列として記号的に実行する。

- 状態は、場所から値への写像である。値は項で、定数、場所の入力、引数の記号、射影、呼び出し、`fresh` の呼び出し、演算からなる。
- 二つの順番の値を比べるとき、定数は字句で比べる。字句が同じ定数は同じ項、字句が違う定数は違う値である。名前の定数の値と数の書き方は知らないので、同じ値を同じ字句で書くのは観測する側である(マニュアル第3章)。
- 呼び出しの値は、同じ呼び出し先に同じ項を渡せば同じ項である。`fresh` の操作の呼び出しは、呼び出しの場所ごとに別の項である。
- ただし、変更前と変更後で呼び出し先の本体が違えば、同じ項とみなせない。本体は、呼び出し先とそこから呼ぶ操作(`calls` の `object` と、`value`・`when` の式の中の呼び出し。たどった先がさらに呼ぶ操作も含む)の構造 Atom(定義と解決を除く)で、Atom の種類、`object`、`via`、`value`、`when` と、呼び出しの Atom ではどの呼び出しか(`<操作>->` から後の名前)で比べる(呼び出し先の名前の違いは見ない)。定義のある操作は、定義の引数の名前と型も比べ、定義のない操作は、その解決(3.3。指す先が同じ重なりは一つ)を比べ、解決が決まらなければ(指す先が違う `resolves`)本体が違うとする。`?` が関わる Atom(`?` の値、`?` で始まる名前、道のフィールド、引数の名前と型)、構文として読めない式、字句の数が上限を超えた式(3.5)があれば、入力から本体が決まらないので、本体が違うとする。手順(書き込み、呼び出し、送信、戻り値)は手順の順で比べ、ほかの Atom は順によらない。変更後の呼び出し先は対応の行き先で、行き先が二つ以上なら、どれか一つでも本体が違えば違うとする。行き先がなければ同じ名前である。本体の違う呼び出し先の呼び出しを値に含む比べる場所は比べず、`unchecked` の沈黙を持つ(反例が出なければ沈黙として返す)。条件に含めば、分岐の組み方が決まらないので、その場で `unchecked` で沈黙する。
- 項は形をそろえる。可換な演算は項を並べ替える。場所の入力の射影は、長い場所の入力にまとめる。
- 条件は、形をそろえた原子と真偽の組の「かつ」に直す。`a != b` は `a == b` の否定、`a > b` は `b < a` にする。`or` でつないだ条件と、`not` の中の `and` は一つの原子である。二重の否定は外してから分ける。条件どうしの関係は見ない。
- 実行は、未割り当ての原子に出会うたびに、真と偽の二つの分岐に分ける。分岐は、原子への真偽の割り当て、状態、書き込みの記録を持つ。
- 呼び出しは、呼び出しの時点の状態で `passes` の値を読んで引数を置き換え、展開する。呼び出しの条件は、呼び出しの時点の状態で一度だけ読む。呼び出し先の手順は、その呼び出しが行われた分岐でだけ行う。
- 再帰と、深さと展開した手順の数の上限は、`limit` で沈黙する。手順の数は、呼び出しを展開する前にだけ、それまでに並べた手順で数える。
- 書き込み、条件、渡す値で作る値の項の節の数が上限を超えれば、`limit` で沈黙する。項の節の数は、再帰せずに数え、上限に達したら数えるのをやめる。形をそろえる前と後の両方で数える。

`changes commute with operations` は、対応する操作の組ごとに次の二つを実行して比べる。

- 変更前の構造で変更前の操作を実行し、その後に対応で場所を写す。
- 対応で写した入力から、変更後の構造で変更後の操作を実行する。

名前は、対応で変更前の名前にそろえてから比べる。一対一で対応するフィールドの場所は、変更前の名前で置く。
二つの実行の分岐の組のうち、割り当てが矛盾しないものを一つの分岐とみなし、`about` の意味を持つ場所の最後の値を比べる。
比べる場所は、次の場所のうち、最後のフィールドが `about` の意味を持つものである。

- `about` の意味を持つフィールドの場所。
- どちらかの順番の書き込みの場所と、その頭の部分の場所(`via` のフィールドまでの場所)。
- 書き込みの場所の最後のフィールドの型から、フィールドの型をたどって作る、書き込みの場所より長い場所。変更後の実行の書き込みは変更後の構造でたどる。変更前の実行の書き込みは、変更前の構造でたどって対応で変更後の名前に写した場所と、対応で写した書き込みの場所から変更後の構造でたどった場所の、両方を使う。

これらのフィールドが意味を持つかが読んだ範囲から決まらなければ、`unread` で沈黙する。候補が定義したフィールドの意味は、3.6 の4で対応の元の要素から移したものなので、元の要素が意味を持つかが変更前の読んだ範囲から決まるときだけ決まる。
型のフィールドは、`<型>.<フィールド>` の名前を持つ、定義を読んだフィールドである。構造が `<型>.<名前>` を名指しているのに(式の中でたどる名前を含む)定義を読んでいなければ、そのフィールドは 3.3 の定義を読んでいない要素として沈黙する。候補が `removes` した要素は、名指されていても、この沈黙の対象にしない。たどる型は次のように扱う。

- 定義を読んだ型は、そのフィールドをたどる。ただし、候補が定義し直した型で、変更前の構造がその型を名指していて(Atom の名前と `value`・`when` の式、要素の型と引数の型、`resolves` のどこかで)定義を読んでいなければ、変更前の構造で 3.3 の定義を読んでいない要素として沈黙する(候補が書き直すのは型の要素の Atom だけで、元のフィールドは分からない)。変更前に `resolves` が外部を指していた型は、外部の型として扱う。変更前が名指していない型は、候補が新しく定義した型である。
- 型のないフィールドは、その先が決まらないので、`unresolved` で沈黙する(道を読むときと同じ)。
- `?` の型、曖昧な型(3.2)、型でない要素は、`unresolved` で沈黙する。`?` の型では、その型を書いたフィールドの `defines` の場所を返す。
- 定義を読んでいない型は、3.3 の定義を読んでいない要素として沈黙する。
- `resolves` が外部を指す型は、外部の要素としてたどらず、意味を持つフィールドを持たないとみなす。この単純化は、関わる結論の `conditions` に並べる。

型がめぐり、その先に意味を持つフィールドがあれば、場所が限りなく伸びるので、`limit` で沈黙する。一つの書き込みの場所からたどったフィールドの数が上限(展開の上限と同じ定数)を超えたときも、`limit` で沈黙する。めぐりの先に意味を持つフィールドがあるかを確かめるたどりは、この数に入れない。
型をたどる所の沈黙(変更前の構造でたどって写した場所の沈黙を含む)は、比べる場所のどこかで反例が決まれば結論に関わらないので、反例を返す。沈黙したフィールドの先だけをたどらず、同じ書き込みからたどったほかの場所は比べる。反例が出ないときに沈黙として返す。
書き込みの場所と頭の部分の場所で最後のフィールドが意味を持つかが決まらない沈黙と、比べる場所の値を読む所の沈黙(その場所の先に書き込みがあって値を決めていない `unchecked` など)も同じに扱う。その場所は比べず、反例が出なければ沈黙として返す。意味 Atom を持つフィールドでも、意味を持つかが読んだ範囲から決まらなければ(候補が定義したフィールドで、元の要素を読んでいないときを含む)、その場所は比べない。操作を実行する所の沈黙と、分岐の組を作る所の沈黙(変更後の条件を変更前の名前にそろえられない)は、比べる分岐が決まらないので、その場で沈黙する。

### 5.5 対応のエンジン

変更の候補と経路を計算する。

- 対応は、変更前の要素から変更後の要素への関係で、行き先が一つとは限らない。
- 経路は、候補の対応を順につないで作る。つないだ対応の上で、終点の操作を 5.4 の実行で比べる。
- 決めていない対応(`|`)は、行き先の組み合わせを数え上げ、組み合わせごとに 5.4 を計算する。同じ Law の計算に関わらない `|` どうしは、別々に数える。

## 6. 幾何

- 読みは、ソースのパスを局所の名前に写す(マニュアル第4章)。
- 要素の局所は、それを定義したソースの局所である。候補の中で新しく定義した要素は `file` の局所である。定義も `resolves` も持たない要素で、名前が `<頭>.<名前>` の形のもの(型のフィールドやメソッド)は、頭の定義を観測していれば頭の局所である(頭の局所が決まらなければ、その要素の局所も決まらない)。
- チャネルとその項目は、送る操作と受け取る操作の局所すべてに属する。
- Atom は、名指す要素の局所すべてに属する。名指す要素は、`subject`、`object`(`|` で並べた行き先はそれぞれ)、`writes` の `via` のフィールドである。二つの局所がともに持つ Atom が重なりである。
- 読み A が読み B より細かいとは、`sources` のどのソースについても、A の局所が B の局所の一つに収まることである。ソースごとの局所の対応から決める。

## 7. 各問いの計算

| 問い(マニュアル第5章) | エンジン |
| --- | --- |
| 1. Law を守っているか | 選択(5.2) |
| 2. 全体で貼り合うか | 値の流れ(5.3) |
| 3. 変更の後も保たれるか | 候補を重ねる(3.6)、操作の実行(5.4) |
| 4. 経路や順序で結果が変わるか | 対応(5.5)、操作の実行(5.4) |
| 5. 粒度を変えても診断は変わらないか | 幾何(6)、値の流れ(5.3) |
| 6. 条件を満たす変更は何通りあるか | 対応(5.5)、操作の実行(5.4) |
| 7. 仕事をどう分け、どう組み立てるか | 幾何(6)、候補を重ねる(3.6) |
| 8. 次にどこを読むか | 各エンジンの沈黙の `next` を集める |

問いごとの細部は、その問いを実装する PRD で決め、決めたことをこの文書とマニュアルに書く。

## 8. 結果

- 結論は、問い、Law、対象、結果(`holds`、`fails`、`silent`)、形、理由、場所、根拠、検算データ、成り立つ条件、Rising Sea の節、次に読む所を持つ。
- 実行は `.archsig/runs/r-<番号>/` に、サマリ `summary.json` と結論ごとの詳細 `<番号>.json` を置く。
- 検算データは、結論の種類ごとに決まった形を持つ。`verify` は、エンジンを使わずに、その形の算術だけで結論を確かめる。

## 9. 実装の単位

Rust のクレート一つで、層ごとにモジュールを分ける。

| モジュール | 層 |
| --- | --- |
| `atom`、`expr` | Atom の形、値と条件の式 |
| `archmap` | ArchMap と候補の読み書き、`record`、版 |
| `law` | Law DSL の字句、構文、解決 |
| `structure` | 構造(3.2〜3.6) |
| `geometry` | 幾何(6) |
| `engine::select`、`engine::flow`、`engine::exec`、`engine::corr` | エンジン(5.2〜5.5) |
| `result` | 結果、実行、`show`、`verify` |
| `cli` | コマンド |

エンジンは、構造、幾何、解決した Law だけを受け取る。ファイルや git に触るのは `archmap` と `cli` だけである。
