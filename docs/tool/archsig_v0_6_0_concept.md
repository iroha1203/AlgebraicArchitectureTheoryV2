# ArchSig v0.6.0 製品コンセプト

## ソフトウェアアーキテクチャを、人とAIが計算できる共通構造にする

この文書は、ArchSig v0.6.0で目指す製品像と設計原則を定める。

**ArchSigは、コードから読み取れるソフトウェアの構造と意味をAATの統一された構造として扱い、その上で理解・設計・変更・検証をつなぐ、AIネイティブなアーキテクチャ計算基盤である。**

目標は、**AI駆動開発における仕事の単位と、成果を積み上げる方法を変えること**である。

## 1. 中心思想――問題が現れる共通構造を解析する

Rising Seaは、局所整合性、診断、輸送、比較、再構成を、同じ入力から構成した共通の対象についての数学的体系として接続している。先行する構成の出力が、次の構成の入力になる。

ArchSigはこの統一性を製品の中心に置き、理解、診断、変更、修復を共通構造に対する異なる問いとして扱う。同じ対象についての計算を接続し、局所の成果を全体の構成へつなぐ。

**ArchSigは、問いに必要な情報、変更が守るべき条件、局所の成果を統合する条件を計算し、人とAIの次の作業を導く。**

## 2. 製品の本体――対象・操作・対応を保持する

ArchSigは、選択した読みの下での対象、操作、Law、局所同士の重なり、対象間の対応とその保存条件を保持する。

Rising Seaでは、Atomから対象を構成し、許された操作に閉じた対象族を持つcoreを生成して、被覆・重なり・係数を備えた幾何へ進む。ArchSigも、この構成と対象間の射を一体として扱う。

### 本物の計算――LawとAtomから結果を導出する

**ArchSigは、事前に定義されたLawと観測されたAtomから本物の計算を行い、結果を出力する。** 人やAIが外部で用意した結論相当のデータを入力へ注入することは認めない。

たとえば、不整合があるという判定をAtomに書くのではなく、観測した値や関係を記録し、選択したLawに照らしてArchSigが不整合を計算する。

### 計算結果を次の計算へ渡す

対象、対応、障害、判定などの計算結果に、関係する対象と導出に用いたLaw・Atomへの参照、計算過程、利用条件を結びつけ、次の計算へ引き継ぐ。

**解析器間の接続を、LLMによる文章の解釈に委ねない。**

### 変更候補を扱い、具体的な反例を返す

設計・変更・表現の候補を現状と同じ体系で扱い、実装前に成立条件や両立可能性を調べる。未確認の条件を持つ候補と、成立済みの射を区別する。

観測モデル上で操作の保存条件が破れる場合は、反例となる入力・操作・結果と、元のソースへの対応を返す。たとえば、注文データの型分割で、配送先の更新と移行の順序によって、引き継ぐ決済情報が異なる具体例を示す。

### 変更の順序と経路を扱う

APIの直接移行と中間版を経由する移行のように、変更の合成を計算して、経路や順序による結果と操作の対応を比較する。すべての経路条件を同時に満たす変換を求め、食い違いがあれば関係する変換と条件を示す。

### 異なる読みと、その対応を扱う

読み方、Law、観測粒度の違いを明示し、その間の対応を構成・比較する。

観測済みの構造を小さくまとめる際は、選んだLawの評価と診断の保存をそれぞれ確認する。元の構造とソースへの対応を保持したまま、SKILLが扱う情報量と再読込みを減らす。

## 3. 実コードとの接続――ArchMapとLawPolicyによる抽象化

### コードから読み取れる情報を対象にする

観測するのは、実装コードから読み取れる操作、データ、依存関係、呼び出し関係と、その使用の文脈である。

**テストコードは観測対象から除外する。** テスト用の呼び出しや検証処理が、実装の構造や意味Atomの観測にノイズを加えるためである。

**ランタイムで起きる問題はAATの対象外である。** 実行時のレースコンディション、I/Oの成否・遅延、パフォーマンスは、ArchSig v0.6.0の診断対象にも含めない。

コードに記述されたI/O操作の役割や依存関係は、構造として読み取る。実行時の挙動や品質は、テスト、動的解析、監視、プロファイリングなどで別途確認する。

### 意味Atomの観測――意味は使用によって決まる

意味Atomの観測では、後期ウィトゲンシュタイン哲学を踏まえ、**意味は具体的な文脈での使用によって決まる**という原則を用いる。

操作やデータの意味を名前や型だけで固定せず、呼び出し元、前後の処理、状態更新、他の操作との関係から読み取る。同じメール送信でも、本人確認、注文受付の通知、障害通知では役割が異なる。この使用の文脈をソース参照とともにArchMapへ記録する。

### ソースコードをSource of truthとする

**現状の実装についてのSource of truthは、ソースコードである。** ArchMapと計算対象を実装コードから導出し、ソース参照と観測時点の版を保持する。コードの変更後は再観測・再計算して同期させ、古い結果を現状のものとして扱わない。

### 観測とLawを共通の計算構造へ接続する

ArchMapは、観測したAtomをソース参照とともに記録する。Context・Cover・重なりは、記録したAtomからArchSigが導出する。LawPolicyはLawと適用・評価条件を定義し、観測と分離する。入力の責務は[Tooling guideline](guideline.md#責務範囲入力トライアドの正本)に従う。

```text
実装コード・仕様・開発上の文脈
                ↕ 観測・解釈・実装への対応
        ArchMap ＋ LawPolicy
                ↕ 構成・読み出し
        AATの統一された計算構造
```

計算結果は、この対応を通して実際のソースと要求へ戻す。

### LawをDSLで定義する

**LawPolicyでは、DSL（ドメイン固有言語）でLawを定義する。** Lawの複雑化と将来の拡張を見据え、規則・制約・適用条件を明示し、定義を再利用・拡張できる形にする。

具体的な構文・言語機能・評価方式は、別途DSLの仕様で定める。

### プログラミング言語やフレームワークに依存しない

**ArchSigの計算核は、プログラミング言語やフレームワークに依存させない。** 言語固有の意味は観測・解釈の側で扱い、静的解析器や型情報もその補助に用いる。Atomから構成する共通構造に対応づければ、言語やフレームワークが混在するソフトウェアにも同じ計算を適用できる。

### 次に必要な観測を計算する

**問いに答えるために、次に読むべき情報も計算対象にする。** 現在の観測では同じに見える変更候補が、Lawを保つかどうかでは異なる場合、その違いを区別する操作や内部値を追加観測として求める。候補間の違いと、実装で確認した不整合は区別する。

Lawの追加・変更時にも必要な観測を見直し、SKILLへ観測箇所とその理由を渡す。未観測の値は、ソースから確認してArchMapを更新する。

## 4. 数学の位置づけ――AtlasやSAGAによる接続

**ArchSigは、Rising Sea論文に記載された構成や結果の再現を目指す。** 実装・計算量・利用体験などのツール側の都合に応じて、構成や結果をアレンジすることを許容する。

Atlasは、選択したLawに十分な読みと、被覆・係数についての比較条件の下で、解像度を変えても障害類の診断が対応することを与える。

SAGAは、意味側の修復問題と、方程式から構成した幾何側の計算を接続する。対応条件と層条件などの下で、障害類の対応から、大域的な修復の存在まで結びつける。

輸送・比較・正規化・変更の分類・再構成も同じ対象上で接続し、診断から修復・変更へ進む。

論文の定理を適用する計算では、その適用条件を保持する。アレンジした部分は、論文との対応・変更点・ツール側で成立する条件と結論を明示する。モデルについての計算結果と、実コードとの対応の確認も区別する。

## 5. 利用体験――AI Agent SKILLを入口にする

入口は、**既存のリポジトリと、理解したいこと・実現したい変更**である。

**ArchSig v0.6.0は、AI Agent SKILLを経由して実行されるAIネイティブツールとして設計する。** 人は普段使うAIエージェントへ目的や制約を伝え、仕様・設計上の選択を判断する。CLIは、SKILLに従うエージェントから呼び出し、人による直接操作を利用の前提にしない。

**分担する仕事は、保存条件を持つ部分構造として扱う。** ArchSigは、観測した操作とLawから、各担当が満たすべき条件と、担当間で共有する対応の条件を計算する。たとえば、口座・送金・会計の変更では、取引IDや状態の対応を揃える条件を、担当するソースと結びつけて渡す。

SKILLは、機能の追加や内部構造の変更を次の流れで進める。

1. **観測と構成。** 既存のArchMapとLawPolicyを基にArchSigを実行し、問いに答える構造を構成する。追加観測や仕様判断が必要な箇所を明らかにする。
2. **変更候補の検討と統合。** エージェントが、保つ構造・変える部分・新たに満たす条件を明示して局所候補を作る。ArchSigが条件を検査し、必要な局所データと保存条件が揃えば、全体の構造と対応へ組み立てる。
3. **実装後の比較。** 実装コードを再観測し、計画した構造との対応を確認して、構造と根拠を更新する。ビルドやテストによる実装の確認も行う。

次の作業は、更新された構造から始める。

人にはソースに結びつく説明・可視化を、AIには対象と対応を照会・操作するインターフェースを提供し、既存のIDEやエージェント基盤から利用できるようにする。

## 6. ArchSigの強みと開発上の価値

| 強み | 開発上の価値 |
| --- | --- |
| アーキテクチャの意味を共通化する | 操作の役割と要求の整合性を、AtomとLawから構成した共通構造で扱う。 |
| プログラミング言語・フレームワークに依存しない | 複数の言語やフレームワークにまたがるアーキテクチャを、同じ構造と計算で解析する。 |
| ソースコードをSource of truthとする | コードに同期した観測と計算により、独立した形式モデルの保守による乖離を防ぐ。 |
| 局所・大域・異なる読みを接続する | 局所の整合・修復可能性と、読みの変更に沿う診断の対応を、適用条件の下で接続する。 |
| 変更そのものを計算対象にする | 保存条件・対応・合成を扱い、設計候補の検討から実装後の比較へ引き継ぐ。 |
| 観測から更新までを一貫して扱う | SKILLが観測・計算・再観測をつなぎ、構造の構築と更新を担う。 |

静的解析やAlloyとの比較では、アーキテクチャ固有の対象・操作・Law・局所性・比較計算を標準で用意し、実装からの観測と更新までつなぐ点を重視する。

確認済みの構造と条件を担当者・エージェント・セッションを超えて再利用し、再確認が必要な箇所から作業を再開する。局所の成果を統合し、並列・長期の作業を大きな変更へ積み上げる。

これらによって、**同じAI能力と同じ人的資源で、完了できる変更の規模や複雑さを広げること**を目指す。生産性への効果は、製品として検証すべき仮説である。

### 応用先

レビュー支援、セマンティックな記憶、意味的ビルド、並列開発支援を、この基盤の利用形態として扱う。

SFTやFieldSigへの接続も可能にするが、ArchSig v0.6.0の実用化を、それらの完成待ちにはしない。

## 7. 設計の判断基準

**ArchSig v0.6.0は、v0.5.xとの互換性を完全に無視し、ゼロから再設計する。** 本コンセプトを基に、実装・スキーマ・コマンド体系・SKILLを設計し直す。

### 問いを起点に、必要な構造を育てる

「この変更で何を保ちたいか」という問いからLawと観測範囲を定め、必要に応じて構造を広げる。確認済みの構造と対応は、後の問いにも利用できるようにする。

### 観測とLawを独立した入力として設計する

ArchMapの観測語彙と、LawPolicyのLaw定義・評価条件を分離し、それぞれを独立に拡張できる構造にする。計算核は両入力から結果を導出し、観測値や診断結果に合わせてLawを暗黙に変更しない。

### 計算結果を、次の作業に使える形で返す

出力の設計は、SKILLがそれを使って観測・候補の修正・分担・統合へ進めるかで判断する。再利用時には、根拠となるソース、Law、成立条件が変更後も有効かを確認する。

### 拡張を、共通構造の中へ位置づける

新しい問題への対応は、Atom、Law、対象、操作、対応のどこを拡張するかで設計する。追加した構造と結果が既存の計算へ接続でき、複数の場面で使えることを重視する。
