# ブログ執筆ガイドライン

この文書は、`outreach/blog/` の研究記事・実務記事・思想記事の執筆と読者向け品質の
レビュー基準を定める。日本語原稿・英語原稿の両方に適用する。
適用対象は新しく執筆する記事に限る（既存記事への遡及修正は対象外）。

記事本文と素材の配置は [Outreach README](../../outreach/README.md) に、
リポジトリ作業の横断規律は [Workflow guideline](../workflow/guideline.md) にある。
論文の執筆は [Paper guideline](../paper/guideline.md)、公開 website の編集は
[Website guideline](../website/guideline.md) が扱う。

## 1. 記事の主軸と読者を決める

執筆前に、記事の種類、想定読者と前提知識、読後に届けたいものを短く言語化する。
これは執筆・レビューの判断材料として、執筆メモやPR本文などレビュー時に参照できる場所に残す（本文への掲載は任意）。

| 種類 | 読者に届けたいもの | 品質の中心 |
| --- | --- | --- |
| 研究記事 | 何を問い、何が分かり、なぜ意味があるのか | 数学へ進む説明の順序と主張の正確さ |
| 実務記事 | 自分の現場で試せる方法と判断材料 | 課題・原因・対処・結果・適用条件の具体性 |
| 思想記事 | 著者の経験や問いを通じた新しい見方 | 著者自身の声と思考のつながり |

分類は媒体ではなく記事単位で決める。複数の種類を含む場合も主軸を一つ決め、
他の要素が主軸の理解を助けているか確認する。独立した説明が必要な話題は、別記事に分ける。

冒頭と要約では、読者がすでに知っている言葉で、今回の話題と読む理由を伝える。
本文で初めて導入する概念は本論の中で順に展開する。TL;DRや用語集は記事に役立つ場合に置く（任意）。

## 2. 数学の難しさと文章が作る難しさを区別する

コホモロジーや層など、内容を理解するために必要な数学的概念は、想定読者に必要な学習を支える
定義・例・計算を添えて正面から導入する。

一方、独自の略語や圧縮表現によって生じる難しさは執筆上の問題として解消し、
書き手が知っている関係を通常の言葉で明示する。

| 語彙の種類 | 扱い |
| --- | --- |
| 標準的な数学・技術用語 | 想定読者に応じて定義・説明・例を添える |
| 研究上必要な新概念 | 何を表し、なぜ必要なのかを説明してから名前を付ける。研究での定義と対応させる |
| 内部用の略称・便宜的な圧縮語 | 対象・操作・関係が分かる通常の表現に展開する |

たとえば「粗側」は、何を粗くした対象なのかを隠してしまう。モデルの比較であれば
「細部を省いて表したほうのモデル」のように、実際の対象と操作を書く。
「正枝」も、何の条件が成り立つ場合なのかを書けばよい。
これらは文脈を確認して展開する例であり、文脈ごとに意味が保たれる表現を選ぶ。
研究上必要な新概念と、書き手の短縮のために作った略称を区別する。

専門語は、想定読者が知っている語や具体例へ落として説明する。
用語をまとめて先に一覧する場合も、本文で必要になる箇所で対象と使い方を具体的に示す。

日本語記事では、自然に通じる日本語を基本にする。英語は固有名、コード上の識別子、
定着した専門用語など、必要な場合に使う。同じ対象は一つの表記で統一する。

## 3. 記事をリポジトリの知識から独立させる

GOALカード、Leanのステートメント、実装、監査記録は記事の根拠として使い、
本文は読者の問いと理解の順序で組み立てる。

- 内部の条件番号、宣言名、完了用語を知らなくても説明を追えるようにする。
- 定理の条件を載せる場合は、何を要求し、どのような失敗を防ぐのかを説明する。
- 数式や記号は対象と役割を導入して使い、定理の成立に必要な条件を保ったまま説明する。
- 結論を理解するために必要な仮定と適用範囲は、その結論の近くに書く。
- 詳細な証明、仕様、監査記録は、読者の目的に応じて別節や参照先に置く。

リポジトリへのリンクは、理解を深めたり根拠を確かめたりするための補足として使い、
本文だけで意味が通るように書く。
記事からリポジトリへリンクするときは、リファクタリングによる移動や削除でのリンク切れを防ぐため、
リポジトリ全体のトップページをリンク先とする。資料を案内する場合は、その内容や名前を文章で説明し、
リポジトリ全体へのリンクを添える。
AI運用を主題にする記事では内部の手順も説明対象になるが、何の問題に対する手順なのかを
記事内で説明する。

## 4. 種類別の執筆指針

ブログでは、読者が主題を理解するために必要な正確さを重視し、既存研究の網羅的な調査、
完全な証明、全仮定の列挙などは記事の主題に応じて取捨選択する。
細部の省略や直感的な説明を活かしつつ、結論の意味を変える誤りや、未証明の内容を証明済みと
扱う記述は修正する。但し書きは本文の流れを妨げない最小限にとどめる。

### 研究記事

中心は「何を問い、何が分かり、なぜ意味があるのか」である。

- 問題、具体例、必要な概念、結果を、理解のつながりに合わせて配置する。
  数学を詳しく扱う記事では、対象と記号を導入し、読者が追える例や計算を用意する。
- 証明の経緯を扱う場合は、反例によって何を学び、考え方がどう変わったかを具体的に説明する。
- 定理、条件付きの帰結、計測結果、予想・展望を読み分けられるようにする。
  簡単な実例の説明から一般的な結果へ進むときは、どこまで一般化されたかを示す。
- Leanの行数やレビュー回数は補足情報にとどめ、数学的な内容と成立条件を中心に説明する。

### 実務記事

中心は「どんな問題に、なぜその対処が効き、どの条件で試せるのか」である。

- 課題・原因・対処・結果を具体的につなぐ。原因が未確定なら、その状態を明示する。
- 計測値には比較条件と測り方を添える。読者が同じ意味で比較できるようにする。
- 試すために必要な手順、環境条件、適用の判断材料を示す。
- AI運用の規則は、実際に起きた問題と、その規則が働いた事例を結び付けて説明する。
- 一つの環境で得た結果は、その環境条件のもとでの知見として示す。

### 思想記事

中心は「著者が何を経験し、何を問い、どう考えるに至ったか」である。

- 著者自身の経験、違和感、判断を文章の軸にする。執筆支援で経験や発言を捏造してはならない。
- 思考の飛躍には、読者が辿れるつながりを作る。
- 比喩や余韻を活かし、実務手順や単一の結論へ無理に回収せず書いてよい。
- 比喩、個人の解釈、事実の記述を明確に書き分ける。
- 数学や哲学の名前を出すときは、その考えが今回の問いにどう関わるのかを書く。

## 5. シンプルな文体と説明

すべての種類の記事（思想記事を含む）で、シンプルでわかりやすい文体を基本とする。
著者らしさは装飾ではなく、経験、問い、判断、具体的な観察を通じて伝える。

- 身近な語と直接的な表現を選び、誰が何をしたのか、何がどう変わったのかを明確に書く。
- 対象と動作を具体的な言葉で直接書く。
- 修飾や括弧書きが重なる文は分け、意味をつなぐ主語や接続を明示する。
- 一度で意味が取れる普通の言い方を選び、必要な説明は省かず残す。

一つの段落では中心となる考えを一つ進め、論理のつながりを文章として明示する。
簡潔さは、読者が関係を復元する負担まで含めて判断する。

同じ主張を言い換えて繰り返す場合は、例、理由、計算、結果など、新しい理解につながる
内容を加える。導入・要約・本文・結びの重複を確認し、理解を助けない反復は削る。

比喩は、理解を助けたり著者の感覚を伝えたりする場面で控えめに使い、意味を取りやすく保つ。
数学的な説明では対象との対応を示して結論を導き、思想記事でも思考の筋道が辿れる形を保つ。

タイトルや冒頭では、問題提起や意気込みを伝えるために少し強い表現を使ってよい
（定理のステートメントと同じ厳密さではなく、本文で具体的な達成と目指す姿が分かる形で評価する）。
「初めて」「唯一」「原理的に」などを具体的な事実の主張として使う場合は、その範囲と
裏付けを確認する。出典のある事実、著者の解釈、将来への期待を読み分けられるようにする。

## 6. 公開前レビュー

レビューでは、執筆前に決めた種類・想定読者・読後に届けたいものを基準とし、
第4節の厳密性の範囲と第5節の表現の許容に従って評価する。
語句に説明が付いているかに加えて、想定読者がその説明を使って考えられるかを確認する。
修正を求めるときは、読者にどのような誤解や理解の支障が生じるかを具体的に示す。

- 記事の中心を自分の言葉で説明できるか。
- 冒頭で想定した前提知識から順を追って理解できるか。
- 独自の略称や内部用語が、読者に通じる表現へ展開されているか。
- 比喩や言い回しが平明で、理解を助けているか。
- 具体例と抽象的な説明の対応を追えるか。
- リポジトリを開かなくても本文の筋道が通るか。
- リポジトリへのリンクが、第3節で定めるトップページへのリンクになっているか。
- 記事の種類に応じた持ち帰りがあるか。
- 主張と根拠が対応し、条件・適用範囲・成果の種類を読み分けられるか。

「難しい」という指摘には、該当箇所と理解が止まった理由を添える。
内容そのものに学習が必要なのか、説明が欠けているのか、独自語彙が妨げているのかを
区別する。本文が約束した前提知識から辿れるかを調べ、想定読者の視点で通読して
読者向け品質を判断する（機械的な語彙チェックは補助として使う）。
